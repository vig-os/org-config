# [PR 278](https://github.com/vig-os/org-config/pull/278) docs(rulesets): record the 30-entry truncation of otterdog's installation map

## What

Documents that the `app_id -> app_slug` map behind the #256 / #262 App-actor
limitations is **truncated at thirty entries**, and makes re-checking it a step
of the otterdog pin bump.

- `README.md` — a new *Known limitations* bullet directly after the #262 one, so
  the pair reads together: otterdog's `get_app_installations`
  (`providers/github/rest/org_client.py:484-491`, 1.5.0, the ADR-0005 pin)
  reaches `GET /orgs/{org}/installations` through the single-shot
  `request_json`, which sends no `per_page` and never reads `Link`, and returns
  `response["installations"]` — one page, while the endpoint paginates at a
  default of **30** and answers with a `{"total_count": N, "installations": […]}`
  envelope. The set it drops is *larger* than #262 describes: these are proper
  org installations, dropped by page position, so "install the App on the
  organization" is not a sufficient mitigation.
- `src/drift_layer/app_actors.py` — the `read_installations` docstring said
  otterdog drops "past 100 installations". It was the one place in this repo
  asserting a threshold for otterdog's behaviour and it asserted the wrong one
  (it assumed otterdog sends the same `per_page=100` this repo does). Corrected
  to 30. **No behaviour change.**
- `justfile.project` — the prose above the `otterdog_version` literal gains the
  two reads no test can make: re-read `get_app_installations` in the new
  otterdog, and re-measure both orgs with
  `gh api /orgs/<org>/installations --jq .total_count`. The
  `otterdog-defaults` paragraph is re-wrapped, not changed.
- `docs/adr/0005-repo-tooling.md` — one clause on the existing *"proposed by
  Renovate and adopted by a human"* Consequences bullet pointing at that
  checklist, rather than a second copy of it.
- `CHANGELOG.md` — one `### Changed` bullet under `## Unreleased`.

## Why

#262 and upstream eclipse-csi/otterdog#732 both reason about an App that is
*not* an org installation, so both are read as saying that installing the App on
the org makes a declaration safe. Truncation says otherwise, and it also makes
the surviving set order-dependent. Unfixed at the 1.5.0 pin and unfixed on
upstream `main` (read 2026-09-25 at `ba3d1f9`, byte-identical). The call is the
odd one out in its own file — `org_client.py` already uses the paged form for
repos, members, advisories and rulesets, and the sibling `app_client.py:32`
pages `/app/installations`.

**Nothing in the fleet is affected today, and it was measured, not assumed:**
`vig-os` **8**, `exo-pet` **12** on 2026-09-25 (re-measured immediately before
this PR), both well under 30.

## The 31–100 band is silent by decision

`read_installations` already reads the same endpoint with `per_page=100`,
refuses a `rel="next"` response and compares `total_count` — but **both signals
only refuse at 101 installations or more**, while otterdog truncates from the
31st. The `total_count > 30` warning that the issue's suggested-fix item 3
proposes was specced, reviewed adversarially and **dropped**: it would fire on
every pull request of an org that crossed 30 — a context that is a required
check downstream (#268) — while naming no remedy (upstream #732 is open and the
single-shot call survives past otterdog 1.6.1), and it could not be suppressed
(`drift-allowlist.toml`'s `[[app_actor]]` is keyed by slug;
`unmanaged-controls.toml` has no threshold operator). The bump-time measurement
is the proportionate guard. Full reasoning:
https://github.com/vig-os/org-config/issues/269#issuecomment-5840052856

## Deliberately NOT done

- **No code.** Documentation, one docstring and a pin-bump comment only — no
  endpoint, engine, workflow, check behaviour or config change, and
  `--controls-report` is unchanged.
- **Nothing posted upstream.** The one-line fix
  (`request_paged_json(…, entries_key="installations")`) plus a unit test in
  upstream's own `pretend.stub` idiom is drafted and verified against upstream
  `main`, and **held**: the #732 comment and the pull request are human steps,
  the PR additionally gated on the Eclipse Contributor Agreement. Nothing here
  claims an upstream state that does not exist yet.
- **#269 stays open after this merges.** Acceptance item 2 is that human
  upstream post, so this body carries `Refs:` and deliberately no closing
  keyword for the issue.
- Consolidating the three consecutive Known-limitations bullets about the same
  map (#262 / #269 / repo-creation) — noted, deferred to whenever one of them is
  next edited.
