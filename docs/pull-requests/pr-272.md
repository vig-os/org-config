# [PR 272](https://github.com/vig-os/org-config/pull/272) docs(rulesets): record that an App bypass actor must be an org installation to be read

## What

Documents the **read**-side requirement for a GitHub App bypass actor on a
ruleset: the App must be an **installation on the organization**, or otterdog
silently drops the actor from its model. Five files, documentation and config
comments only — README *Known limitations*, the `bypass_actors+` note in
`otterdog/vig-os/vig-os.jsonnet`, both `unmanaged-controls.toml` comments, and a
`### Changed` CHANGELOG entry.

## Why

#256 documented the **write** side (`apply` resolves the slug through
`GET /apps/{slug}`, so only a readable App can be written) and left a
one-sentence forward reference to #262 for the read side. That reference named
the symptom but not the mechanism, the upstream tracker, or the contrast that
makes it actionable. #262's acceptance is an `or`; item 2 — *"the limitation is
documented where bypass actors are declared, with the upstream reference"* — is
what this PR delivers.

## Mechanism (otterdog 1.5.0, the ADR-0005 pin)

- `models/github_organization.py:555-558` builds **one** `app_id → app_slug` map
  per org load, from `GET /orgs/{org}/installations` alone. The project's own
  `FIXME` at `:758` says why: GitHub exposes no id→slug endpoint.
- `:758-765` applies that map to every repository ruleset's `bypass_actors`.
  There is no `else`: an unmapped actor keeps its `actor_id` and gains no
  `app_slug`.
- `models/ruleset.py:541-548` then logs
  `fail to map integration actor '<id>', skipping` — into otterdog's log, never
  into `plan.txt` — and `continue`s, so the actor never reaches
  `mapping["bypass_actors"]`.

Both failure directions follow, and neither reaches the pull request: a
**declared** actor is proposed for addition on every `plan` and `apply` never
converges, because a ruleset patch re-sends the whole bypass list
(`models/repo_ruleset.py:63-71`); an **undeclared** one is a standing,
unreported bypass of a protected branch or tag.

## The #732 contrast — the load-bearing part

The same map is applied to `required_status_checks` ten lines below
(`models/github_organization.py:771-777`), but that reader has a fallback the
bypass-actor reader does not: `transform_status_check`
(`models/ruleset.py:145-151`) degrades to `str(integration_id) + ":" + context`,
so an unmapped status check stays **visible and writable** (the write side takes
the `app_slug.isdigit()` branch at `:208-209`). That is exactly why this
repository's own status-check prefixes are numeric `15368:` (#69). A bypass
actor has no numeric form on either side — no `isdigit()` branch at `:649` — so
it does not degrade, it **vanishes**. #262 is the strictly worse variant of
[upstream #732](https://github.com/eclipse-csi/otterdog/issues/732), and one
`bypass_actors` patch upstream would close both.

Verified unfixed at the 1.5.0 pin **and** on upstream `main`
(`models/ruleset.py:545-552` there, identical logic), read 2026-09-25.

## Evidence — nothing here is affected today

Enumerated live rather than assumed: all **fifteen** `Integration` bypass actors
across the readable `vig-os` and `exo-pet` rulesets — `2433383`
`commit-action-bot` (×11), `2930017` `vig-os-release-app` (×3) and one private
App owned by a sibling org (×1) — appear in their org's `/installations`
listing.

Two blind spots, both named in the prose rather than glossed, and both limits of
the billing plan rather than surfaces left unread by choice:

- `vig-os/qms` is private on a Free-plan org — both ruleset endpoints answer
  `403 Upgrade to GitHub Pro or make this repository public`.
- `GET /orgs/vig-os/rulesets` answers `403 Upgrade to GitHub Team`; org-level
  rulesets are a Team/Enterprise feature, so a Free-plan org can hold none.
  (`exo-pet` is on Team, was read in full, and holds no org-level ruleset.)

`just test`: `166 passed`. `just precommit`: every hook `Passed`, L0 prelude
green (`No findings to report. Good job! (67 ignored, 140 suppressed)`,
`jsonnetfmt: OK`, `Validation succeeded`).

## What is deliberately NOT done

- **No `[[control]]` row in this repo's table.** Unlike the #256 write-side gap
  — where a row is pointless because the plan already detects it — a row *would*
  be the only detector here, since the dropped actor is invisible to plan and
  drift alike. It still gets none, for a reason of **fact**, not doctrine: there
  is nothing to assert. The unusual row shape is written down instead, in both
  the live table and the template, for a downstream that does have one:
  `endpoint = "/repos/{org}/{repo}/rulesets/<id>"`,
  `path = "bypass_actors[].actor_id"`, `compare = "set"` — the one row form that
  must carry a ruleset id, because bypass actors are not returned by
  `/rules/branches/{branch}`.
- **No detection.** Surfacing the declared half at plan time is #259's scope
  (one extra `GET /orgs/{org}/installations` on top of the `GET /apps/{slug}`
  reads it already performs). It covers only the declared direction; the
  undeclared-live direction needs a read outside otterdog's model and stays
  open. See the comment on #262.
- **No ADR-0005 correction.** The pin is not wrong; the upstream tool is.
- **The private App's slug and numeric id are not published.** This repository is
  public, so the enumeration reads "one private App owned by a sibling org",
  matching how #256's merged CHANGELOG already words it. The slug stays in the
  issue thread.
- **No upstream comment posted.** The draft for eclipse-csi/otterdog#732 is on
  #262 for Carlos to post by hand.
- **"Neither reaches the pull request" is left as written.** It is true at this
  commit; #259's PR amends it when the declared half starts being reported.

- No endpoint, engine, workflow or ruleset change; `--controls-report` output is
  unchanged.
