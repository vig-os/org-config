# [PR 119](https://github.com/vig-os/org-config/pull/119) chore(config): dismiss stale approvals on push for devkit's Main protection

Closes #118. Approved finding **D7** of the devkit settings review; follows #115 / PR #117.

## Change

One field on `devkit`'s `Main protection` ruleset:

```jsonnet
required_pull_request+: {
  dismisses_stale_reviews: true,   // <- new
  required_approving_review_count: 1,
  requires_code_owner_review: false,
  requires_review_thread_resolution: true,
},
```

`dismisses_stale_reviews` is the otterdog `newPullRequest` field name (vendored `otterdog-defaults.libsonnet:153`, default `false`); it maps to GitHub's `dismiss_stale_reviews_on_push`.

## Why

`Main protection` required 1 approving review and let it survive every subsequent push:

```console
$ gh api repos/vig-os/devkit/rulesets/13444364 --jq '.rules[]|select(.type=="pull_request").parameters|{required_approving_review_count, dismiss_stale_reviews_on_push}'
{"required_approving_review_count":1,"dismiss_stale_reviews_on_push":false}
```

So a reviewer could approve a two-line docs change and the author could then push arbitrary new commits onto the same branch and merge to `main` on the strength of a review that never saw them. The required status checks are `strict` and re-run on every push, so CI could never be stale — the human review could, and after #115 retired the unsatisfiable code-owner gate it is the only human control on `main`.

## Scope

`main` only. `Dev protection` and `Release protection` both require **0** approvals, so there is no review for them to dismiss; adding the flag there would be inert config.

## Live reconciliation — deliberately deferred, see below

Per #69 (otterdog 1.3.4 cannot PATCH a ruleset whose `required_status_checks` use the numeric `15368:<context>` form), this change has to be reconciled live by hand before the apply runs — as #117 did.

**It has not been done yet, and doing it now would break the pending apply.** The apply run for #117 ([31190546346](https://github.com/vig-os/org-config/actions/runs/31190546346)) is still `waiting` on the `production` gate. `otterdog apply` re-plans at execution time against the merged tree, and that tree does **not** declare `dismisses_stale_reviews`. Flipping the live flag now would therefore turn `Main protection` into a pending `~ modify` for that run — a PATCH of a ruleset carrying `15368:` status checks, i.e. exactly the #69 failure — and the run would fail before creating the `Tag protection` ruleset it exists to create.

Sequence to finish this PR:

1. Approve the `production` gate on run [31190546346](https://github.com/vig-os/org-config/actions/runs/31190546346) and let it complete (it creates `devkit`'s `Tag protection` ruleset).
2. `PUT /repos/vig-os/devkit/rulesets/13444364` flipping only `dismiss_stale_reviews_on_push` to `true`, everything else byte-identical passthrough; re-`GET` and verify.
3. Re-run the plan check here — it must show **no** `devkit` resource.
4. Merge; the apply for this PR then has nothing to do for `devkit`.

Until step 2 lands, the plan check below will legitimately show `~ repo_ruleset[name="Main protection", repository=devkit]`. **Do not merge before the plan is clean** — the apply would trip #69.
