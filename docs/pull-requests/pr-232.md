# [PR 232](https://github.com/vig-os/org-config/pull/232) fix(ci): plan on an otterdog pin bump by watching justfile.project

## Summary

Adds `justfile.project` to `plan.yml`'s `pull_request` `paths:` filter, so a PR
that changes **which otterdog version the plan runs** actually gets a plan run.

That file holds `otterdog_version` — the ADR-0005 single source of truth the
workflow's own *Resolve otterdog version pin* step greps at run time — which
makes it the file that selects the binary producing the diff. A pure pin bump
touches no config path, so it matched nothing in the filter:

- #225's 1.5.0 bump (#229) got **no plan run at all**, and an empty plan is that
  issue's acceptance evidence — it had to be produced by hand
  ([`workflow_dispatch` run 35844030809](https://github.com/vig-os/org-config/actions/runs/35844030809),
  `0 to add, 0 to change, 0 to delete`).
- #145 (1.3.4 → 1.4.0) was covered only incidentally, because it also edited
  `otterdog/vig-os/vig-os.jsonnet` and was pulled in by `otterdog/**`.

## One correction to the issue's framing

The issue calls this a lost "merge gate". It isn't, and the distinction is
load-bearing enough to record in the changelog: `Plan` is **not** a required
status check — the `Main protection` ruleset requires exactly one context,
`CI Summary` — and a path-filtered workflow *cannot* be required, because a
required check that never runs leaves the PR pending forever. What a bump was
losing is the **automatic plan evidence on the PR**, not enforcement.

## Also in this PR (comments only)

- **`apply-engine.yml`** keeps omitting the same file deliberately, and now says
  why. (The issue said "`apply.yml` is dispatch-only so it has no paths filter to
  fix" — `apply.yml` is `workflow_call`-only; the push-triggered caller is
  `apply-engine.yml`, which *does* have a filter.) The asymmetry: plan must
  **prove** before merge that the newly pinned engine produces no diff; apply must
  not **mutate** the live org off an engine-version edit carrying no config delta.
- **`template/.github/workflows/plan.yml`** needs no equivalent line and now says
  so, to stop a future reader adding one by symmetry: downstream the pin is the
  `otterdog_version:` input literal inside the caller workflow, already matched by
  `.github/workflows/plan.yml`, and the skeleton ships no `justfile.project` (#56).

`drift.yml` and `testbed-e2e.yml` also resolve the pin but are
`schedule`/`workflow_dispatch` only — no filter exists to fix.

## Scope trade, accepted explicitly

`justfile.project` carries unrelated recipes, so some plan runs will now diff
nothing. It has moved **8 times** in this repo's life — no Renovate manager
matches a bare Just variable (#225) and devkit upgrades preserve it, so it only
moves on a hand edit. A handful of read-only runs against a pin bump silently
losing its evidence is the right trade.

## Acceptance

- [x] `justfile.project` in `plan.yml`'s `pull_request` paths filter
- [x] Rationale recorded inline, so the next reader sees why a `justfile` is in a
      config-paths filter
- [ ] A PR that edits only `otterdog_version` triggers the plan check — **cannot
      be shown by this PR**, which edits `plan.yml` and so matches the filter's
      pre-existing entry. Verified by a follow-up PR touching only
      `justfile.project`.
