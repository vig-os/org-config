# [PR 104](https://github.com/vig-os/org-config/pull/104) chore: release 1.0.0

# Release 1.0.0

Cuts the first release of the org-config engine and rewrites the root README to
describe what v1.0.0 actually ships.

## What is in it

- **`README.md` rewrite** — the README described this repo only as `vig-os`'s own
  config store, with the GitOps tooling summarized in one paragraph and no
  mention of the engine/consumer split M4 shipped. It now covers the Otterdog
  reconciliation model, the three reusable `plan`/`apply`/`drift` workflows and
  their shared `otterdog-mutate` serialization, the `production` human gate,
  issue-only drift with the inventory sweep and allow-list, SOPS/age secrets, the
  least-privilege App auth model, the four testing layers, downstream
  distribution via `template/` (pinned to a release tag/SHA, `exo-pet` pilot),
  the trunk model, and a new **Known limitations** section.
- **`CHANGELOG.md` cut** — the accumulated `## Unreleased` content is frozen into
  `## [v1.0.0] - 2026-08-07` with a fresh empty `Unreleased` section, produced by
  the house `prepare-changelog prepare` + `finalize` pair with
  `DEVKIT_TAG_PREFIX=v`.

No engine, config, or workflow change — `otterdog/`, `secrets/`, and `src/` are
untouched, so this merge triggers no apply.

## Release mechanism deviation

The devkit release pipeline (`prepare-release` -> `release` -> `promote-release`)
cannot drive this repo today. Both blockers are properties of this repo's own
governance, not of the change:

1. **`prepare-release.yml` freeze push is refused.** It commits the frozen
   CHANGELOG straight to `main` via `commit-action`. `org-config`'s `Main
   protection` ruleset requires a pull request and bypasses only
   `OrganizationAdmin`, so the bot push is rejected — the same failure as
   [vig-os/devkit#1227](https://github.com/vig-os/devkit/issues/1227), which was
   first seen on this repo and whose resolution explicitly rules out adding the
   commit App as a bypass actor on `main` (a bot that can write `main` can
   rewrite the applied org configuration). Under the trunk model the release
   branch is also cut from post-freeze `main`, so the draft release PR would have
   an empty diff.
2. **`release-core` requires an approved release PR** for a final release, and
   the sole maintainer cannot approve their own PR.

So the freeze is landed here as a reviewed PR (strictly more auditable than the
bot push it replaces) using the same `prepare-changelog` tool the pipeline runs,
and the tag + GitHub Release are created manually from the merge commit with
notes from this CHANGELOG section. End state is identical to a pipeline release:
`v1.0.0` annotated tag, published GitHub Release, `## [v1.0.0] - 2026-08-07` plus
an empty `Unreleased` on `main`.
