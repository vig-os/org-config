# [PR 292](https://github.com/vig-os/org-config/pull/292) chore(config): retarget tessera's main to the flake gate

## Description

Closes #234. One declared field on `tessera` › `branch_protection_rules` › `main`, plus the comment
that explains it and the `requires_strict_status_checks` call beside it.

The issue was filed as blocked on an external trigger — *"nothing to do until tessera changes what
`main`'s CI emits"*. **That trigger has fired.** tessera's alpha promotion
[`5281db2a`](https://github.com/vig-os/tessera/commit/5281db2ab4bb129f45389ebf2f9ce0b5e2e6eb31)
(2026-09-23T22:13Z, *"release: v0.1.0-alpha.1 — flip main to the first alpha (dev → main)"*)
replaced `main`'s tree with dev's then-tree, which took `main`'s `ci.yml` with it.

Verified live, today:

- `GET /repos/vig-os/tessera/commits/main/check-runs` reports `nix flake check`,
  `nix flake check (x86_64-linux)` and `nix flake check (aarch64-linux)`, every one of them from
  app `15368` (`github-actions`). No `CI Summary` job exists anywhere on `main` any more.
- `GET /repos/vig-os/tessera/branches/main/protection` still declares
  `contexts: ["CI Summary"]`, `checks: [{app_id: 15368, context: "CI Summary"}]`, `strict: true`.

So live `main` currently requires a context that can never report on a `main`-origin PR — the exact
mirror image of the #226 defect that #231 fixed, arrived at from the other side.

On the `dev` side, [tessera#442](https://github.com/vig-os/tessera/pull/442) (merged 2026-09-24,
devkit scaffold adoption) gave `dev` a **second** workflow also named `CI`: `ci.yml` emits
`CI Summary`, `Dependency Review`, `Lint & Format`, `Tests`, `Commit Messages`, `Scaffold Drift`,
`Devkit staleness` and `Resolve toolchain`, while `nix-check.yml` emits the three flake contexts.
A `pull_request` run uses the workflow files from the PR's merge ref, so the contexts a PR into
`main` reports depend on where it branched from — and `nix flake check` is the **only** context
both a `main`-origin PR and a `dev` → `main` promotion PR produce. It is now the single declared
requirement.

**Un-prefixed, deliberately.** The prefix explanation added in #231 is preserved verbatim in the
comment, because it is the part that bites past review: `tessera` is the last repo in this config
still on *classic* branch protection rules, where otterdog resolves a status-check prefix as an app
**slug** via `GET /apps/{slug}` with no numeric branch. The `15368:` form every ruleset here uses is
ruleset-only syntax and would `404` at **apply** — past the `production` gate — while `plan` stayed
green. Un-prefixed binds to `github-actions` = app `15368`, matching live `dev`.

**`requires_strict_status_checks` stays `true`**, and the issue's "re-check that call" is answered
in the comment rather than left silently inherited: live `dev` deliberately runs `strict: false`
because it moves constantly, so re-running both arch legs on every push would cost more there than
up-to-date-ness is worth; `main` is release-only and moves rarely, so the same re-run is cheap and
the guarantee is worth more on a release branch.

**Deliberately out of scope.** The same `tessera` block carries `default_branch: 'dev'` with a
comment saying to *"flip back to the vendored `main` default at the first alpha"*. That condition is
now satisfied too, but it belongs to the #215/tessera#383 lineage, not to #234, and is untouched
here.
