# [PR 247](https://github.com/vig-os/org-config/pull/247) docs: record that otterdog does not model ruleset rule parameters

Refs #246. Documentation only — no jsonnet, ruleset, workflow or table-row
change. Keep #246 open as the tracker for adopting the upstream fix.

## What was wrong

Two claims in this repo said, or implied, that Otterdog models what is *inside*
a repository ruleset's rules:

1. `unmanaged-controls.toml`, "Repository ruleset internals": a row for a public
   repo "would duplicate a modelled control ... because otterdog models rulesets
   and the plan already diffs them".
2. `README.md`: the enumeration of the controls Otterdog **cannot model** listed
   SHA-pinning, fork-PR approval, new-repo security defaults and org-secret
   visibility/readers — and no ruleset rule parameter at all.

Otterdog models the ruleset **object** and the rule parameters its schema knows;
it does not model `allowed_merge_methods` on a `pull_request` rule (every
version through 1.6.0, the current pin included). That parameter is worse than
merely invisible: `plan` shows no diff, and `apply` re-`PUT`s the rule *without*
it, so GitHub's default-on-omit — all three merge methods — is restored each
time the ruleset is touched.

## Evidence

On 2026-08-08 09:34 CEST one routine apply by the org-config App reverted a
hand-set `["merge"]` on **ten rulesets across four repos** (`commit-action`,
`devkit`, `sync-issues-action` Dev/Main/Release + `org-config` Main). Each is
provable through `GET /repos/{org}/{repo}/rulesets/{id}/history/{version}`; all
ten were re-checked for this PR, and all ten are still widened live. The
cleanest single case is `org-config` Main protection (19092020): version
43742326 (User, 2026-07-20) `["merge"]`, next version 45947063 (Bot,
2026-08-08) `["merge","squash","rebase"]`, no config change between them.

`docs/pull-requests/pr-117.md:172` and `docs/pull-requests/pr-119.md:210` record
hand-`PUT`s merged 2026-08-07 that rebuilt each payload from a fresh `GET`
specifically so `allowed_merge_methods` passed through verbatim. The next
morning's apply wiped it.

Filed upstream: eclipse-csi/otterdog#768.

## What this PR records

- **`unmanaged-controls.toml`** — the section comment now separates the ruleset
  *object* (modelled, plan-diffed on a public repo, so no row) from rule
  parameters that are modelled by neither leg, and adds an "unmodelled rule
  parameters" block: the incident, the decision that the **modelled repo merge
  settings** (`houseMergePolicy` in `otterdog/vig-os/house-defaults.libsonnet`)
  own the merge-method policy, why no assertion row is added (it would open an
  issue every time this engine's own apply re-widened the value — self-inflicted
  drift noise over a dual source of truth), the `#768` exit criterion, and that
  `require_extra_approval_for_unattributed_changes` needs no action because
  GitHub's default-on-omit is `true`, the value we want.
- **`README.md`** — the "cannot model" enumeration now includes the
  `pull_request`-rule parameters, states that Otterdog models the ruleset object
  rather than every parameter in it, notes that apply actively restores the
  default for an unmodelled rule parameter, and points at the TOML for why merge
  methods deliberately get no row.
- **`CHANGELOG.md`** — one `## Unreleased` / `### Changed` entry; the posture is
  user-visible to consumers reading the controls table.

## Deliberately not done

No hand re-narrowing of the ten rulesets (the next apply re-widens them), no
`unmanaged-control` row, no jsonnet change. The one capability deferred until
#768 lands is per-branch merge-method granularity, which nothing here uses.
