# [PR 231](https://github.com/vig-os/org-config/pull/231) chore(config): require a reportable check on tessera's main

## Description

Implements **step 1** of #226: `tessera`'s `main` branch protection now requires a status context `main` can actually report.

The rule demanded `any:nix flake check`, which no workflow on `main` produces — `main`'s `ci.yml` defines exactly two PR jobs, `Dependency Review` and `CI Summary`, and its own header comment records that the real gate *"lives on the development branch"*. The required check could never report, so every `main` PR merged by admin override (`enforce_admins` is off, the only reason `main` was not simply frozen). Same always-bypassed-control pathology as #195 / #115 / #167; flagged by the merger of [tessera#383](https://github.com/vig-os/tessera/pull/383) and never followed up.

It now requires `CI Summary` — `main`'s own aggregating job (`needs: [dependency-review]`, `if: always()`, exits 1 when dependency-review failed), so one context covers the lane. `requires_strict_status_checks` stays on and, with a context that can report, finally means something.

**What this buys, stated plainly:** `main` runs one real job, so the gate means *no new high-severity dependency vulnerabilities*. Thin — but satisfiable, honest, and it ends the routine bypass. The deeper gate is step 2, at the first alpha cut, when `main` inherits the real CI.

### The prefix form is the load-bearing detail

The context is deliberately **un-prefixed**, binding it to the `github-actions` app exactly as the neighbouring `dev` rule does.

The numeric `15368:` form used everywhere else in this config is **ruleset** syntax (`models/ruleset.py`, `elif app_slug.isdigit()`). `tessera` is the only repo here still on classic `branch_protection_rules`, where otterdog resolves the prefix as an **app slug** via `GET /apps/{slug}` with no numeric branch (`models/branch_protection_rule.py` → `get_app_node_ids` → `rest/app_client.py`). A `15368:` prefix would have resolved as `GET /apps/15368`, 404'd, and raised `RuntimeError: failed retrieving app node id` — and because that resolution sits on the write path, **plan would have stayed green and the failure would have landed at apply**, past the `production` approval.

Re-verified against the **newly pinned 1.5.0** (#229 landed while this was in progress), not just the 1.4.0 I first checked: `branch_protection_rule.py` is unchanged on this path — no `isdigit` branch, un-prefixed still defaults to `github-actions`.
