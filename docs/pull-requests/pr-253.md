# [PR 253](https://github.com/vig-os/org-config/pull/253) chore(secrets): grant tessera the org App secrets its devkit scaffold reads

Closes #252. Unblocks [tessera#364](https://github.com/vig-os/tessera/issues/364).

## What

`tessera` is added to `selected_repositories` on exactly four org secrets:

| Secret | Why |
|---|---|
| `COMMIT_APP_CLIENT_ID` | managed `sync-issues.yml` mints the commit token |
| `COMMIT_APP_PRIVATE_KEY` | same |
| `DEVKIT_UPGRADE_APP_CLIENT_ID` | managed `devkit-upgrade.yml` opens the adoption PR |
| `DEVKIT_UPGRADE_APP_PRIVATE_KEY` | same |

Without them the failure is silent — the trap this config's own
`DEVKIT_UPGRADE_APP_ID` comment already warns about: *"its upgrade workflow fails
with an empty credential and no error"*.

## Which four, and why not six

Derived from tessera's freshly scaffolded files rather than assumed, because the
ID form is per-repo and these lists deliberately differ:

- `sync-issues.yml` reads `client-id: ${{ secrets.COMMIT_APP_CLIENT_ID }}` with
  **no** numeric fallback;
- `devkit-upgrade.yml` takes the legacy numeric `DEVKIT_UPGRADE_APP_ID` only as a
  fallback — `if { [ -z CLIENT_ID ] && [ -z ID_LEGACY ]; } || [ -z PRIVATE_KEY ]`.

So the client-ID form alone satisfies both, and `tessera` is **deliberately
absent** from `COMMIT_APP_ID` and `DEVKIT_UPGRADE_APP_ID`. Adding it there would
hand the repo a credential nothing reads and enlarge exactly the surface #112
exists to retire. tessera becomes the **first repo on the client-ID form from day
one** — every other entry on those lists retires with its repo's re-scaffold;
this one never needs to.

## Not just the arrays

The prose above each list is updated too. Those comments are the only record of
which repo sits on which ID form and why; a silent list edit would leave them
quietly wrong — the same class of error #225 found in ADR-0005.

`tests/conftest.py`'s `DECLARED_ORG_SECRETS` moves in lockstep: it is the L1
ground truth that the generated org-secret assertion families (#116) compare live
metadata against. Its guard failed on the first attempt and caught the omission
before CI would have.

## Checked, needing no action

- **`GHCR_PULL_TOKEN`** — referenced by the scaffolded `ci.yml` and
  `sync-issues.yml`, but it is not an org secret, not in this config, and not a
  repo secret anywhere: `h5v` runs the same scaffold with **zero** repo secrets.
  It is an optional fallback for pulling the public devcontainer image, which
  `GITHUB_TOKEN` covers.
- **`CACHIX_AUTH_TOKEN`** — declared here as a repo secret for the one repo that
  uses it, and optional in `ci.yml`.

## Verification

- `just test` — 145 passed.
- `just precommit` — full suite green, exit 0.
- Config only: four arrays plus the comments above them. No new secret, no value,
  no visibility change, no repo/ruleset/workflow change.

## Expect on the plan

Four `~ modify` lines against the four secrets — **plus two unrelated
deletions**: `tessera` carries two undeclared repo secrets (`RP_APP_ID`,
`RP_APP_PRIVATE_KEY`, created 2026-09-23 for release-plz) that show as proposed
deletions on every plan right now. They are untouched by this change, and nothing
can delete them — `apply.yml` omits `--delete-resources`. Their fate is part of
[tessera#441](https://github.com/vig-os/tessera/issues/441).

## [Comment #2](https://github.com/vig-os/org-config/pull/253#issuecomment-5810366705) by [@c-vigo](https://github.com/c-vigo)

_Posted on September 24, 2026 at 08:09 AM_

### Merging this PR does **not** grant the access on its own

Worth stating prominently, because the plan output is misleading if read quickly.

The plan on this PR reports **`0 to add, 0 to change, 0 to delete`** for the four secrets — no `~ modify` lines at all, despite four `selected_repositories` arrays changing. That is not a missed diff: the nine org secrets here carry a `'********'` dummy value, so `include_for_live_patch` is false and otterdog excludes them from live patches entirely. `apply` will not touch them either.

This config already documents the consequence, in the comment above `DEVKIT_UPGRADE_APP_ID`:

> Once visibility is `selected`, the list is editable without the secret value via `PUT /orgs/vig-os/actions/secrets/<NAME>/repositories` (#123).

So the split is: **this PR is the committed ground truth; the live grant is a hand API call.** Both are required, and neither is sufficient alone. Verified live before the call — `tessera` is absent:

```
$ gh api orgs/vig-os/actions/secrets/COMMIT_APP_CLIENT_ID/repositories --jq '.repositories[].name'
commit-action devkit devkit-smoke-test h5v org-config scitadel sync-issues-action
```

The single-repo add endpoint is used rather than the whole-list `PUT`, so an existing list cannot be clobbered by a stale local copy:

```bash
TID=$(gh api repos/vig-os/tessera --jq .id)
for s in COMMIT_APP_CLIENT_ID COMMIT_APP_PRIVATE_KEY \
         DEVKIT_UPGRADE_APP_CLIENT_ID DEVKIT_UPGRADE_APP_PRIVATE_KEY; do
  gh api -X PUT "orgs/vig-os/actions/secrets/$s/repositories/$TID" && echo "granted: $s"
done
```

Verify with the same read as above; each of the four lists should then include `tessera`.

**Do not merge this and assume tessera is unblocked.** If the declaration lands without the API call, the committed ground truth claims an access that does not exist, and `tessera`'s first scheduled `sync-issues` run fails with an empty credential and no error — the exact failure this PR exists to prevent, just relocated.

The two `RP_APP_*` deletions in the plan are the unrelated pre-existing drift noted in the description, untouched by this change.
