## [2.0.0] - TBD

### Added

- **House ruleset shapes in `house-defaults.libsonnet`** ([#294](https://github.com/vig-os/org-config/issues/294)): the overlay now exports `mainProtection(checks)`, `devProtection(checks, bypass)`, `releaseProtection(checks, bypass)`, `signedCommits()` and `tagProtection(bypass)` next to the merge policy, encoding the rule [ADR-0008](docs/adr/0008-repository-protection-and-merge-policy.md) states. `mainProtection` is the house `Main protection` standard — 1 approval with stale-review dismissal, review threads resolved, code-owner review off, the given CI aggregator required and strict, and `#OrganizationAdmin` as the only bypass, in `pull_request` mode — and with `checks = []` it declares no status-check rule at all (tier B: a repo with no aggregator yet gets the review half without a check that could never report). Every repo-specific value — status-check contexts and bot bypass actors — is a parameter, so the file stays org-neutral and `template/otterdog/YOUR_ORG/house-defaults.libsonnet` remains a byte-identical copy (ADR-0006). The shapes are additions: `newRepoRuleset` is still re-exported, and a repo that deviates overrides a field on the returned ruleset with the reason beside it. They carry no merge-method policy on purpose — the repo fields own it until eclipse-csi/otterdog#768 ([#246](https://github.com/vig-os/org-config/issues/246)).

- **`plan` now checks every declared App slug against the two calls otterdog makes and the plan diff does not** ([#259](https://github.com/vig-os/org-config/issues/259)): a new `drift-layer --app-actors-report` mode, wired into `plan.yml` between the otterdog run and the report build, and folded into the marker-upserted PR comment and the job summary. Otterdog's read and write paths resolve a GitHub App differently, which is why this class of config passes review and fails on apply — the write path calls `GET /apps/{slug}` (`models/ruleset.py:649`, `:177-189`, `models/branch_protection_rule.py:348`, `models/environment.py:244`), while the read path never does, mapping `actor_id` back to a slug from `GET /orgs/{org}/installations` instead. The mode runs **two independent** checks with the installation token the job already minted. First, `GET /apps/{slug}` per declared slug: a `403`/`404` means `apply` will fail on any add or change of that resource, including one already live, because a ruleset patch re-sends the whole bypass list — the [#256](https://github.com/vig-os/org-config/issues/256) case. Three of the four sites abort the patch and the fourth, an environment reviewer, is caught and **skipped** (`providers/github/__init__.py:502-506`), leaving a protection that was never written, so the report separates them. Second, membership of the org's App installations, for the two sites whose read path needs it: a declared App the org has no installation for is dropped outright as a bypass actor (`models/ruleset.py:541-548`) or read back in its numeric `<id>:context` form as a status check (`:145-151`), so `plan` proposes the same change on every run and `apply` never converges — the detection half of [#262](https://github.com/vig-os/org-config/issues/262). That second check is deliberately **not** applied to branch-protection status checks or environment reviewers: an unprefixed branch-protection check resolves to the implicit `github-actions`, a first-party App that is never an org installation and that this org's own `tessera` rules declare and plan clean — asking for an installation there would fire on green config, the exact failure mode rejected when #256 was spiked. Both checks read the **declared** config only: an actor that exists live but is declared nowhere needs a live ruleset read (which a Free-plan private repo refuses anyway) and is not covered, and the report says so. Declared actors are extracted token-free — `plan.yml` evaluates the committed jsonnet with otterdog's own `jsonnet_evaluate_file`, the exact call `GitHubOrganization.load_from_file` makes (`models/github_organization.py:536`), verified identical to a `go-jsonnet` evaluation of the same file — so only the two reads are credentialed. The finding is **advisory**: the mode always exits 0 — it catches every exception itself rather than relying on the workflow wrapper — no new step can fail the job, and `steps.plan.outputs.rc` keeps its meaning, so *Fail on plan error* still means config/auth/harness and never drift. That posture is not a convenience: `Plan` is not a required check *in this repository* (ADR-0007 Axis D, [#236](https://github.com/vig-os/org-config/issues/236)), but the only consumer org makes its plan context a required check on `main` and ships no `paths:` filter for that reason ([#268](https://github.com/vig-os/org-config/issues/268)), so every step added to this reusable workflow sits on a downstream merge gate for every pull request — each of the three new steps is therefore guarded, `continue-on-error: true` and `if:`-gated on the guard's output, and the comment body now reserves the fragment's bytes inside the 55000-byte budget so an over-long body can never 422 the upsert and fail that gate. A read that fails for any other reason (401, 0, 5xx, a truncated page) is reported as **not checked**, never as a finding — including a rate-limit `403`, which GitHub renders identically to a permission `403` and which the step immediately after a full org read on the same token is the likeliest to hit: `ApiError` now carries the response headers, and a `403` with `retry-after` or `x-ratelimit-remaining: 0` is classified as undetermined rather than as "`apply` will fail on these". A slug that is unresolvable **by design** — the standard case is a private App owned by a sibling org, on a ruleset that is already live and correct and unrepairable until upstream [#772](https://github.com/eclipse-csi/otterdog/issues/772) lands — takes an `[[app_actor]]` entry (slug + reason) in `drift-allowlist.toml`, the third section of the same governance file as `[[expected]]` and `[[unmanaged]]`: the check still names the slug on every run, under *known and suppressed* with its reason, so the suppression is reviewed rather than silent and the finding list keeps meaning something. `vig-os` adds no entry — all three slugs it declares resolve — and the shape is documented in `template/drift-allowlist.toml` for the org that will need one. `plan.yml`'s own `paths:` filter gains `src/drift_layer/**`, `pyproject.toml` and `drift-allowlist.toml`, because the engine's source now selects part of what the plan report says and a change to it would otherwise ship with no plan run at all (the [#230](https://github.com/vig-os/org-config/issues/230) lesson). Downstream callers inherit the step on their next engine pin bump with no change to their caller workflow — `plan.yml` gains the `.drift-engine` checkout `drift.yml` already uses ([#169](https://github.com/vig-os/org-config/issues/169)), and `template/` changes only in that allow-list comment. **Proof limits, stated:** this PR's own plan run proves the green path only — three declared slugs all `200`, the org's installations read whole, `github-actions` correctly not flagged — while the unresolvable, suppressed and rate-limited paths are unit-tested, and the downstream `.drift-engine` checkout is first exercised at the next consumer pin bump.

- **"Otterdog models rulesets" is corrected — it models the ruleset *object*, not every parameter inside a rule, and the merge-method policy is owned by the repo settings** ([#246](https://github.com/vig-os/org-config/issues/246)): two claims in this repo were over-broad in the same direction. `unmanaged-controls.toml`'s "Repository ruleset internals" comment argued that a row for a public repo "would duplicate a modelled control, which is exactly what this table is not for", and `README.md` enumerated the controls Otterdog **cannot model** without naming ruleset rule parameters at all — so a reader concluded that anything inside a ruleset on a public repo is plan-diffed. It is not. Otterdog (every version through 1.6.1, the current pin included) does not model the `allowed_merge_methods` parameter of a `pull_request` rule, and an unmodelled *rule* parameter is worse than merely invisible: `plan` shows no diff because there is no model field, and `apply` re-`PUT`s the rule **without** it, so GitHub's default-on-omit — all three merge methods — is restored every time the ruleset is touched. On **2026-08-08** one routine apply by the org-config App did exactly that to **ten rulesets across four repos** (`commit-action`, `devkit`, `sync-issues-action` Dev/Main/Release plus `org-config` Main), each dropping a hand-set `["merge"]`, and it went unnoticed for six weeks; every row is provable through `GET /repos/{org}/{repo}/rulesets/{id}/history/{version}` — `org-config` Main protection is the cleanest, a human version (43742326, 2026-07-20) carrying `["merge"]` followed directly by a bot version (45947063) carrying all three, with no config change between them. This repo had already recorded the care that was wasted: [`docs/pull-requests/pr-117.md`](docs/pull-requests/pr-117.md) and [`pr-119.md`](docs/pull-requests/pr-119.md) document hand-`PUT`s on 2026-08-07 that rebuilt each payload from a fresh `GET` precisely so `allowed_merge_methods` passed through verbatim — wiped the next morning. Filed upstream as [eclipse-csi/otterdog#768](https://github.com/eclipse-csi/otterdog/issues/768). The **decision** now documented in both files: **repo merge settings own the merge-method policy**. `allow_merge_commit` / `allow_squash_merge` / `allow_rebase_merge` *are* modelled, are declared once in `otterdog/vig-os/house-defaults.libsonnet` (`houseMergePolicy` — merge commits only), and are therefore plan-diffed on every config PR and drift-guarded daily; all four affected repos sit on that policy by construction, so merge-only is still enforced where a contributor meets it, and the widened ruleset parameter cannot offer a button the repo settings do not expose. The ruleset-level parameter stays at the platform default **by decision**, not by neglect. Re-narrowing the ten rulesets by hand is rejected as permanent toil (the next apply re-widens them, with no signal), and an `unmanaged-control` row asserting `["merge"]` is rejected for a subtler reason worth stating: the row would be *correct* and would open an issue every time this engine's own apply re-widened the value — self-inflicted drift noise over a dual source of truth for one policy, with the table asserting a state the tool actively fights. The one capability genuinely deferred is per-branch merge-method granularity, which nothing here uses. The neighbouring unmodelled parameter `require_extra_approval_for_unattributed_changes` needs no action and the comment says so: GitHub's default-on-omit is evidently `true` (it reads `true` in every version above, human- and bot-written alike), which is the value we want. The exit criterion is written into both files — when the [ADR-0005](docs/adr/0005-repo-tooling.md) otterdog pin reaches a version fixing #768, `allowed_merge_methods` gets declared in the jsonnet as ordinary config, matching **each repo's declared merge policy** rather than a blanket `["merge"]` mixin: the house policy is merge commits only, but `qms` restates the retired `legacyMergePolicy` fields inline (all three merge methods) and `org-config-testbed` carries `orgs.upstreamMergePolicy` (`otterdog/vig-os/vig-os.jsonnet`), so one blanket declaration would silently narrow any of them that later gains a ruleset — the same class of unnoticed narrowing this entry exists to record, only self-inflicted. Today the distinction is latent, because every ruleset-carrying repo (`commit-action`, `devkit`, `devkit-smoke-test`, `org-config`, `scitadel`, `sync-issues-action`) sits on the house policy; the declaration must still be derived per repo, not assumed. #246 stays open as that tracker. Documentation only: no jsonnet, ruleset, workflow or table-row change, and `--controls-report` is unchanged.

- **The `template/` starter no longer tells a downstream org that Otterdog cannot read its private repositories' rulesets** ([#248](https://github.com/vig-os/org-config/issues/248)): three places still asserted the read gate that [#225](https://github.com/vig-os/org-config/issues/225) retired when it moved the pin to otterdog **1.5.0** for engine `v1.4.0`. `template/unmanaged-controls.toml` — the file every downstream org copies — opened its ruleset section with *"Otterdog cannot read live rulesets on a private repo below Enterprise, so on a private Team-plan org they are precisely the controls with no other detector"* and then recommended "the two rows worth holding"; `README.md` said ruleset internals are assertable *"which matters most on a private repo where Otterdog cannot read rulesets at all"*; and this repo's own `unmanaged-controls.toml` held the capability *"for downstream orgs on Team/Enterprise, whose private repos otterdog cannot read"*. Upstream [eclipse-csi/otterdog#731](https://github.com/eclipse-csi/otterdog/pull/731) removed the plan-and-visibility gate from **both** ruleset read paths — which is precisely what closed [#107](https://github.com/vig-os/org-config/issues/107) / [upstream #729](https://github.com/eclipse-csi/otterdog/issues/729) and released the [#205](https://github.com/vig-os/org-config/issues/205) downstream conversions — so repository rulesets are read on every plan tier and both repo visibilities, the fields Otterdog's schema models are plan-diffed everywhere, and a row asserting one now *duplicates a modelled control*: the template was recommending exactly what the shipped table's own comment rejects. The README already recorded the correction under "Known limitations", so the repo contradicted itself. Each passage is rewritten to say when a row is warranted rather than which repos are unreadable: a rule parameter Otterdog does not model ([#246](https://github.com/vig-os/org-config/issues/246), [upstream #768](https://github.com/eclipse-csi/otterdog/issues/768)), a ruleset deliberately kept out of the config, and — the stronger case now — **organization**-level rulesets, which #731 made readable but which `GitHubOrganization.validate()` still refuses to declare below Enterprise ([upstream #763](https://github.com/eclipse-csi/otterdog/issues/763)), leaving them hand-managed with a row here as their only detector. The two example rows stay exactly as they were, re-labelled as the *shape* a row takes rather than rows to hold by default, so a consumer reading the starter still learns the `/repos/{org}/{repo}/rules/branches/{branch}` form and the `compare = "set"` semantics. Untouched by design: `docs/issues/*.md` and `docs/pull-requests/*.md`, which are archival records of what was true when written; `template/README.md`'s migration note, which already says "previously unreadable"; and the `otterdog-defaults` `v0.13.1` pin, which is held for the `max_cache_size_gb` HTTP 402 reason and has nothing to do with reads. Documentation and template comments only — no row, endpoint, engine, workflow or config change, and `--controls-report` is unchanged.

- **Renovate proposes the otterdog pin bump; a human still adopts it** ([#250](https://github.com/vig-os/org-config/issues/250)): the [ADR-0005](docs/adr/0005-repo-tooling.md) `otterdog_version` pin was moved entirely by hand across **five** literals, because `renovate.json` enabled only `github-actions`, `pep621` and `npm` — none of which matches a bare Just variable or a workflow input `default:` — and defined no `customManagers`. - **The installation map behind the two App-actor limitations is documented as truncated at thirty entries, which makes the dropped set larger than either of them describes** ([#269](https://github.com/vig-os/org-config/issues/269)): [#262](https://github.com/vig-os/org-config/issues/262) and [upstream #732](https://github.com/eclipse-csi/otterdog/issues/732) both reason about an App that is *not* an org installation, and both are therefore read as saying that installing the App on the organization makes a declaration safe. It does not. The map is built from **one unpaginated call** — `providers/github/rest/org_client.py:484-491` in otterdog **1.5.0**, the [ADR-0005](docs/adr/0005-repo-tooling.md) pin, reaches `GET /orgs/{org}/installations` through the single-shot `request_json`, which sends no `per_page` and never reads the `Link` header, and returns `response["installations"]`, one page — while that endpoint paginates at a default page size of **30** and answers with an envelope (`{"total_count": N, "installations": [...]}`). So past the thirtieth installation the rest are dropped silently; `total_count`, in the same response body, is never compared against the entries received; and the Apps that vanish are **proper org installations**, dropped purely by page position, which also makes the surviving set depend on the order GitHub returns them in — the same committed config can plan differently on two runs after an unrelated App is installed or removed. Verified against the published `otterdog-1.5.0-py3-none-any.whl` and unfixed on upstream **`main`** on 2026-09-25 (`ba3d1f9`; the call is byte-identical there and the map has moved to `models/github_organization.py:576`). The call is the **odd one out in its own file**: the same `org_client.py` already uses the paged form for repos, members, security advisories and rulesets, and the sibling `app_client.py:32` pages `/app/installations` — so the fix is that one call swapped for `request_paged_json(…, entries_key="installations")`, which is **drafted and verified against upstream `main` with a unit test in the upstream style — and not posted**: it is held for [upstream #732](https://github.com/eclipse-csi/otterdog/issues/732) rather than opened as a third upstream issue, since it is the same map, the same file and the same patch, and both the #732 comment and the pull request are human steps (the pull request additionally gated on the Eclipse Contributor Agreement), so nothing here claims an upstream state that does not exist yet. **Nothing in the fleet is affected today, and it was measured rather than assumed:** `gh api /orgs/<org>/installations --jq .total_count` answered **8** for `vig-os` and **12** for `exo-pet` on 2026-09-25. Both orgs sit at **8** and **12**, the condition the issue itself attaches to that item (*"if either org approaches 30"*) is not met, and the full reasoning is recorded [on the issue](https://github.com/vig-os/org-config/issues/269#issuecomment-5840052856); if either org does approach 30 while upstream is unfixed, the warning becomes worth filing on its own terms, with an otterdog-version gate and a test asserting silence once upstream is fixed. The bump-time measurement is the proportionate guard in the meantime, and the docstring in `app_actors.py` that said otterdog drops "past 100 installations" is corrected to say 30, since it was the one place in this repo asserting the wrong threshold. Documentation, a docstring and a pin-bump comment only — no endpoint, engine, workflow, check behaviour or config change, and `--controls-report` is unchanged.
- **`ORG_CONFIG_APP_CLIENT_ID` is decided to stay an Actions secret, with the reason, and the runbook now states that a disclosed Client ID is not a rotation trigger** ([#270](https://github.com/vig-os/org-config/issues/270)): the value has never been confidential — `GET https://api.github.com/apps/vig-os-org-config` answers **200 to an anonymous caller** and returns `client_id` plus the full **17-permission** grant (re-probed 2026-09-28) — while the repo held it as a bootstrap secret beside the PEM under a runbook heading that says *"never managed as code"*, and said nowhere that its publication is harmless. The **decision (2026-09-28) is to keep it a secret**, knowingly: the secret buys **uniformity, not confidentiality** — every consumer hands it to `actions/create-github-app-token` in the same breath as the private key (`client-id:` beside `private-key:`), so one `secrets:` mechanism covers the pair, and the three sibling `*_APP_CLIENT_ID` **org** secrets the client-ID convention ([#112](https://github.com/vig-os/org-config/issues/112)) created are declared the same way (`otterdog/vig-os/vig-os.jsonnet:66`, `:124`, `:189`), so a variable here would make this App the exception rather than the rule. The alternative's cost is the **cutover, not the edit**: an engine reading `vars.ORG_CONFIG_APP_CLIENT_ID` while a downstream caller still passes `secrets.ORG_CONFIG_APP_CLIENT_ID` does not fail loudly, because an undefined `vars.` reference resolves to the **empty string** — a silent empty credential, failing late in the token step or, on the scheduled `drift` leg, in a run nobody is watching — so a move to a variable is only safe inside a coordinated pin bump. `docs/runbooks/github-app.md`'s **Bootstrap secrets** section carries all of it: that the Client ID is an identifier and not a credential (it mints no token without the key that signs the JWT), that finding it in a log, a screenshot or a stranger's `curl` is **not an incident and starts no rotation**, that [Key rotation](docs/runbooks/github-app.md#key-rotation) is triggered by the schedule or by exposure of `ORG_CONFIG_APP_PRIVATE_KEY` and by nothing else — restated at the rotation step itself, which previously said only that the Client ID *does not change* — and the decision plus a four-step sequence for a future variable migration (both forms accepted in the engine's `workflow_call` blocks and references first — `plan.yml:150`/`:229`, `apply.yml:165`/`:390`/`:499`, `drift.yml:131`/`:222`/`:316`, `apply-engine.yml:118`/`:142`, `testbed-e2e.yml:162`/`:172` — then the jsonnet declaration at `:625` moved from `secrets:` to `variables:` where otterdog would genuinely assert it instead of a dummy `'********'` row, then `template/README.md:101` and the four `template/.github/workflows/*.yml` callers plus `exo-pet`'s org-config caller cut over **at a pin bump**, and only then the shim retired). The statement is deliberately **fleet-wide**, covering the three sibling secrets — their Apps `commit-action-bot`, `vigos-devkit-upgrade` and `vig-os-release-app` each answer `200` to the same anonymous call (probed 2026-09-28) — so the next reader does not re-derive it per App; what stays per App is the paired private key, each its own rotation trigger. **Deliberately not done:** nothing moved — no workflow, `template/`, jsonnet or ADR edit, no secret value touched, and no variable migration issue filed, since the decision is to keep the current storage and a migration issue with no decision behind it would only re-open the one just made. The exposure is unchanged and was never a flip, which is why this is a `Changed` and not a `Security` entry.


- **The second public `vig-os` App, `vigos-devkit-upgrade`, now has a recorded visibility decision too** ([#271](https://github.com/vig-os/org-config/issues/271)): [#261](https://github.com/vig-os/org-config/issues/261) established that a `vig-os`-owned App's visibility is a posture to be decided and written down, and recorded one for the engine App — leaving this App in exactly the same position with a record **nowhere**: not in this repo, not in `vig-os/devkit`, not in an ADR, while `GET https://api.github.com/apps/vigos-devkit-upgrade` answers **200 to an anonymous caller** (re-probed 2026-09-28; three sibling `vig-os`-owned Apps answer `404`). The posture is **kept — public, *Any account*, decided 2026-09-28 and pending the same UI verification #261 prescribes**, stated as a hedge rather than a reading: `GET /apps/{app_slug}` carries no visibility field at all, so the only API evidence is that anonymous status code — an observation, not a documented mapping — and only the App's own settings page states the value. Public is not a preference here but a property of the live topology: the App is installed on `exo-pet` (installation `151387251`) as well as `vig-os`, and GitHub's private setting means installable only on the account that owns the App, so that installation could not exist under it — the one-App/N-installations model [ADR-0004](docs/adr/0004-auth-model-github-app.md) chose under *"One App, not four"*, exactly as for the engine App. The record lives where the App does: an `APP VISIBILITY DECISION` comment at `otterdog/vig-os/vig-os.jsonnet:115-181`, above the `DEVKIT_UPGRADE_APP_*` declarations and beside the `MAINTENANCE COUPLING` note already there, because that block is the App's only appearance in code anywhere; `docs/runbooks/github-app.md`'s **Visibility** section, which named this App as *"the one still lacking a decision of its own"*, now cross-references it instead. **Two differences from the engine App are stated rather than left to be inferred, and they are why the same posture is cheaper here.** The grant is **five** permissions — `contents`, `issues`, `pull_requests`, `workflows` write and `metadata` read, with no `organization_administration`, no secrets, no members, no administration — against the engine App's **seventeen**, so the world-readable grant table an unauthenticated caller gets (id, owner, creation date, Client ID, `events: []`, that table) reads *this org runs a write-capable upgrade bot* and discloses none of: the private key, the installation set, or which repositories the `selected_repositories` lists name — the Client ID being public regardless of how it is stored ([#270](https://github.com/vig-os/org-config/issues/270)). And the [#256](https://github.com/vig-os/org-config/issues/256) coupling **does not bind**: this App is named as a ruleset bypass actor or a status-check app **nowhere** in `otterdog/vig-os/vig-os.jsonnet` ([#81](https://github.com/vig-os/org-config/issues/81) proposed exactly such a bypass and was closed as superseded by [vig-os/devkit#1308](https://github.com/vig-os/devkit/issues/1308)), so unlike `commit-action-bot` / `vig-os-release-app` its visibility is load-bearing for nothing `apply` does, and making it private would strand no ruleset — only the `exo-pet` installation keeps it public. The one accepted cost with a standing control is the installation set: any account owner can install from the public page, `events: []` means there is no `installation` event to catch it, and `GET /app/installations` needs a JWT signed with `DEVKIT_UPGRADE_APP_PRIVATE_KEY`, which no workflow holds — so the sweep is written into the comment as a step of **that key's** rotation, the one moment it is free (a stray installation is inert while the key is sound; what it widens is the blast radius of a key compromise). **Deliberately not done:** no flip is proposed or performed, and no UI value is claimed as confirmed — reading *Where can this GitHub App be installed?* remains a human step, with #261's trap repeated (the Danger-zone button names the action, not the state); no `unmanaged-controls.toml` row, for #261's reason — the controls transport reads authenticated and can never observe the anonymous discriminator; no second **Visibility** section in a runbook whose own title scopes it to the org-management App; and no `devkit`-side creation runbook for this App, which is filed as [vig-os/devkit#1739](https://github.com/vig-os/devkit/issues/1739) rather than scoped into this change.
