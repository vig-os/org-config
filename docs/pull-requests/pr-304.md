# [PR 304](https://github.com/vig-os/org-config/pull/304) chore(config): add org-config Release protection and tier-A Dependabot updates

## Description

PR 8 of the #294 plan. It records two decisions taken on 2026-09-29:

- **A.** `org-config` gets the `Release protection` ruleset that
  [ADR-0008](docs/adr/0008-repository-protection-and-merge-policy.md) tier A
  prescribes for any repo whose train uses `release/*`. #302 left this pending.
- **B.** Dependabot security updates are turned on for the eight tier-A repos
  other than `devkit`, which already has them.
- **C.** ADR-0008 records the Dependabot policy under its repository settings,
  and lists `scitadel`'s `rust-ci.yml` gap as a known gap in the exceptions
  table.

## Changes Made

Two commits, in the same order as #300, #301 and #302:

1. `docs(adr)`: ADR-0008 changes in two places.
   - "Repository settings" gains a bullet: tier-A repos enable Dependabot
     security updates, while tier B, the exempt testbed and `qms` stay on the
     vendored default (`false`). It is stated as a policy, not as an exception.
   - The exceptions table gains a `scitadel` row for a known gap. Main gates

     jobs cannot gate a merge. Listing those job names as extra required checks
     was considered and rejected, because a rename would block every merge and
     it would put the repo's CI layout into the org config. The exit is
     vig-os/devkit#1761.

   - `org-config` gains
     `orgs.releaseProtection(checks=['15368:CI Summary'], bypass=['commit-action-bot'])`
     with a comment naming the writers. It is the same call as
     `devkit-smoke-test`'s.
   - Eight repo blocks declare `dependabot_security_updates_enabled: true`,
     placed alphabetically as on `devkit`.

   The commit also adds two CHANGELOG bullets, one under `### Changed` and one
   under `### Security`. `### Security` is where #298's secret-scanning entry
   sits. The App-actor ground-truth test goes from 19 to 20 bypass sites.

### Bypass verification (org-config, `origin/main` at `8d38f66`)

The App IDs come from `gh api orgs/vig-os/installations`:
`commit-action-bot` = 2433383 and `vig-os-release-app` = 2930017.
`org-config` has no repo or org secret named `token`, so the
`secrets.token || release_app_token` fallback in `release-core.yml` always
resolves to the Release App. That token is used only to check out the branch,
dispatch `sync-issues.yml` and poll it. It never writes to `release/*`.

**Writers of `release/*`**: only the Commit App (`COMMIT_APP_CLIENT_ID`), which
is the bypass.

- `prepare-release.yml`
  - Creates the branch with `POST git/refs` (L220) using `commit_app_token`.
  - Commits the freeze through commit-action (L296).
  - Fast-forwards the branch with `PATCH git/refs/heads/release/...` (L365).
  - On rollback, deletes the branch (L564) and re-commits (L595), still with
    `commit_app_token`.
  - The Release App token (L416) only lists and opens the draft release PR.
- `release-core.yml`
  - The finalize commit goes to `refs/heads/release/X.Y.Z` through
    commit-action with `commit_app_token` (L529-533).
  - So does the archive fold (L685-689).
- `release.yml`
  - The rollback revert commit plus `PATCH git/refs/heads/release/X.Y.Z`
    (L283-291) use `commit_app_token` (L203).
  - The Release App token here only files the failure issue.
- `sync-issues.yml`
  - Dispatched with `target-branch=sync/issue-mirror` (release-core L561-562),
    so it commits to `sync/issue-mirror`, not to `release/*`. It uses the
    Commit App in any case (L97, L197, L209).
  - Its release-branch contribution is the fold above.
- **Deleters of `release/*`**
  - `abandon-release.yml` (L202, Release App token from L142).
  - `prepare-release.yml`'s rollback (Commit App).
  - `promote-release.yml`'s `gh pr merge --merge` with the Release App, where
    `delete_branch_on_merge` removes the head branch.
  - The shape sets `allows_deletions: true`, so none of these needs a bypass.
- `promote-release.yml` never writes `release/*` otherwise. Its only
  `git push` targets are `refs/tags/*` (floating tags) and
  `refs/heads/sync/issue-mirror`.
- `devkit-upgrade.yml` writes `chore/devkit-*` only.

**The required check can be met**: `ci.yml` runs on `pull_request` into
`release/**` and `main` (L56-59), and its `summary` job is named `CI Summary`
(L596-597). PRs into `release/*` therefore report the check. Train writes come
from the Commit App, which bypasses it.

### Renovate overlap (informational, no change)

Each repo's `renovate.json` and its `.github/renovate-default.json` preset were
read via the Contents API on the default branch. **None sets `vulnerabilityAlerts`
or `osvVulnerabilityAlerts`.** The Renovate App is installed on all repos with
`vulnerability_alerts: read`, and Renovate's `vulnerabilityAlerts` handling is
on by default on GitHub, so it can also open a security PR from an alert. OSV
alerts are off by default.

| Repo | Renovate config | `vulnerabilityAlerts` / `osvVulnerabilityAlerts` | Renovate base | Dependabot security PR base (default branch) | Possible duplicate PR |
|---|---|---|---|---|---|
| `commit-action` | yes (`github-actions`, `pep621`, `npm`) | not set (Renovate default) | `dev` | `main` | yes, different base |
| `sync-issues-action` | yes (`github-actions`, `npm`) | not set | `dev` | `main` | yes, different base |
| `h5v` | yes (`github-actions`, `pep621`, `npm`) | not set | `main` | `main` | yes |
| `scitadel` | yes (`github-actions`, `pep621`, `uv`, `npm`; no `cargo`) | not set | `dev` | `main` | for the non-Cargo ecosystems; Cargo advisories go to Dependabot only |
| `qx` | **none** | n/a | n/a | `main` | no, Dependabot only |
| `tessera` | yes (`github-actions`, `pep621`, `npm`) + `.github/dependabot.yml` (version updates, `target-branch: dev`) | not set | `dev` | `dev` (its default) | yes. Dependabot already opens version PRs here |
| `devkit-smoke-test` | yes (`github-actions` only) | not set | `dev` | `main` | only for Actions advisories |
| `org-config` | yes (`github-actions`, `pep621`, `npm`, `custom.regex`) | not set | `main` | `main` | yes |

Where both bots can act, expect two PRs for the same advisory. Renovate's PR
targets its `baseBranchPatterns`, and Dependabot's targets the default branch.
If the noise matters, set `vulnerabilityAlerts.enabled: false` in the
repo-owned `renovate.json`. That is outside this PR.

Both checks read the **declared** config only — an actor that exists live but is not declared needs a live ruleset read and is not covered.
