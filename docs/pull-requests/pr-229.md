# [PR 229](https://github.com/vig-os/org-config/pull/229) chore(config): adopt otterdog 1.5.0 and correct the pin's Renovate claim

## What

Bumps the ADR-0005 otterdog pin **1.4.0 → 1.5.0** across all **five** hand-maintained
literals, and corrects the documentation that claimed Renovate did this for us.

| File | Change |
|---|---|
| `justfile.project:19` | `otterdog_version := "1.5.0"` (ADR-0005 SSoT) |
| `template/.github/workflows/plan.yml` | input literal → `"1.5.0"` |
| `template/.github/workflows/apply.yml` | input literal → `"1.5.0"` |
| `template/.github/workflows/drift.yml` | input literal → `"1.5.0"` |
| `template/.github/workflows/import.yml` | `default:` → `"1.5.0"` |

The 1.4.0 bump (`818e1f8`) moved only three of these and left `import.yml` on
`1.3.4` — a template consumer importing on one version and planning on another,
logged as #164 item 7. Hence the explicit five-item checklist on #225.

## Why

otterdog 1.5.0 ships upstream [#731](https://github.com/eclipse-csi/otterdog/pull/731),
which removes the `repo.private is False or org_settings.plan == "enterprise"` gate
from **both** ruleset read paths — the gate behind #107 and
[upstream #729](https://github.com/eclipse-csi/otterdog/issues/729). A private-repo
org below Enterprise can finally declare its repository rulesets instead of
hand-managing them.

The same commit also added `if ex.status in (403, 404): return []` to both ruleset
clients at `debug` level, and **that** is the half that makes this bump safe here —
it is not mentioned in #225. On Free, the two newly-attempted calls both fail
closed and are absorbed silently:

```console
$ gh api repos/vig-os/qms/rulesets
403 Upgrade to GitHub Pro or make this repository public to enable this feature.
$ gh api orgs/vig-os/rulesets
403 Upgrade to GitHub Team to enable this feature.
```

**Effect on `vig-os` is nil by design.** Every repo but `qms` is public and already
ruleset-complete; `qms` declares none. `otterdog 1.5.0 validate --local` output is
identical to 1.4.0. This ships capability for downstream Team/Enterprise orgs.

## Correction carried into the changelog

#225's Migration section says an `apply` dispatch **deletes** live branch
protection. It does not. `apply.yml:411` omits `--delete-resources` (rationale at
`apply.yml:91-93`), and `git diff v1.4.0..v1.5.0 -- otterdog/operations/apply.py`
is **empty** — at v1.5.0 the loop still reads:

```python
if patch.patch_type == LivePatchType.REMOVE and not self._delete_resources:
    progress.advance(task)
    continue
```

So the real downstream exposure is a **red plan** plus one `drift`+`critical`
issue per ruleset (none self-closing), not destroyed protection. The
declare-before-bump ordering stands — for noise, not for data loss. Full
evaluation, including three further corrected claims (#712 is webapp-only, #718
is backwards, #643/#642 are inert at the current defaults pin), is in the
[evaluation comment](https://github.com/vig-os/org-config/issues/225#issuecomment-5792407835).

## Deliberately NOT in this PR

`otterdog.json` keeps `otterdog-defaults@v0.13.1`. v0.14.x adds
`max_cache_size_gb`, which would enter otterdog's `included_keys` and call
`/orgs/{org}/actions/cache/storage-limit` — `402` on this org's Free plan —
writing a permanent `WARNING` into every `plan.txt` the drift layer parses.
The two pins are **not** in lockstep; recorded as an ADR-0005 correction so the
next bump does not move them by reflex.

## Documentation truth

- **ADR-0005 `## Corrections`** (previously "None to date") gains two dated
  entries. Its Consequences claimed *"Renovate owns the pin … without hand
  edits"*; `justfile.project:18` repeated it; the three `template/` callers told
  operators *"Renovate can bump this alongside the engine SHA pin"*. None was
  ever true — `renovate.json` enables only `github-actions`/`pep621`/`npm`, the
  pin is a bare Just variable no manager matches, and there is no
  `customManagers` regex here or in `template/renovate.json`. Four places
  advertised automation that does not exist, which is how the 1.4.0 bump came to
  miss a literal.
- **README "Known limitations"** is reconciled with the new pin: the
  private-repo ruleset *read* gate bullet (#191) is retired as fixed and replaced
  by the two that genuinely remain — org-level rulesets still erroring below
  Enterprise, since #731 left the `validate()` gate in place
  ([upstream #763](https://github.com/eclipse-csi/otterdog/issues/763)), and
  #209's two-dispatch repository creation, whose `_update_code_scanning_config`
  is byte-identical at v1.5.0
  ([upstream #738](https://github.com/eclipse-csi/otterdog/issues/738)).

remain open and are now documented as such in the README.

```
  Plan: 0 to add, 0 to change, 0 to delete.
```

All zeros against live `vig-os` under the new pin — so the ungated ruleset reads
introduce no diff here, the two Free-plan `403`s are absorbed as documented, and
the `#643`/`#642` fields stay unmanaged at `otterdog-defaults` v0.13.1 as
predicted. Plus all 11 PR checks green.

### Why this had to be dispatched by hand — a gap worth its own issue

`plan.yml`'s `pull_request` trigger filters on `otterdog.json`, `otterdog/**` and
`.github/workflows/plan.yml` (`plan.yml:60-63`). **`justfile.project` is not in
that list** — yet it is the ADR-0005 single source of truth for *which otterdog
binary the plan runs*. So a pure pin bump changes the engine the plan executes
and the plan check does not fire.

This went unnoticed because the previous pin bump (PR #145) also edited
`vig-os.jsonnet`, which lives under `otterdog/**` and pulled the check in
incidentally. This PR touches no config path, so nothing triggered.

Left out of this PR deliberately — changing a workflow trigger is a behaviour
change to the engine and belongs to its own issue under the house single-issue
scope rule, not as a drive-by on a pin bump. Filed as #230.
