# [PR 117](https://github.com/vig-os/org-config/pull/117) chore(config): harden devkit rulesets with tag protection, a CodeQL gate, and no code-owner review

Closes #115.

Three approved changes to the `devkit` block of `otterdog/vig-os/vig-os.jsonnet` (findings D2, D5, D8 of the devkit settings review), plus the outcome of D10.

## 1. `Tag protection` ruleset added (D2)

`devkit` publishes the release tags every consumer pins and declared no `target: 'tag'` ruleset, so anyone with write access could create, move, or delete one out of band. The new block mirrors `commit-action`'s verbatim.

One always-bypass actor is enough because the tag write path is a single choke point:

- `release.yml:982` `git tag -a` + `:1000` `git push origin "$PUBLISH_VERSION"` — the repo's **only** `git tag` — on a checkout token minted from `RELEASE_APP_CLIENT_ID`/`RELEASE_APP_PRIVATE_KEY`, i.e. `vig-os-release-app` (`app_id` 2930017, the same integration id already bypassing `commit-action`'s ruleset);
- `promote-release.yml` deletes leftover RC tags with the same App;
- `devkit` uses bare `X.Y.Z` tags (no `DEVKIT_TAG_PREFIX`) and declares no floating tags, so nothing ever force-moves a published tag.

## 2. CodeQL required on `main` (D5)

`Main protection` gated only on `15368:Test Summary`, so a PR with a red CodeQL leg merged. Verified the exact contexts against `main@ffa7a5f`:

| check name | app | note |
|---|---|---|
| `CodeQL Analysis (actions)` | `github-actions` (15368) | matrix leg |
| `CodeQL Analysis (python)` | `github-actions` (15368) | matrix leg |
| `CodeQL` | `github-advanced-security` | code-scanning result check, not a workflow job |

**Two contexts, not one** — `codeql.yml`'s `analyze` job is a `language: ['python', 'actions']` matrix, so each leg reports under its own matrix-suffixed name. Both are declared; the `github-advanced-security` check is deliberately not (different app, and it is a results check rather than a job).

No pending-forever risk: `devkit` is public, so `codeql.yml`'s `if: ${{ !github.event.repository.private }}` guard never skips the job, and its `pull_request` trigger carries no `paths:` filter, so both legs report on every PR to `main`.

`Dev protection` and `Release protection` are deliberately unchanged.

## 3. `requires_code_owner_review: false` on Main and Release protection (D8)

`.github/CODEOWNERS` names exactly one owner (`@c-vigo`) on every entry, and that same account authors the PRs. GitHub will not accept an author's own review, so the code-owner gate on a CODEOWNERS-covered PR was structurally unsatisfiable and its only possible outcome was an `#OrganizationAdmin` bypass. A control that produces nothing but bypasses is worse than no control: it normalizes the bypass and pollutes the audit trail. [vig-os/devkit#1219](https://github.com/vig-os/devkit/issues/1219) already reduced CODEOWNERS to the single-maintainer reality; this is the ruleset half.

The gates that actually bind are untouched: 1 approving review on `main`, review-thread resolution, required status checks, and the bypass-free `Signed commits` ruleset.

Declared as an explicit `false` with an inline rationale rather than by deleting the line (the vendored default is already `false`), so the config states the decision instead of leaving it to a default.

## 4. D10 — secret-scanning extras: not changed

`secret_scanning_non_provider_patterns` and `secret_scanning_validity_checks` read `disabled` on `devkit` and **cannot be turned on**. otterdog 1.3.4 models neither, and the out-of-band route is also a dead end: `gh api -X PATCH repos/vig-os/devkit` returns `200 OK` and changes nothing, because `devkit` is attached to the **enforced** org code-security configuration `237480`, which already declares both `enabled`. Full evidence in [#115's comment](https://github.com/vig-os/org-config/issues/115#issuecomment-5218553609). Nothing was changed; recorded as an unassertable control in #116.

## Apply sequencing — read before merging

otterdog 1.3.4 cannot PATCH an existing repo ruleset whose `required_status_checks` use the numeric `15368:<context>` form (#69, upstream eclipse-csi/otterdog#695). Changes 2 and 3 are ruleset **modifications**, so they were reconciled live with `gh api -X PUT` before this merges; change 1 is a ruleset **add** with no status checks, which `otterdog apply` creates normally.

The plan check on this PR should therefore show **1 to add, 0 to change, 0 to delete** for `devkit`. If it shows a ruleset change, the live reconciliation did not land and the apply will fail — do not merge.

## Follow-up

#116 — assert unmanaged live controls the otterdog schema cannot model (`sha_pinning_required`, fork-PR approval policy, the secret-scanning extras above).
