# Release 1.4.0

This PR prepares release 1.4.0 for merge to main.

## [1.4.0] - TBD

### Added

- **Unmanaged-control rows can address JSON list elements, so ruleset internals are assertable** ([#205](https://github.com/vig-os/org-config/issues/205)): `select_path()` walked objects only, which made anything GitHub returns *inside a list* unassertable — and the most consequential control is exactly that shape, since a repository ruleset's `rules` are an array keyed by `type` and the required status checks inside one of them are an array of objects. Two new path forms close it, both stdlib-only and still deliberately not jq ([ADR-0005](docs/adr/0005-repo-tooling.md)): `rules[type=required_status_checks]` selects the **one** element whose field equals the literal, and `required_status_checks[].context` projects a field out of **every** element; an empty key applies either operator to the response itself, for the endpoints that answer with a list at the root. A companion row field `compare = "set"` compares the projected result with a TOML array **order- and duplicate-insensitively**, because GitHub returns a check list in no guaranteed order and an exact comparison would report drift every time the UI reshuffled it. Every ambiguity **degrades instead of guessing**, which is the whole point: zero or several matches, a projection over a non-list or one element that cannot satisfy it, a malformed path, a live value that cannot become a set (a row that forgot its `[].context`, or a field that stopped being a list) all resolve to `UNRESOLVED`, leaving the row's own issue exactly as it was — two rulesets can contribute a rule of the same type to one branch, and picking either would fabricate or hide a security finding, while a partial projection would compare as a shorter set and read as drift or, worse, as clean. Match literals compare against **strings only**, since coercion would make `[id=1]` match a live `true`, the same conflation `_equal` already refuses; declared values are validated at load, so an unknown `compare` mode, an unparsable path, or a set row whose `expect`/`tolerated` is not a list of plain values **drops the row** under the standing rule that a malformed row must never manufacture a finding. Drift bodies gain `missing:`/`unexpected:` lines, since a dropped required check and an unexpected extra one are different incidents. The engine repo itself deliberately gains **no new row**: every vig-os repo but one is public, where Otterdog models rulesets and the plan already diffs them, and the exception (`qms`) is private on a Free-plan org where both ruleset endpoints answer `403 Upgrade to GitHub Pro`. This is capability for **downstream** orgs on Team/Enterprise, whose private repos Otterdog cannot read ([#107](https://github.com/vig-os/org-config/issues/107), [eclipse-csi/otterdog#729](https://github.com/eclipse-csi/otterdog/issues/729)) while REST can — `exo-pet/org-config` can now convert its four `kind = "unassertable"` `main-protection-*` rows into real assertions. Both the shipped table and the `template/` starter document the shape, which reads `/repos/{org}/{repo}/rules/branches/{branch}` rather than `/rulesets/{id}`: no ruleset id to hard-code, readable with repo read access, and it asserts what actually protects the branch whichever ruleset carries it. No behaviour change for any existing row — `--controls-report` on live `vig-os` is unchanged at 13 `OK` / 3 `TOLERATED`.

### Changed

- **ADR-0007 stops describing the pre-#63 `dev` trunk** ([#237](https://github.com/vig-os/org-config/issues/237)): four statements still narrated the old branch topology — apply "runs only from trunk (`dev`)" in the **binding credential rules**, config "applies from `dev` on merge" while the engine "releases to `main` + version tags" in the split cadence, "Config from `dev`; engine to tags" as Axis B's chosen option, and "not a silent `dev` merge" in the Consequences — all stale since [#63](https://github.com/vig-os/org-config/issues/63) retired `dev` and made `main` the single trunk and applied-state branch (`plan.yml` and `apply-engine.yml` have said so, citing #63, the whole time). The credential rule is the reference that mattered: a reader auditing where the write token can run was pointed at a branch that no longer exists. The decisions themselves are untouched — apply stays trunk-only and environment-gated, and the split cadence (config-on-merge vs engine-by-tag) is intact; only the branch names moved, with the engine releasing as version tags cut by the devkit release train rather than by promotion to a separate branch. Recorded as a dated entry in ADR-0007's `## Corrections` block alongside [#235](https://github.com/vig-os/org-config/issues/235)'s, found while [#236](https://github.com/vig-os/org-config/issues/236) amended the same document, and kept out of both per the single-issue scope rule. Documentation only; no workflow, config, or behaviour change.

- **Downstream callers inherit the otterdog pin from the engine ref they already pin, instead of hand-mirroring a literal nothing bumped** ([#228](https://github.com/vig-os/org-config/issues/228)): [#56](https://github.com/vig-os/org-config/issues/56) made `otterdog_version` an optional `workflow_call` input defaulting to `''` and put the burden on the consumer — *"`template/` callers pass `otterdog_version` explicitly (lockstep comment; Renovate can bump both)"* — but Renovate never bumped both and structurally could not: `template/renovate.json` enables exactly one manager, `github-actions`, which extracts `uses:` refs and container images, and a bare `with:` input string is a dependency to no enabled manager — no datasource, no annotation, nothing on the dependency dashboard. "Lockstep" was a convention with no mechanism behind it, and it failed silently and one-directionally: Renovate advanced a consumer's engine ref on schedule while its otterdog pin stayed wherever onboarding left it — no failed run, no drift issue, the divergence visible only to someone who thought to diff two files in two repositories, and every org onboarded from `template/` starting from the same stale literal. The three reusable workflows now default the input to the engine's own pin, the `template/` plan / apply / drift callers drop the input and the comment that advertised the automation, and a consumer that wants a different otterdog still passes one — a non-empty default removes no override. The duplication this buys is **guarded rather than trusted**: the literal count is unchanged at five, but all five now live in this repo — `justfile.project` (the [ADR-0005](docs/adr/0005-repo-tooling.md) single source of truth), the three `workflow_call` defaults, and `template/.github/workflows/import.yml`, a standalone `workflow_dispatch` bootstrap rather than a caller, which therefore keeps its own literal and is the very one the 1.4.0 bump missed ([#164](https://github.com/vig-os/org-config/issues/164) item 7) — and a new `tests/test_otterdog_pin.py` asserts each mirror equals the justfile pin, so a bump that forgets one fails here, in this repo's CI, rather than silently in someone else's org. Downstream mirrors go to **zero**. **Corrected against the issue as filed**, and the correction is load-bearing: a `workflow_call` default is *not* "visible only to callers" in another repo — `apply-engine.yml` reaches `plan.yml` and `apply.yml` through `workflow_call` exactly like a downstream, so leaving its `with:` omitted would have made the engine's own preview and apply resolve the pin from a workflow literal instead of `justfile.project`, quietly inverting ADR-0005 for the runs that matter most here; both jobs now pass an explicit `otterdog_version: ''`, which keeps the justfile the effective resolver for every event this repo triggers itself and leaves the `elif` branch precisely as ADR-0005 describes it. The hard-error branch ("no input and no `justfile.project` in the checkout") becomes unreachable unless a caller passes a deliberately empty string — [#56](https://github.com/vig-os/org-config/issues/56)'s actual bug is more fixed, not less — and its message now says so. **Migration, and the order matters:** an existing consumer's `otterdog_version` literal keeps working and simply wins over the new default, so nothing breaks on a pin bump; deleting that literal while still pinned to a pre-#228 engine, however, sends an empty input to a workflow whose `justfile.project` fallback does not exist in the consumer's checkout, and every run fails at "Resolve otterdog version pin". **Bump the engine pin first, then delete the literal** — `template/README.md` now says so, beside the consequence worth stating plainly: the engine ref selects the otterdog release as well as the workflow code, so an engine bump can change what a plan *sees* (see [#225](https://github.com/vig-os/org-config/issues/225), where 1.5.0 makes previously-unreadable private-repo rulesets visible and can turn a plan into proposed deletions), with the caller's own `plan` run on the Renovate PR as the backstop and the release note as what makes the diff expected rather than alarming. Additive contract change — **semver:minor**: no existing caller's behaviour changes and no consumer is required to act.

- **The `Plan` check is advisory by decision, and ADR-0007 now says so** ([#236](https://github.com/vig-os/org-config/issues/236)): `Main protection` requires exactly one context, `15368:CI Summary`, and `Plan` was never one — a fact recorded in passing by [#230](https://github.com/vig-os/org-config/issues/230) but never actually decided. It is now decided, with the trade in [ADR-0007](docs/adr/0007-ci-and-testing-strategy.md)'s alternatives table as a new Axis D. The reasoning corrects the framing the question is usually raised with: `otterdog plan` exits **0** on a non-empty diff, so a *red* plan is invalid config, broken auth or a harness failure — never drift — and the config-validity half of that is already behind the required check, since `otterdog validate --local` runs offline as an L0 pre-commit hook inside the `Lint & Format` job. Requiring `Plan` would therefore gate merges on App-credential health, a property of the runner rather than of the PR, while the diff it is actually reached for is explicitly not a failure under [ADR-0002](docs/adr/0002-drift-semantics.md). The enforcing control stays where mutation happens: the `production` environment reviewer pauses every apply with the exact tree's plan in the same run's summary ([#105](https://github.com/vig-os/org-config/issues/105), [#176](https://github.com/vig-os/org-config/issues/176)), guarded against a stale tree by the tip-of-branch check added after [#99](https://github.com/vig-os/org-config/issues/99). The mechanically-possible alternative is recorded rather than hand-waved: a workflow-level `paths:` filter leaves a required check `Pending` forever, but a job skipped by a **conditional** reports *Success*, so a broad trigger plus a job-level gate and a static summary job would make the check requirable for roughly ten seconds and no live API call on an unrelated PR. It is rejected for now on cost of meaning, not cost of compute — the green would mean *clean*, *skipped* and *fork PR* alike, it needs the templated job name (`Plan committed config against live ${{ ... }}`) made static plus a new ruleset context, and it propagates into `template/` and every consumer org. Its revisit triggers are written down: an unintended diff the `production` approval misses, a second maintainer, or GitHub shipping path-conditional required checks. Empirically the gate has never been needed — `plan.yml` has run 57 times and never once concluded `failure`. Documentation only; no workflow, config or ruleset change — `plan.yml` and `Main protection` are byte-identical.

- **ADR-0007's "L2 runs on every same-repo PR" is corrected — the live plan has been path-filtered since day one** ([#235](https://github.com/vig-os/org-config/issues/235)): the test pyramid described its L2 layer as a read-only `otterdog plan` against `vig-os` "on every same-repo PR", and `plan.yml` has never worked that way — the `pull_request` `paths:` filter was in the workflow's first commit (`f101cc6`), landed the same day the ADR was accepted, so L2 fires only on a same-repo PR into `main` touching `otterdog.json`, `otterdog/**`, `.github/workflows/plan.yml` or, since [#230](https://github.com/vig-os/org-config/issues/230), `justfile.project`. The claim is load-bearing rather than incidental: the pyramid's shape *is* this ADR's decision, and a reader sizing the L2/L3 gap — or waving a new check off to L3 because L2 "already covers every PR" — was reading something untrue of the implementation. The bullet now states the real trigger set and says why it is narrow: a plan is a live-API round trip against the org on a full App installation token ([ADR-0004](docs/adr/0004-auth-model-github-app.md) Corrections), so running one on a README typo diffs the same committed config against the same live org for no new signal — the filter is why L2 is cheap, not an oversight. It is still a real coverage boundary, and #230 is what a wrong one costs: [#229](https://github.com/vig-os/org-config/pull/229)'s pure pin bump touched no config path, so the empty plan that was its acceptance evidence had to be produced by hand. Recorded as a dated entry in ADR-0007's `## Corrections` block (previously "None yet") rather than silently rewritten, matching [#225](https://github.com/vig-os/org-config/issues/225)'s handling of ADR-0005. Explicitly unaffected: the binding credential rule — plan runs **only** on same-repo PRs — is an upper bound on who may reach the App token, never a promise that every such PR is planned, and L3's "never per-PR" stands; `README.md` already described L2 as "`plan` on every config PR" and is unchanged. A supersession trigger is added for [#236](https://github.com/vig-os/org-config/issues/236), whose skip-job-shim option would drop the filter and retire this correction. Documentation only; no engine, config, or workflow behaviour change.

- **`tessera`'s `main` protection requires a check `main` can actually report** ([#226](https://github.com/vig-os/org-config/issues/226)): the rule demanded `any:nix flake check`, a context no workflow on `main` produces — `main`'s `ci.yml` defines exactly two PR jobs, `Dependency Review` and `CI Summary`, and its own header says the real gate *"lives on the development branch"*. The required check could therefore never report, so every `main` PR merged by admin override (`enforce_admins` is off, which is the only reason `main` was not simply frozen) — the same always-bypassed-control pathology as [#195](https://github.com/vig-os/org-config/issues/195), #115 and #167, flagged in passing by the merger of [tessera#383](https://github.com/vig-os/tessera/pull/383) and never followed up. It now requires `CI Summary`, `main`'s own aggregating job (`needs: [dependency-review]`, `if: always()`, exits 1 when dependency-review failed), so one context covers the lane; `requires_strict_status_checks` stays on, and with a context that can report, "up to date with base" finally means something. Stated plainly rather than oversold: `main` runs one real job, so the gate means *no new high-severity dependency vulnerabilities* — thin, but satisfiable and honest, and it ends the routine bypass. The deeper gate follows at the first alpha cut, when `main` inherits the real CI. The context is deliberately **un-prefixed**, binding it to the `github-actions` app exactly as the neighbouring `dev` rule does: the numeric `15368:` form used everywhere else in this config is **ruleset** syntax, and `tessera` is the only repo here still on classic `branch_protection_rules`, where otterdog resolves the prefix as an app slug via `GET /apps/{slug}` with no numeric branch (re-verified against the newly pinned 1.5.0 `models/branch_protection_rule.py`, unchanged from 1.4.0) — a `15368:` prefix would have 404'd at **apply**, past the `production` approval, while `plan` stayed green. Unlike [#215](https://github.com/vig-os/org-config/issues/215), this is a real live change: the plan shows one changed field and it takes effect only once applied.

- **ADR-0005's "Renovate owns the pin" is corrected — the otterdog pin has always been a hand edit** ([#225](https://github.com/vig-os/org-config/issues/225)): the ADR's Consequences promised the exact `uvx otterdog` version was "bumped by Renovate, keeping the tool current without hand edits", `justfile.project` repeated it, and the three `template/` callers told downstream operators that "Renovate can bump this alongside the engine SHA pin". None of it was ever true: `renovate.json` sets `enabledManagers` to `["github-actions", "pep621", "npm"]`, the pin is a bare Just variable no manager matches, and neither this repo nor `template/renovate.json` defines a `customManagers` regex — so four places advertised automation that does not exist, which is how the 1.4.0 bump came to miss a literal ([#164](https://github.com/vig-os/org-config/issues/164) item 7). Recorded as a dated entry in ADR-0005's `## Corrections` block (previously "None to date") rather than silently rewritten, with a second entry recording that the otterdog pin and the `otterdog-defaults` `base_template` pin are **not** in lockstep. The consequence now reads as what it is — a deliberate authored bump, which suits a pin that doubles as the L1 plan-fixture format anchor (ADR-0007), since the bump PR is where plan output is re-checked against live. The README's "Known limitations" section is reconciled with the 1.5.0 pin in the same pass: the private-repo ruleset *read* gate bullet ([#191](https://github.com/vig-os/org-config/issues/191)) is retired as fixed and replaced by the two limitations that genuinely remain — org-level rulesets erroring below Enterprise ([upstream #763](https://github.com/eclipse-csi/otterdog/issues/763)) and the two-dispatch repository creation ([#209](https://github.com/vig-os/org-config/issues/209)). Documentation and template comments only; no engine, config, or workflow behaviour change.

- **`tessera` declares `dev` as its default branch, adopting a documented upstream decision** ([#215](https://github.com/vig-os/org-config/issues/215)): the repo block carried no `default_branch`, so it inherited the vendored `main` and the daily drift run had reported `dev -> main` every day since 2026-09-08. The live value is neither an accident nor an incident — it is documented in the repo it governs ([tessera#383](https://github.com/vig-os/tessera/pull/383), *"point the default branch to dev until the first alpha"*): `main` is release-only with no release cut yet (`0.1.0-alpha.1` is held), while `dev` carries all five open PRs, every Dependabot branch, and 516 commits `main` does not have. Reverting — the other half of the [ADR-0002](docs/adr/0002-drift-semantics.md) choice the issue exists to force — would have pointed every fresh clone and default PR base at a branch untouched since 2026-06-30, and would have silently undone a maintainer decision, which is precisely what issue-only drift reporting is designed to prevent. Adopted in config rather than silenced in `drift-allowlist.toml`: `default_branch` is a first-class Otterdog field, and the allow-list is for divergence the schema *cannot* express. `tessera` is the only vig-os repo not on `main` (the other nine all are), so the deviation is declared explicitly and carries its expiry — *until the first alpha* — as a comment, making the eventual flip back a one-line change rather than a re-investigation. Config-only: nothing live is touched, the plan for that repo simply goes empty and #215 closes itself on the next scheduled drift run.

### Fixed

- **A pure otterdog pin bump no longer merges without a plan run** ([#230](https://github.com/vig-os/org-config/issues/230)): `plan.yml`'s `pull_request` `paths:` filter listed `otterdog.json`, `otterdog/**` and the workflow itself, but not `justfile.project` — which holds `otterdog_version`, the [ADR-0005](docs/adr/0005-repo-tooling.md) single source of truth that the workflow's own "Resolve otterdog version pin" step greps at run time. That file selects the **binary that produces the diff**, which makes it the highest-leverage input to plan behaviour in the repo, and [ADR-0007](docs/adr/0007-ci-and-testing-strategy.md)'s entire argument for pinning is that a version change can move that behaviour. The gap stayed invisible because the previous bump ([#145](https://github.com/vig-os/org-config/issues/145), 1.3.4 -> 1.4.0) also edited `otterdog/vig-os/vig-os.jsonnet` and was pulled in by `otterdog/**`; [#225](https://github.com/vig-os/org-config/issues/225)'s 1.5.0 bump ([PR #229](https://github.com/vig-os/org-config/pull/229)) was a pure pin-plus-documentation change touching no config path, so **no plan ran at all** — and an empty plan is precisely that issue's acceptance evidence, which had to be produced by hand ([`workflow_dispatch` run 35844030809](https://github.com/vig-os/org-config/actions/runs/35844030809), `0 to add, 0 to change, 0 to delete`). Stated precisely, because the distinction is load-bearing: what a bump was losing is the **automatic plan evidence on the PR**, not a blocking gate. `Plan` is not a required status check — the `Main protection` ruleset requires exactly one context, `CI Summary` — and a path-filtered workflow *cannot* be required, since a required check that never runs leaves the PR pending forever. Scope-wise the filter stays tight and the trade is accepted explicitly: `justfile.project` also carries unrelated recipes, so some plan runs will now diff nothing, but the file has moved **8 times** in this repo's life — no Renovate manager matches a bare Just variable ([#225](https://github.com/vig-os/org-config/issues/225)) and devkit upgrades preserve it, so it only ever moves on a hand edit — which puts a handful of read-only runs against a pin bump silently losing its evidence. `apply-engine.yml` deliberately keeps omitting the same file, and the asymmetry is now recorded inline where a future reader will trip over it: plan must **prove** before merge that the newly pinned engine produces no diff, while apply must not **mutate** the live org off an engine-version edit carrying no config delta — if a pin bump ever does need applying, that is a human `workflow_dispatch` taken after reading the plan. `template/` needs no equivalent line and now says so: downstream the pin is the `otterdog_version:` input literal inside the caller workflow, already matched by `.github/workflows/plan.yml`, and the skeleton ships no `justfile.project` at all ([#56](https://github.com/vig-os/org-config/issues/56)). Workflow trigger and comments only — no engine, config, or plan-execution behaviour change.

- **Otterdog pin bumped 1.4.0 -> 1.5.0, ungating repository-ruleset reads on private repos below Enterprise** ([#107](https://github.com/vig-os/org-config/issues/107), [#225](https://github.com/vig-os/org-config/issues/225)): otterdog read live repo rulesets only when a repository was public or the org was on `enterprise`, so a private downstream org on Team could not declare a repo ruleset at all — the declaration diffed against an empty live set, giving a permanent phantom `add` on every plan and a duplicate `POST` on apply, which is why those rulesets were hand-managed with the declaration held out of the jsonnet. Upstream [#731](https://github.com/eclipse-csi/otterdog/pull/731) removed the gate from both ruleset read paths and, in the same commit and just as load-bearing, gave both clients `if ex.status in (403, 404): return []` at `debug` level — which is what makes the bump safe on a **Free**-plan org, where the newly-attempted `/repos/{org}/{repo}/rulesets` and `/orgs/{org}/rulesets` calls answer `403` and are absorbed silently rather than aborting the plan or adding lines to the `plan.txt` the drift layer parses. Effect here is deliberately nil: every `vig-os` repo but `qms` is public and already ruleset-complete, `qms` declares none, and `otterdog 1.5.0 validate --local` output is identical to 1.4.0 — so this ships the capability for **downstream** Team/Enterprise orgs rather than changing this org's plan. **Migration, and it is not safe to adopt blind:** before v1.5.0 a private repo's live rulesets were never read, so config-declares-none matched live-holds-none and the plan was silent; at v1.5.0 the live model holds them while the config still declares none, so the plan flips from silence to proposing one **deletion per ruleset** — a red plan, and one `drift`+`critical` issue per ruleset on the next scheduled run, none of which self-close. **Declare the rulesets in the jsonnet first, then bump the pin, in one change**, with an empty plan as the acceptance evidence. Deliberately corrected against the issue that requested this: an `apply` dispatch does **not** delete that protection — `apply.yml` omits `--delete-resources` and `operations/apply.py` is byte-identical across the two releases, still skipping every `REMOVE` patch without the flag — so the exposure is plan noise, not lost branch protection. Still blocked upstream and unchanged by this bump: **organization**-level rulesets, which `GitHubOrganization.validate()` still rejects with an `ERROR` below `enterprise` ([upstream #763](https://github.com/eclipse-csi/otterdog/issues/763)), and [#209](https://github.com/vig-os/org-config/issues/209)'s two-dispatch repository creation, whose `_update_code_scanning_config` is byte-identical at v1.5.0 ([upstream #738](https://github.com/eclipse-csi/otterdog/issues/738)). The pin moves across **five** hand-maintained literals — `justfile.project` (the ADR-0005 single source of truth) plus `template/.github/workflows/{plan,apply,drift,import}.yml` — because nothing propagates it ([#56](https://github.com/vig-os/org-config/issues/56)); the 1.4.0 bump missed `import.yml` and left a template consumer importing on one version and planning on another ([#164](https://github.com/vig-os/org-config/issues/164) item 7). The `otterdog.json` `otterdog-defaults` pin **stays at v0.13.1** by decision: v0.14.x adds `max_cache_size_gb`, which would enter otterdog's `included_keys` and call `/orgs/{org}/actions/cache/storage-limit` — `402` on a Free plan — writing a permanent `WARNING` into every plan. The two pins are not in lockstep and must not be moved by reflex.
