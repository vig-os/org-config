# [PR 328](https://github.com/vig-os/org-config/pull/328) chore(config): declare vigil config-first as a tier-A gitflow repo

## Description

Declares the new public `vig-os/vigil` **config-first**: `apply` creates it, so it never sits as undeclared inventory the way stepv did (#317). vigil (*Verifiable Integrity-Guarded Instrumentation & Logging*) is the opinionated OpenTelemetry logging, metrics and tracing crate, plus an opt-in hash-chained audit trail, for vig-os Rust projects. Design rationale is in #327.

The six secrets are dummy-valued, so `apply` will **not** grant `vigil` live. Run the six `gh api -X PUT` grants that `plan`'s *Declared org-secret readers* section prints, or the devkit workflows will read empty credentials.

## Changelog Entry

### Added
- **`vigil` is declared as a tier-A repository, config-first** ([#327](https://github.com/vig-os/org-config/issues/327)): the new public `vig-os/vigil` (*Verifiable Integrity-Guarded Instrumentation & Logging*, the opinionated OpenTelemetry logging/metrics/tracing and audit-trail crate for vig-os Rust projects; devkit 1.18.0 gitflow scaffold) is created by `apply` rather than `gh repo create`, so it never appears as undeclared inventory. It gets the same shapes as `revkit` under [ADR-0008](docs/adr/0008-repository-protection-and-merge-policy.md): `Dev`/`Main`/`Release protection` gated on `CI Summary` with `commit-action-bot` as the Dev/Release bypass, `Signed commits`, and `Tag protection` bypassed only by `vig-os-release-app`; plus `allow_update_branch` (#188) and `type: ['tools']`. It joins only the six client-ID-form App org secrets (`COMMIT_APP_*`, `RELEASE_APP_*`, `DEVKIT_UPGRADE_APP_*` client ID and private key), not the numeric `*_APP_ID` lists (#112, #313). Those six are dummy-valued, so `apply` does not grant them live ([#318](https://github.com/vig-os/org-config/issues/318)): the grants are run by hand from `plan`'s *Declared org-secret readers* section. The `crates-io` environment and `CARGO_REGISTRY_TOKEN` come with the first release.

#### Declared App slugs

Two checks otterdog makes and `plan` does not, run with the token this run minted: `apply` writes every App-shaped actor by resolving its slug through `GET /apps/{slug}`, and otterdog's read path maps a live App actor back to a slug only through `GET /orgs/{org}/installations`. Neither is exercised by the plan above, so config that fails either is green on review ([#259](https://github.com/vig-os/org-config/issues/259)). Both checks read the **declared** config only — an actor that exists live but is not declared needs a live ruleset read and is not covered.

All 2 declared App slugs resolved, and every one whose read path needs it is installed on `vig-os`. Nothing here blocks `apply`.


#### Declared org-secret readers

Who may read each `selected` org secret, committed config vs live, read with the token this run minted. `plan` cannot show this: otterdog skips any org secret whose committed value is a `'********'` dummy for live patching, so `apply` **never writes the reader list** of such a secret — a repository added to it is green here and never granted, and its workflows read the secret as an empty string with no error ([#318](https://github.com/vig-os/org-config/issues/318)). The same comparison runs daily as the drift layer's `org-secret-repositories` check.

**Declared, not granted live.** These repositories are in the committed `selected_repositories` but cannot read the secret. For a dummy-valued secret `apply` will **not** grant them — not on this merge, not on any later one — so an org owner runs the grant by hand. A repository this change also declares does not exist until `apply` creates it: grant it after that apply.
