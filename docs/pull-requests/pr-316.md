# [PR 316](https://github.com/vig-os/org-config/pull/316) chore(config): declare stepv and grant it the App org secrets

## Description

Brings `vig-os/stepv` under org-config management, declaration and
credentials together (they are one file and one apply).

### The declaration

A devkit 1.17.0 **trunk** scaffold (`.vig-os` `DEVKIT_WORKFLOW=trunk`),
so it takes the same ruleset shapes as `h5v` — the only other trunk repo
— and deliberately carries **no** `Dev protection`: there is no `dev`
branch to protect. Releases fork `release/X.Y.Z` from `main` and merge
back through the release PR. `type: ['tools']` on the required org custom
property, and `allow_update_branch` so the "Update branch" button can
satisfy Main protection's `strict` requirement without a manual rebase
(#188).

One honest note, recorded in the declaration itself: this repo was
created with `gh repo create` rather than by `otterdog apply`, which is
the bypass the org-settings comment at the top of this file warns about.
Nothing was lost — apply never deletes what the config omits — but stepv
sat as an inventory drift finding (#21) until this landed.

Unlike `h5v` (whose vig-os/h5v#9 is still open), stepv ships
`DEVKIT_SYNC_TARGET=sync/issue-mirror` from its first scaffold, so its
nightly `sync-issues.yml` never attempts the direct `main` push that
`Main protection` would refuse (vig-os/devkit#1227).

### The secrets

stepv joins the six **client-ID-form** lists only —
`COMMIT_APP_CLIENT_ID`, `DEVKIT_UPGRADE_APP_CLIENT_ID`,
`RELEASE_APP_CLIENT_ID` and the three matching `*_PRIVATE_KEY` unions.
Like `tessera` it is on that form FROM DAY ONE, so it is deliberately
absent from the numeric `*_APP_ID` lists and leaves nothing for #112 to
retire. Without these its scaffolded workflows fail with an empty
credential and no error.

### Not yet declared, on purpose

The `crates-io` environment and `CARGO_REGISTRY_TOKEN` that `scitadel`
carries. stepv's first crates.io publish is step S6 of its own plan, and
declaring a repo secret whose live value does not exist is how an apply
goes wrong. Both land in the same PR as the first release.

#### Declared App slugs

Two checks otterdog makes and `plan` does not, run with the token this run minted: `apply` writes every App-shaped actor by resolving its slug through `GET /apps/{slug}`, and otterdog's read path maps a live App actor back to a slug only through `GET /orgs/{org}/installations`. Neither is exercised by the plan above, so config that fails either is green on review ([#259](https://github.com/vig-os/org-config/issues/259)). Both checks read the **declared** config only — an actor that exists live but is not declared needs a live ruleset read and is not covered.

All 2 declared App slugs resolved, and every one whose read path needs it is installed on `vig-os`. Nothing here blocks `apply`.
