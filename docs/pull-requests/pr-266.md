# [PR 266](https://github.com/vig-os/org-config/pull/266) docs(changelog): tie the merge-method exit criterion to each repo's declared policy

## What

The live `## Unreleased` entry for [#246](https://github.com/vig-os/org-config/issues/246) stated the exit criterion as declaring `allowed_merge_methods: ["merge"]` in the jsonnet once the [ADR-0005](docs/adr/0005-repo-tooling.md) otterdog pin reaches a version fixing [upstream #768](https://github.com/eclipse-csi/otterdog/issues/768). That literal is wrong for the org as a whole, and `.github/workflows/prepare-release.yml` freezes `## Unreleased` verbatim into the released section — so without this it ships as a permanent instruction that no later PR may edit.

The criterion now reads: declare `allowed_merge_methods` **matching each repo's declared merge policy** (house = merge commits only), not a blanket `["merge"]` mixin.

## Why — evidence

`otterdog/vig-os/house-defaults.libsonnet` defines three policies, and the org is not uniformly on the house one. In `otterdog/vig-os/vig-os.jsonnet`:

| Repo | Policy | Line |
| --- | --- | --- |
| `h5v` | `orgs.legacyMergePolicy` | 565 |
| `nvd-mirror` | `orgs.legacyMergePolicy` | 584 |
| `org-config-testbed` | `orgs.upstreamMergePolicy` | 677 |
| `qms` | `orgs.legacyMergePolicy` | 689 |
| `qx` | `orgs.legacyMergePolicy` | 711 |
| `vigos-mvp` | `orgs.legacyMergePolicy` | 959 |
| `vs-dolt` | `orgs.legacyMergePolicy` | 967 |

A single `["merge"]` in a shared ruleset mixin would silently narrow any of those seven the moment it gained a ruleset — the same class of unnoticed narrowing the #246 entry exists to record, only self-inflicted. The distinction is latent today because every ruleset-carrying repo (`commit-action`, `devkit`, `devkit-smoke-test`, `org-config`, `scitadel`, `sync-issues-action`) sits on the house policy; the entry now says the declaration must still be derived per repo rather than assumed.

The same line's *"every version through 1.6.0"* becomes *"through 1.6.1"*, verified rather than assumed:

```
$ uvx --from otterdog==1.6.1 python -c "from otterdog.models.ruleset import PullRequestSettings as P; print(list(P.__dataclass_fields__.keys()))"
['required_approving_review_count', 'dismisses_stale_reviews', 'requires_code_owner_review',
 'requires_last_push_approval', 'requires_review_thread_resolution']
```

No `allowed_merge_methods` in 1.6.1 either.

## What was checked and deliberately NOT changed

- **`unmanaged-controls.toml` L330-332** — its own exit criterion is already generic (*"declare `allowed_merge_methods` in the jsonnet as ordinary config — no row, either way"*). Its two `["merge"]` occurrences (L316, L326) describe the 2026-08-08 incident and the rejected control row respectively; both are correct as written.
- **`README.md` L54-63** — names the unmodelled parameters but carries no `["merge"]` literal and no exit criterion. Nothing to fix.
- So only the changelog disagreed with the tree; this restores a single source of truth.
- **`unmanaged-controls.toml:301`** still says *"every version through 1.6.0"*. Left alone deliberately: it is outside the lines this PR touches and, unlike `## Unreleased`, it is not frozen by a release, so it can be corrected whenever that file is next edited.
- `README.md:67-68`'s duplicated `unmanaged-controls.toml` link is a known prose nit, out of scope here.

## Scope

Changelog prose only — no jsonnet, ruleset, workflow, table-row or engine change, and `--controls-report` is unchanged. Hooks (`just precommit`) and tests (`just test`, 158 passed) green locally.

**#246 stays open** as the upstream #768 tracker; acceptance criterion (c) is unblocked only when the pin reaches a version carrying the fix.
