# [PR 273](https://github.com/vig-os/org-config/pull/273) docs(runbook): record that the engine App is public and why

## What

Docs-only. `docs/runbooks/github-app.md` told whoever creates the engine App to
answer *"Where can this GitHub App be installed?"* with **Only on this account**,
and contradicted itself two sections later by telling a downstream org's owner to
open *"the App's **public** install page"*. This records the actual posture —
**public, "Any account"** — with the reason, the two costs it carries, how to
verify it, and what a future flip would have to touch.

- creation step → **Any account**, public by decision, pointing at the new section;
- new **Visibility** section: the decision (dated, `#261`), what the setting controls
  per GitHub's own reference, the trade-off stated in *both* directions, the `#256`
  coupling with its scope corrected, and a `#### Verifying the setting` subsection;
- **Key rotation** gains step 6 — sweep `GET /app/installations` while the key is in
  hand, the only inventory a webhook-less App has;
- **Downstream-org installation** step 1 now says that step is *why* the App is public;
- `CHANGELOG.md` → `## Unreleased` → `### Changed`.

## Why — the two facts that decide it

1. **"Only on this account" is not compatible with the live installation set.**
   GitHub documents the private setting as *"can only be installed on the account
   that owns the app"*. This App is installed on `exo-pet` (installation
   `147219320`) as well as `vig-os` — under the documented setting that
   installation could not exist, so the only downstream org there is could not have
   been onboarded. That ties ADR-0004's *"One App, not four"* to this setting:
   private means one App, one key and one rotation **per org**, and `exoma-ch` /
   `MorePET` are meant to follow `exo-pet` through the same install page the
   runbook already points them at.
2. **Flipping would hide nothing.** `GET /apps/vig-os-org-config` returns, to an
   **unauthenticated** caller, the Client ID *and* the full 17-permission grant
   including `organization_administration: write`. A Client ID mints nothing
   without the PEM, so private would cost the multi-org model and buy no
   confidentiality. The residual risk is named rather than waved away: `events: []`
   means no `installation` webhook and `GET /app/installations` needs a JWT the CI
   credential never holds, so the set of accounts that have installed the App is
   unbounded, unmonitored and un-enumerable from CI — which is what Key rotation
   step 6 answers.

## Verification is a plain UI checklist, deliberately

`GET /apps/{app_slug}` carries **no visibility field**. The only API signal is the
status code to an *unauthenticated* call (`200` public / `404` private, with a
private App owned by a sibling org as the same-day control) — GitHub documents
neither that mapping nor the endpoint's auth requirements, so the section states it
as an observation, not a contract. The section therefore ships the UI checklist
(Settings → Developer settings → GitHub Apps → **Edit** → **Advanced**), including
the trap that the Danger-zone button names the **action**, not the state: a button
reading *Make private* means the App is currently public.

## Deliberately NOT done

- **No setting was changed.** This PR is a description catching up with reality; the
  App's posture is untouched.
- **`#261` is not auto-closed** (`Refs:`, not `Closes:`). Acceptance criterion 1 is
  the UI reading, which only an org owner can do — the decision paragraph says so in
  as many words and is phrased as *decided 2026-09-25, pending that verification*.
- **No `unmanaged-controls.toml` row**, and the section records why rather than
  leaving it to be rediscovered: there is no visibility field to assert, and the
  discriminator is visible only to an unauthenticated caller, which the controls
  transport can never be.
- **ADR-0004 is cited, not amended** — it already decided the model this setting
  implements; a visibility line there would be a second copy.
- **The flip is not treated as a one-paragraph swap.** Since a runbook has to state
  a setting where it is set, the section lists all four places a flip would touch
  (creation step, decision paragraph + CHANGELOG section, Downstream-org
  installation step 1, Key rotation step 6) so a future flip is a checklist.
- The spike's out-of-scope findings are filed separately and cross-referenced from
  the grant-table bullet: #270 (Client ID held as an Actions secret although the
  value is world-readable) and #271 (`vigos-devkit-upgrade` is public with no
  recorded decision either).
