# [PR 126](https://github.com/vig-os/org-config/pull/126) chore(config): declare selected visibility for the remaining eleven org secrets

Implements the rest of #123. **Stacked on #124** (the `ORG_CONFIG_CANARY` pilot) so it merges cleanly whichever order you take them in — if #124 goes first, that commit is already in `main` and this PR shrinks to its own diff; if this one goes first, it carries the pilot with it.

## What changes

All twelve `vig-os` org secrets were `visibility: all` — three GitHub App **private keys** and a Docker Hub token readable by every workflow in all 14 repos, including unmaintained `vs-dolt` and the automation-churned `org-config-testbed`. Each secret now declares the exact repositories whose workflows reference it.

| Secret | Selected repositories |
|---|---|
| `COMMIT_APP_CLIENT_ID` | commit-action, devkit, devkit-smoke-test, org-config, sync-issues-action |
| `COMMIT_APP_ID` | commit-action, devkit, devkit-smoke-test, **h5v**, org-config, **scitadel**, sync-issues-action |
| `COMMIT_APP_PRIVATE_KEY` | commit-action, devkit, devkit-smoke-test, h5v, org-config, scitadel, sync-issues-action |
| `DEVKIT_UPGRADE_APP_CLIENT_ID` | commit-action, devkit-smoke-test, org-config, sync-issues-action |
| `DEVKIT_UPGRADE_APP_ID` | commit-action, devkit-smoke-test, org-config, sync-issues-action |
| `DEVKIT_UPGRADE_APP_PRIVATE_KEY` | commit-action, devkit-smoke-test, org-config, sync-issues-action |
| `DOCKERHUB_TOKEN` | *(none — orphaned, see #125)* |
| `DOCKERHUB_USERNAME` | *(none — orphaned, see #125)* |
| `RELEASE_APP_CLIENT_ID` | commit-action, devkit, devkit-smoke-test, org-config, sync-issues-action |
| `RELEASE_APP_ID` | **h5v, scitadel only** |
| `RELEASE_APP_PRIVATE_KEY` | commit-action, devkit, devkit-smoke-test, h5v, org-config, scitadel, sync-issues-action |

`nvd-mirror`, `org-config-testbed`, `qms`, `qx`, `tessera`, `vigos-mvp` and `vs-dolt` end up in **no** list — 7 of 14 repos lose all org-secret reach. Full evidence: [consumer matrix](https://github.com/vig-os/org-config/issues/123#issuecomment-5219672966).

The lists deliberately differ per secret. The client-ID migration (#112) means `*_APP_CLIENT_ID` covers the five repos on `DEVKIT_VERSION=1.6.0` while `*_APP_ID` still covers `h5v` (`0.3.1`) and `scitadel` (`0.3.3`); the private keys are the union of both. Collapsing them into one shared list would silently re-widen the ID secrets.

## Config-only — and why

This PR **cannot** change live state, and that is a property of GitHub and otterdog, not a shortcut ([full investigation](https://github.com/vig-os/org-config/issues/123#issuecomment-5219693657)):

- `PUT /orgs/{org}/actions/secrets/{name}` -> `422 "encrypted_value", "key_id" weren't supplied` — the REST API will not change visibility without the value.
- `PUT .../{name}/repositories` -> `409 cannot update selected repositories ... when the visibility is not set to 'selected'` — cannot bootstrap the flip either.
- `otterdog apply` **skips** dummy-valued secrets entirely (`otterdog/models/secret.py:88`, `include_for_live_patch() == not has_dummy_secret()`), and these eleven are all `value: '********'`.

### Correction after seeing the plan

I expected eleven `~ org_secret` diffs that apply would decline to act on. The plan shows **none** — only the pilot's `ORG_CONFIG_CANARY` and the permanent `vs-dolt` noise:

```
  ~ org_secret[name="ORG_CONFIG_CANARY"] {
    ~ selected_repositories = [ + "org-config" ]
    ~ visibility            = "public" -> "selected"
  ~ }
  ~ repository[name="vs-dolt"] { ... }
  Plan: 0 to add, 3 to change, 0 to delete.
```

`plan` renders *live patches*, and `include_for_live_patch` gates live-patch generation (`models/__init__.py:788`), so dummy-valued secrets are dropped from the plan entirely rather than merely skipped at apply.

Good news: **no phantom drift** — the plan will not nag forever about a diff apply cannot fix.

Bad news, and the honest caveat on this PR: **the declared visibility for these eleven is documentation, not an assertion.** Nothing in this repo will notice if a list is widened again — `plan` will not diff it and the drift layer parses `plan`. It should be machine-checked alongside the other unmanaged controls in #116. Making it genuinely declarative would mean moving the eleven values into SOPS as the canary already is, which collides with ADR-0003's deliberate bootstrap exclusions and is a separate decision.

This is exactly why the pilot (#124) was kept separate — it is the one secret apply *can* write, so it is the one that stays enforced.

## Ordering — why this is safe

Config merges first (declaring the **full** consumer list), then live is narrowed to exactly that list. In between, live is *broader* than declared — never narrower — so no consumer can lose reach mid-flight. That is the opposite of the ordering that caused the `playground-carlos` outage.

## Maintenance coupling introduced

`DEVKIT_UPGRADE_APP_*` now reaches only the four repos carrying a scaffolded `devkit-upgrade.yml`. **Any repo re-scaffolded to devkit >= 1.6 must be added to those three lists** or its upgrade workflow fails with an empty credential and no error. This is recorded as a comment in the jsonnet beside the declaration. The good news: once visibility is `selected`, the list is editable **without** the secret value —

```console
$ gh api -X PUT orgs/vig-os/actions/secrets/DEVKIT_UPGRADE_APP_ID/repositories \
    --input <(printf '{"selected_repository_ids":[...]}')
```

— verified against a throwaway probe secret during the investigation. Asserting these lists automatically belongs with the other unmanaged controls in #116.
