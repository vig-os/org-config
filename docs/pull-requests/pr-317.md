# [PR 317](https://github.com/vig-os/org-config/pull/317) chore(config): declare stepv and grant it the App org secrets

## Description

Brings `vig-os/stepv` under org-config management — declaration, credentials and
test ground truth together, since they are one file set and one apply.

Supersedes #316, which was opened on a branch named `feat/declare-stepv`. The
branch-name gate only accepts `<type>/<issue>-<summary>` for
`feature,bugfix,hotfix,release,docs,test,refactor`, or `chore/<summary>`; `feat`
is not a type. Renaming the branch closed that PR rather than retargeting it, so
this is the same two commits on a correctly named branch.

### The declaration

A devkit 1.17.0 **trunk** scaffold (`.vig-os` `DEVKIT_WORKFLOW=trunk`), so it
takes the same ruleset shapes as `h5v` — the only other trunk repo — and
deliberately carries **no** `Dev protection`: there is no `dev` branch to
protect. Releases fork `release/X.Y.Z` from `main` and merge back through the
release PR. `type: ['tools']` on the required org custom property, and
`allow_update_branch` so the "Update branch" button can satisfy Main
protection's `strict` requirement without a manual rebase (#188).

One honest note, recorded in the declaration itself: this repo was created with
`gh repo create` rather than by `otterdog apply`, which is the bypass the
org-settings comment at the top of that file warns about. Nothing was lost —
apply never deletes what the config omits — but stepv sat as an inventory drift
finding (#21) until this lands.

Unlike `h5v` (whose vig-os/h5v#9 is still open), stepv ships
`DEVKIT_SYNC_TARGET=sync/issue-mirror` from its first scaffold, so its nightly
`sync-issues.yml` never attempts the direct `main` push that `Main protection`
would refuse (vig-os/devkit#1227).

### The secrets

stepv joins the six **client-ID-form** lists only — `COMMIT_APP_CLIENT_ID`,
`DEVKIT_UPGRADE_APP_CLIENT_ID`, `RELEASE_APP_CLIENT_ID` and the three matching
`*_PRIVATE_KEY` unions. Like `tessera` it is on that form from day one, so it is
deliberately absent from the numeric `*_APP_ID` lists and leaves nothing for
#112 to retire. Without these its scaffolded workflows fail with an empty
credential and no error.

### The test ground truth

This is what #316 got wrong. Adding a repo to the jsonnet without updating the
pinned ground truth is a red CI:

- `DECLARED_REPOS` in `tests/conftest.py` — the set the inventory sweep must
  extract from the committed config.
- `DECLARED_ORG_SECRETS` — name -> (visibility, sorted
  selected_repositories), updated for exactly the six lists above.
- `tests/test_app_actors.py` — declared App-actor sites, 23 -> 25. A
  trunk-model repo contributes exactly two bypass sites (`Release protection`'s
  `commit-action-bot`, `Tag protection`'s `vig-os-release-app`); `Main
  protection` and `Signed commits` declare none. That rule is now in the
  docstring.

Verified with `jsonnet` actually on PATH, because the two app-actor ground-truth
tests skip silently without it: `nix shell nixpkgs#go-jsonnet -c uv run pytest
tests/` gives **224 passed, 0 skipped**. `jsonnetfmt --test` passes.

### Not declared yet, on purpose

The `crates-io` environment and `CARGO_REGISTRY_TOKEN` that `scitadel` carries.
stepv's first crates.io publish is step S6 of its own plan, and declaring a repo
secret whose live value does not exist is how an apply goes wrong. Both land in
the same PR as the first release.

## [Comment #2](https://github.com/vig-os/org-config/pull/317#issuecomment-5980665589) by [@gerchowl](https://github.com/gerchowl)

_Posted on October 4, 2026 at 01:46 PM_

### Reviewer note: merging this does **not** actually grant stepv the credentials

The Otterdog plan on this PR is `4 to add, 11 to change, 0 to delete` — four rulesets and eleven
repo settings. **Zero secret actions.** The six `selected_repositories` additions in this diff do
not appear in the plan at all, and that is not a plan-rendering quirk.

#### The evidence is `revkit`, independently of this PR

`revkit` was added to the same six lists in `63420ca` ("grant revkit the App org secrets scitadel
has"), merged as #312 on 2026-09-29. `apply-engine.yml` ran **successfully for exactly that
commit** at 2026-09-29T20:59, and twice more since (2026-09-30, 2026-10-01). Live state today:

| secret | declared but not live |
| --- | --- |
| `COMMIT_APP_CLIENT_ID` | `revkit`, `stepv` |
| `COMMIT_APP_PRIVATE_KEY` | `revkit`, `stepv` |
| `DEVKIT_UPGRADE_APP_CLIENT_ID` | `revkit`, `stepv` |
| `DEVKIT_UPGRADE_APP_PRIVATE_KEY` | `revkit`, `stepv` |
| `RELEASE_APP_CLIENT_ID` | `revkit`, `stepv` |
| `RELEASE_APP_PRIVATE_KEY` | `revkit`, `stepv` |

(`live-not-declared` is empty for all six, so nothing has drifted the other way.)

Three successful applies over five days did not add `revkit`. The declaration is not being
reconciled.

#### Why, most likely

The `ORG_CONFIG_CANARY` comment in this very file already says it: that secret's value is a real
credential-provider reference "rather than a `'********'` dummy, so `include_for_live_patch` is
true and apply can set visibility declaratively (secret.py:88)". The other nine carry dummies, so
apply skips their live patch — and the `DEVKIT_UPGRADE_APP_ID` comment's note that the list "is
editable without the secret value via `PUT /orgs/vig-os/actions/secrets/<NAME>/repositories`"
reads, in hindsight, as an out-of-band instruction rather than something apply performs.

#### What this means for merging

Merging and applying this PR is still correct and still worth doing — it lands the rulesets, the
settings, the custom property and the test ground truth, and it closes the #21 inventory drift.
But stepv's scaffolded workflows (`sync-issues`, `devkit-upgrade`, the release train) will keep
failing with an empty credential and no error message until someone runs the six PUTs by hand.
Same for revkit today.

Filed separately as #318 so it does not ride on this PR, and noted in stepv's own `plan.md` §7.
