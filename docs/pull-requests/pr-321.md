# [PR 321](https://github.com/vig-os/org-config/pull/321) feat(plan): report declared org-secret readers against live

## Description

Option 1 of #318. `otterdog apply` never live-patches an org secret whose committed value is a `'********'` dummy (nine of ten here), so a repository added to such a secret's `selected_repositories` plans clean, merges, and is never granted (revkit #312, stepv #317, surfaced days later by drift #313). This adds a read-only **Declared org-secret readers** section to the plan report, beside **Declared App slugs** and built the same way: it diffs each comparable declared secret's reader list against live `GET /orgs/{org}/actions/secrets/{name}/repositories`, lists declared-not-live readers with the exact hand-grant `gh api -X PUT` command (and says `apply` will **not** do it for a dummy-valued secret), and lists live-not-declared readers with the matching `DELETE`.

The comparison reuses the drift layer's: the `org-secret-repositories` family now calls the same `drift_layer.secret_repositories` helpers, so the review-time section and the daily issue cannot disagree.

## Changelog Entry

### Added

- **`plan` now reports each `selected` org secret's declared readers against live** ([#318](https://github.com/vig-os/org-config/issues/318)): a new `### Declared org-secret readers` section in the marker-upserted PR comment and the job summary, beside `### Declared App slugs` and for the same reason — config that is green on review and wrong on apply. `otterdog apply` never live-patches an org secret whose committed value is a `'********'` dummy (`models/secret.py` `include_for_live_patch` → `has_dummy_secret`), and nine of the ten org secrets are dummies, so a repository added to one of their `selected_repositories` plans clean, merges, and is never granted; its workflows then read the secret as an empty string with no error. That is what happened to `revkit` ([#312](https://github.com/vig-os/org-config/issues/312)) and `stepv` ([#317](https://github.com/vig-os/org-config/issues/317)), surfaced only days later by the daily drift run ([#313](https://github.com/vig-os/org-config/issues/313)). A new `drift-layer --org-secrets-report` mode, wired into `plan.yml` after the App-slug step, diffs every comparable secret's committed list against `GET /orgs/{org}/actions/secrets/{name}/repositories` and reports, per secret, **declared-not-live** readers — with the exact `gh api -X PUT "/orgs/{org}/actions/secrets/{name}/repositories/$(gh api /repos/{org}/{repo} --jq .id)"` to run, and a statement that `apply` will **not** do it for a dummy-valued secret — and **live-not-declared** readers, with the matching `DELETE`. A real-valued secret (`ORG_CONFIG_CANARY`) is marked as reconciled by `apply` instead, with no command. The comparison is not a second differ: the drift layer's `org-secret-repositories` family now calls the same `drift_layer.secret_repositories` helpers, so the review-time section and the daily issue cannot disagree, and the committed-config extractor now records whether each declared value is a dummy. The read uses the full installation token `plan` already mints, which holds *Organization → Secrets* (the org-management App writes org secrets at apply, and drift's controls leg reads the same endpoints with the same token). Same posture as the App-slug check (#259, #268): advisory, the mode always exits 0, the step is `continue-on-error` and `if:`-gated on the engine guard, and an unreadable list or a missing token degrades the section to "could not read — reason", never a finding or a red job; the comment's fragment byte cap moves from 8000 to 16000 to hold both sections. Org-generic: it reads `otterdog/<org>/<org>.jsonnet` from the caller's checkout, so downstream callers inherit it on their next engine pin bump. `docs/runbooks/secrets.md` gains a pointer to the section.
