# [PR 267](https://github.com/vig-os/org-config/pull/267) fix(client): follow the Link next header instead of stopping on a short page

## What

The four dedicated list methods on `RestGitHubClient` — `list_org_repos()`,
`list_open_drift_issues()`, `list_org_secrets()` and
`list_org_secret_repositories()` — each composed `page=N` by hand and stopped
walking on `len(batch) < 100`. They now share one page walk, `_paginate()`, over
the `(body, Link)` transport #258 split out, and the stop condition is the
`Link` header and nothing else: follow `rel="next"` until GitHub stops sending
one.

## Why

`len(batch) < 100` is an inference about GitHub's behaviour rather than a
reading of what GitHub said, and it is wrong in **both** directions: an endpoint
that filters *after* paginating returns a short page that is not the last, and a
collection ending exactly on a page boundary returns a full page that is.

`list_org_repos()` is the `live` side of the ADR-0002 inventory sweep, so an
undercount there fails twice over at `inventory.py:182-183` — a live repo past
the cut never produces its `undeclared` record (the shadow-repo finding the
sweep exists for, gone quiet on a green run), and a declared repo past the cut
produces a **false `absent`** record with a real issue opened against it.
Neither degrades: `cli.py:163-175` drops the inventory leg on a *raised*
failure, and a truncation raises nothing.

## The `next` target is followed verbatim

Not pedantry: `/repos/{owner}/{repo}/issues` paginates by **cursor**. Captured
live, its `next` is
`…/issues?state=open&per_page=1&page=2&after=Y3Vyc29yOnYyOpLPAAABoNmJ4NjPAAAAAUzzW7E%3D`
and it sends **no `rel="last"`** — the "cannot be calculated" case GitHub's
pagination guide describes. A composed `page=N` is therefore a *different
request* from the one GitHub hands back, and page-number walking on that
endpoint is on borrowed time. Following the URL verbatim is the only form that
survives the cursor migration.

The walk yields **whole documents** rather than merged rows, so the two body
shapes (root list for `/orgs/{org}/repos`, envelope keyed `secrets` /
`repositories` for the Actions-secret endpoints) stay the callers' knowledge and
the transport learns no per-endpoint table — the same argument #258 used to
*refuse* generic pagination inside `get_json`.

## Two loud failures instead of two quiet ones

- A `next` the walk cannot follow raises `TruncatedResponseError` rather than
  ending the walk quietly: "there is more" must never be read as "that was all".
- Following a URL costs the walk the ceiling a composed page number gave it for
  free (a repeating server used to end the loop as soon as the number ran past
  the collection). It now tracks the URLs it has fetched and refuses a `next`
  that repeats one, rather than spinning until the job's `timeout-minutes` burns
  the rate limit. The bound is on the thing that actually misbehaves — a server
  handing back a page it already served — not on a page count, which would have
  to guess how long a legitimate collection may be.

## Evidence

Red → green, TDD in two commits. The test commit is **10 failed, 156 passed**;
with the implementation, **166 passed**. One note on reading the red: every
failure is a `KeyError` on `/orgs/vig-os/repos?per_page=100&page=1` — the old
code composing a page number the header-driven fixture does not serve. That is a
*request-shape* red, not a rendering of the undercount itself; the old walk
cannot be asked to produce the undercount, which is precisely why it never
failed.

The fake transport moved down a layer with the code: `_RecordingClient` (faking
`_request`, one layer above the `Link` header, so it never exercised a page walk
at all) is replaced by `_PagedClient` faking `_send`, a URL → `(document, Link)`
map that asserts the **exact request sequence** — a multi-page walk, a
short-but-not-last page, a full 100-row last page that must cost exactly one
request, the issues endpoint's cursor `next`, the envelope endpoints, the
unfollowable `next`, and the repeated `next`.

Hooks: full `just precommit` green in the working tree (zizmor `No findings to
report`, `jsonnetfmt: OK`, otterdog `Validation succeeded`, every `prek` hook
`Passed`). `just test`: `166 passed`.

**Nothing is truncated today.** `vig-os` has 14 repositories and `exo-pet` 9,
and `GET /orgs/vig-os/repos?per_page=100` answers with **no `Link` header at
all**. This closes the stop condition before a fleet past 100 repositories gets
the bad half of it without a signal — a correctness fix ahead of the fleet, not
an incident.

## Deliberately not done

- `get_json()` is **untouched**: it still refuses a multi-page collection rather
  than resolving it (#258's deliberate choice, sketch option 3 deferred).
  `_paginate` now exists and yields documents, so the narrow version #258
  sketched is a short follow-up if a row ever needs it — noted on #258, not
  changed here.
- `_request` keeps its body-only signature and still serves the write methods.
- No live-API exercise: both orgs are single-page today, so the multi-page path
  is covered by fixtures only. A `--controls-report` or drift dry run with the
  full read token would confirm the single-page path end to end.
- `page=1` is no longer sent (the first request is `?per_page=100`); GitHub
  defaults to page 1 and omitting it was verified identical live.
- `TruncatedResponseError`'s message tail changed from "the row cannot be
  asserted against a partial answer" to "a partial answer cannot stand in for
  the whole collection", because it now has two raisers and the old wording was
  controls-specific. Nothing asserts the old text.
