# [PR 122](https://github.com/vig-os/org-config/pull/122) chore(config): block workflow PR approvals and member repo creation org-wide

Closes #121. Two approved org-level settings changes from the settings audit; follows #115 / #118.

## 1. `settings.workflows.actions_can_approve_pull_request_reviews: false`

```console
$ gh api orgs/vig-os/actions/permissions/workflow
{"default_workflow_permissions":"read","can_approve_pull_request_reviews":true}
```

An approving review from a workflow satisfies `Main protection`'s `required_approving_review_count: 1` **without a human**. It is the one permission that can defeat every review gate in the fleet, reachable by any workflow with `pull-requests: write` — including a workflow introduced by the very PR it would approve — and with `allowed_actions: all` and no action allow-list it reached every repo in the org. `devkit` was the only repo closing it at repo level.

Note the nesting: org-level workflow settings live under `settings.workflows` in the vendored schema's `newOrg`, which is a **different** location from the repo-level `workflows+:` block that hangs directly off `newRepo`.

`devkit`'s repo-level declaration is deliberately left in place — now redundant, but it keeps the intent explicit on the repo that publishes the fleet's tooling.

### Why the validation info count jumps 21 -> 33

`otterdog validate` still succeeds with **0 errors**, but now emits 12 new INFOs of this form:

```
Info: repository[name="org-config"] has 'actions_can_approve_pull_request_reviews' enabled,
      while on organization level it is disabled, setting will be ignored.
```

That is otterdog confirming the change does what we want. GitHub's semantics are org-wins, and otterdog encodes them: `repo_workflow_settings.py:64-65` UNSETs the repo-level field from diff computation whenever the org has it `False`. So the twelve repos still carrying the schema's permissive repo-level default are now moot, and — importantly — otterdog will **not** try to PATCH each of them. The plan below confirms that: org settings only.

## 2. `members_can_create_{public,private}_repositories: false`

Both were declared an explicit `true` at `vig-os.jsonnet:12-13`. This binds today rather than being theoretical — the org has three members, two owners (`c-vigo`, `gerchowl`) and one plain member (`irenecortinovis`).

Repository creation here is meant to be config-first: declared in `vig-os.jsonnet`, created by `otterdog apply`. A repo created through the UI bypasses every default this repo exists to enforce — merge policy, rulesets, signed commits, secret scanning — and starts with no ruleset at all.

The recovery path is deliberately asymmetric and slow, which is what makes the prevention worth having:

- apply **creates** what the config declares but never **deletes** what it omits. `--delete-resources` is deliberately omitted (`.github/workflows/apply.yml:72-73`: *"resources absent from the config are NOT deleted (apply.py:142-144 skips REMOVE patches without the flag). Destructive deletions stay a manual, explicitly-flagged operation."*).
- So an undeclared repo is never cleaned up automatically; it surfaces only as a `drift` + `critical` inventory issue in the `repository-inventory:<name>` namespace (#21) and is then removed by hand.

Organization **owners** can still create repositories — GitHub grants that unconditionally and no org setting revokes it — so for `c-vigo` and `gerchowl` this remains discipline plus the drift sweep. That residual is accepted, not overlooked.

Kept as explicit values with an inline rationale comment (house style: state the decision rather than lean on a default).

Plain org-settings PATCHes — #69 affects repo *rulesets* only, so **no manual live reconciliation** here. The plan below shows the three org-setting changes and `otterdog apply` writes them after merge.
