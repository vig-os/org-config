# [PR 206](https://github.com/vig-os/org-config/pull/206) feat(drift): address JSON list elements in unmanaged-control paths

## Summary

Closes #205.

`select_path()` walked objects only, so anything GitHub returns **inside a list** was unassertable — and the most consequential control is exactly that shape: a repository ruleset's `rules` are an array keyed by `type`, and the required status checks inside one of them are an array of objects. Downstream `exo-pet/org-config` keeps four hand-managed `Main protection` rulesets as `kind = "unassertable"` rows for precisely this reason.

- **Two new path forms**, stdlib-only and still deliberately not jq (ADR-0005): `rules[type=required_status_checks]` selects the **one** element whose field equals the literal; `required_status_checks[].context` projects a field out of **every** element. An empty key applies either operator to the response itself, for endpoints answering with a list at the root. Path splitting is bracket-aware, since check contexts are free text (`CodeQL Analysis (python)`, `build.test`).
- **`compare = "set"`**: an order- and duplicate-insensitive comparison against a TOML array, because GitHub returns a check list in no guaranteed order. Both sides normalise to a type-tagged frozenset, keeping `_equal`'s discipline that `true` is not `1`.
- **Every ambiguity degrades, none guesses.** Zero or several matches, a projection over a non-list or one element that cannot satisfy it, a malformed path, and a live value that cannot become a set all resolve to `UNRESOLVED`, leaving the row's own issue untouched. Two rulesets can contribute a rule of the same type to one branch — picking either would fabricate or hide a security finding — and a partial projection would compare as a shorter set and read as drift or, worse, as clean.
- **Load-time validation**: an unknown `compare` mode, an unparsable path, or a set row whose `expect`/`tolerated` is not a list of plain values **drops the row**, per the standing rule that a malformed row must never manufacture a finding.
- **Drift bodies** gain `missing:`/`unexpected:` lines — a dropped required check and an unexpected extra one are different incidents.

## Acceptance (#205)

| Criterion | Where |
|---|---|
| Assert the required-check **set** of a ruleset, order-insensitively | `[type=required_status_checks].parameters.required_status_checks[].context` + `compare = "set"` |
| Assert `strict_required_status_checks_policy` | `[type=required_status_checks].parameters.strict_required_status_checks_policy` |
| Zero/several matches degrade | `MISSING` → `UNRESOLVED`, tested both directions |
| Downstream can convert its `main-protection-*` rows | worked rows in `template/unmanaged-controls.toml` |

## Two deliberate decisions

**`/repos/{org}/{repo}/rules/branches/{branch}`, not `/rulesets/{id}`.** The issue's wording says "a *named* ruleset", but the name-addressed endpoint (`/rulesets`) returns summaries with **no `rules`**, so honouring it literally costs a second request and a name→id hop. The branch-rules endpoint carries the full `parameters` in one read, needs no id hard-coded in the table, is readable with repo read access, and asserts what actually protects the branch whichever ruleset carries it. Verified live against the exact repo the issue cites:

```console
$ # GET /repos/exo-pet/exo-fleet/rules/branches/main
[type=required_status_checks].parameters.required_status_checks[].context  -> ['CI Summary', 'Check Summary']
[type=required_status_checks].parameters.strict_required_status_checks_policy -> True
```

**No new row in this repo's table, and the table says why.** Every vig-os repo but one is public, where Otterdog models rulesets and the plan already diffs them — a row would duplicate a modelled control, which is what this table is not for. The exception, `qms`, is private on a Free-plan org where both ruleset endpoints answer `403 Upgrade to GitHub Pro`. This is capability for downstream orgs on Team/Enterprise, whose private repos Otterdog cannot read (#107, eclipse-csi/otterdog#729) while REST can.
