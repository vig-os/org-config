# [PR 285](https://github.com/vig-os/org-config/pull/285) fix(ci): make the plan report and comment upsert steps fail-soft

## Description

The reusable `plan.yml` had two auxiliary steps that could redden the job on their own, independently
of the plan verdict. `Build plan report (comment body + job summary)` and `Upsert plan comment on the
PR` render cosmetics — a marker-upserted PR comment and the job summary — and contribute nothing to
the verdict, which is carried by `Run otterdog plan` (captures `rc` rather than failing) and `Fail on
plan error` (reflects that `rc` and is *meant* to redden). Yet both ran under `if: always()` with
`set -euo pipefail` and no `continue-on-error`, so any nonzero command in the body assembly, or any of
the upsert's three network calls (a `--paginate` comment read, then a `PATCH` or a `POST`), failed the
whole `Plan` job.

None of those failure modes says anything about whether the committed config is valid: a 422, a 403 on
a paginated page, a secondary rate limit on a token this job has already spent on a full org read, a
plain GitHub 5xx, or a `comment-body.md` the report step never got to write.

**The exposure is downstream, not here.** ADR-0007's Axis D verdict stands for this repository —
`vig-os`'s own `Main protection` requires exactly one status context, `CI Summary` (integration_id
`15368`), so `Plan` is advisory locally (#230, #236). But `exo-pet/org-config`'s `Main protection`
requires exactly `plan / Plan committed config against live exo-pet`, and its caller ships no `paths:`
filter for precisely that reason (#268) — so there a cosmetic comment upsert that 5xx'd took the
consumer's merge gate with it, for every pull request including ones that touch no config, arriving
silently on a Renovate pin bump. That is the one failure this design forbids.

Closes #276

## Changes Made

- `.github/workflows/plan.yml`
  - `Build plan report (comment body + job summary)` (`:432`) gains `id: report` and
    `continue-on-error: true`, plus a step comment stating the degradation shape: **a red X on the
    step inside a green job**, the plan output still present in the job summary (written at
    `:459-476`, before the comment body is built, so a failure in the byte-budget half still leaves
    the diff readable), and no PR comment. Visible, not swallowed.
  - `Upsert plan comment on the PR` (`:547`) gains `continue-on-error: true` and its `if:` is
    extended with `&& steps.report.outcome == 'success'`. The guard is what keeps degradation to a
    single red X: without it, a failed report leaves a *second* red step here — `jq` exiting nonzero
    on a `comment-body.md` that was never written — pointing at the symptom rather than the cause.
    Its comment records the three network calls and why none of them is a verdict.
  - The header's fail-soft rule (`:54-77`) is rewritten to state its two classes with **no
    exceptions**, retiring the "known exceptions, not precedent" wording #268 shipped. A future
    auxiliary step that is not fail-soft now has no precedent in the file to point at.
  - Both steps follow the pattern the three steps #274 shipped already use (`:300`, `:325`, `:363`).
- `docs/adr/0007-ci-and-testing-strategy.md`
  - One sentence corrected: the #268 correction bullet described the header as *naming* these two as
    shipped exceptions. Changing the header made that description false, so it now records the
    original wording in the past tense and that #276 retired it. Same change, so the two cannot
    drift apart.
- `CHANGELOG.md` — one `### Fixed` bullet under `## Unreleased`.

**Deliberately unchanged:**

- `Fail on plan error` (`:574`) stays unguarded under `if: always()`. `continue-on-error` there would
  silently disarm the check; it *is* the verdict spine, and the consumer's stated contract is that the
  check reddens on invalid config, auth, or harness errors.
- `MAX_BODY_BYTES=55000` (`:487`) stays. It closes one 422 cause cheaply while `continue-on-error`
  covers the rest — both, not either.
- `template/.github/workflows/plan.yml` is a thin `uses:` wrapper and needs no change.

### Manual Testing Details

**What this PR's own run proves, and what it does not.** Stated plainly because there is no test here
and it would be easy to imply one.

**Provable, and proved by this PR's own `Plan` run — the green path.** `plan.yml` is inside its own
`paths:` filter (`:88`), so editing it runs the job on this pull request. That run exercises exactly
the two steps changed, on the real API, and the expected observable is: the plan comment is upserted
**in place** on the hidden marker (not stacked — the `--paginate` read still finds the existing one
across re-runs), the job summary is written, `Fail on plan error` still reports the plan's `rc`, and
the job is **green**. The `steps.report.outcome == 'success'` guard is exercised on its success branch
by the same run.

**Not provable, and not claimed — the degraded path.** There is no way to make GitHub return a 422 or
a 5xx to `gh api` on demand from this repository, and `act`-style local runs do not reproduce the
comment API at all. So the failure branch — red X on the step, green job, summary intact, no comment,
and the upsert correctly skipped — is **unexercised**. The remaining evidence for it is a read of the
diff plus `actionlint` and `zizmor --offline` on the changed workflow; its first real exercise is
whenever GitHub next fails a write. No test is added, because a test that cannot induce the condition
would only assert the YAML back to itself.
