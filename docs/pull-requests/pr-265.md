# [PR 265](https://github.com/vig-os/org-config/pull/265) docs(rulesets): record that an App bypass actor cannot be created by apply under an installation token

## What

Docs-only. Records, in the four places that describe ruleset fields and ruleset
ownership, that a GitHub App **bypass actor** can only be written by `apply`
while the engine's own token can read the App:

- `README.md` → new *Known limitations* bullet (mechanism, observation,
  workaround, residual gap, cross-links);
- `otterdog/vig-os/vig-os.jsonnet` → a `//` note at the first `bypass_actors+`
  list, explicitly scoped to **every** App actor throughout the file;
- `unmanaged-controls.toml` and `template/unmanaged-controls.toml` → the
  residual gap plus the decision that it gets **no control row**;
- `CHANGELOG.md` → one `### Changed` bullet under `## Unreleased`.

This closes items (1) and (3) of #256. Item (2) — surface it at plan time — was
split out to #259; the read-side sibling is #262.

## Why

Otterdog resolves an App bypass actor on the **write** path through
`GET /apps/{app_slug}` (`models/ruleset.py:649`), and every otterdog job here
authenticates as an App *installation* (ADR-0004 *Corrections*), so the write
succeeds only where that endpoint is readable to such a token. The **read** path
never calls it — it maps the live `actor_id` back to a slug from
`GET /orgs/{org}/installations` — which is why `plan` and `drift` render the
actor correctly and this one class of change is green on review and red on
apply. A green L2 gate over an unappliable merge is the thing this repo's model
exists to prevent, so it gets written down where an editor will meet it.

## The predicate, stated as an observation

GitHub's reference for `GET /apps/{app_slug}` documents **no** authentication
requirement at all, so the docs say "observed", not "documented". Probed
2026-09-25:

| App | anonymous | org-owner PAT | installation token |
|---|---|---|---|
| `commit-action-bot` (public) | `200` | `200` | writes succeed (below) |
| `vig-os-release-app` (public) | `200` | `200` | writes succeed (below) |
| the private App in the report | `404` | `200` | `403` (the traceback in #256) |

## Six, not ten

An earlier draft said "the apply of 2026-08-08 rewrote **ten** rulesets carrying
them". Two different tens were being conflated: #246's incident set (ten
rulesets rewritten that day) and this file's ten declared App bypass actors. The
intersection is **six** — *Dev* + *Release* protection on `commit-action`,
`devkit`, `sync-issues-action`, all naming `commit-action-bot` (e.g. ruleset
`18922479`, `updated_at 2026-08-08T09:34:28+02:00`, `actor_id 2433383`).

`vig-os-release-app` sits on the three *Tag* protection rulesets, none of which
is in that set, so it is evidenced separately: apply run `31190546346` **created**
`vig-os/devkit` *Tag protection* (`20558615`, `created_at
2026-08-07T17:11:11+02:00`) with that App as its only bypass actor, from an
`apply.yml` that already minted an installation token at that sha — i.e. both
Apps are observed to be resolvable by an installation token, just on different
days.

## Workaround wording

The out-of-band path documented is a **one-off `otterdog apply` run with an
org-owner PAT** (an owner can read the slug), *not* a hand-built REST `PUT` with
`actor_id`: hand-assembling a ruleset payload is exactly the operation #246
proved loses unmodelled fields, and it would be self-contradictory to recommend
it in the same release as that entry. Once the actor is live, the installation
token's read path maps `actor_id` via `/orgs/{org}/installations`, matches the
declaration and plans clean, so the declaration still detects drift.

## Deliberately NOT done

- **No plan-time check** — that is #259 (warn-only, per the ADR-0007 Axis D
  decision on #236, and scoped to all four `get_app_ids` write-path call sites,
  not bypass actors alone).
- **No control row** in `unmanaged-controls.toml` — the field is modelled and
  read, so a row would duplicate detection the plan already does, and no row can
  restore a write path. The decision is recorded in the comment instead.
- **No jsonnet config change** — the only jsonnet edit is a comment; `plan` runs
  on this PR and should be empty.
- **No downstream/exo-pet action** — the consumer that hit this was remediated
  2026-09-24, before the issue was filed, and its applies are green since. What
  remains there is the *repair* gap, which is what this PR documents.
- **No ADR-0004 edit** — the README bullet cites its *Corrections* block rather
  than adding a second home for the same fact.
