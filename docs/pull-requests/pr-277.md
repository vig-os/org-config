# [PR 277](https://github.com/vig-os/org-config/pull/277) docs(adr): correct ADR-0007's claim that Axis D propagates downstream

## What

Docs and comments only, six files, no behaviour change.

- **`docs/adr/0007-ci-and-testing-strategy.md`** — the last Consequences bullet (`:148-151`) is corrected in place: the Axis D decision is `vig-os`-local and does not propagate; a consumer org decides the enforcement status of its own plan context, and the required context and the deleted `paths:` filter are **one** decision, because a filtered skip leaves a required context `Pending` forever. A dated **2026-09-25 (#268)** Corrections entry quotes the original verbatim with the evidence, and a supersession trigger records that `template/`'s shipped filter is provisional on a sample of one. The L2 bullet's "`Plan` is not a required status check" is scoped to this repository.
- **`.github/workflows/plan.yml`** — a file-level `DOWNSTREAM MERGE GATE — FAIL-SOFT IS BINDING` block above `name: Plan`, beside the `paths:` rationale, plus a scoping fix on the one unscoped sentence at the App-slug step.
- **`template/.github/workflows/plan.yml`**, **`template/README.md`** — delete the `paths:` filter in the same change that makes the context required, stated as a rule.
- **`renovate.json`** — the otterdog `packageRules` description stated the advisory claim unscoped; the sweep behind #274 missed it.
- **`CHANGELOG.md`** — one `## Unreleased` → `### Changed` bullet.

## Why

`plan.yml` is a reusable `workflow_call` workflow, and the only consumer makes its context a required check on `main`. So every step added here runs on another org's merge gate, on every pull request, including ones that touch no config — and the ADR, which is the source the next author reads, said the opposite. #259 was designed against that wrong model and drafted an unguarded engine checkout into this workflow (shipped fail-soft and scoped instead, #274).

## The dating evidence, re-derived

The issue body says the claim "has been wrong since the consumer's #62". That is wrong, and in the direction that would have put a self-refuting date pair into a record kept verbatim for audit. Verified here, GETs only:

| Fact | Evidence | When |
| --- | --- | --- |
| the ADR bullet is written | `git blame -L 148,151` → `868d4f5` *"docs(adr): decide the Plan check stays advisory (ADR-0007 Axis D)"* | 2026-09-23 |
| `exo-pet/org-config` deletes its caller's `paths:` filter | `04d8645` *"ci(plan): run plan on every PR as the required main status check"*, `Refs: #35` | 2026-08-24 07:52Z |
| ruleset `20545163` gains `required_status_checks: [plan / Plan committed config against live exo-pet]` | `/rulesets/20545163/history` → version `47427003` (live version `47427597`, 08:02Z); versions `46521975` and `45767895` carry no such rule | 2026-08-24 07:53Z |
| that repo's **#35** *"Make plan an always-running required status check on org-config main"* closes | `gh issue view 35` | 2026-08-24 07:56Z |
| that repo's **#62** *"Declare the six hand-managed rulesets…"* closes | `gh issue view 62` | 2026-09-24 |

So both halves went live on **2026-08-24 under #35**, a month before the ADR bullet and a month before #62 — which only imported the already-live, hand-managed ruleset into the committed jsonnet, and closed a *day after* the bullet. The entry therefore says the bullet was untrue on the day it was written, not that it went stale, and dates it by #35.

Severity is stated as it is live rather than at its worst: `gh api repos/exo-pet/org-config/rulesets/20545163` shows `enforcement: active` with one `bypass_actors` entry, `#OrganizationAdmin` at `bypass_mode: pull_request`, alongside `required_approving_review_count: 0`. A red context there blocks everyone *but* the org owner — which is an accidental instance of the #115 / #167 / #195 / #226 pathology the neighbouring ADR bullet rejects, and the correction says so instead of claiming "no consumer PR can merge".

The header splits the rule the way the file actually behaves, so a rule declared *binding* is not contradicted by the file it heads: the **verdict spine** (checkout, uv, pin resolve, token mint, `Run otterdog plan`, `Fail on plan error`) reddens by design — that is the contract the consumer's own caller states — while **everything auxiliary** must be fail-soft. The two shipped auxiliary steps that do not meet the rule yet, `Build plan report` and `Upsert plan comment on the PR`, are named as the known exceptions and tracked in #276.

## What survives unchanged

- `:145-147` — *"`Main protection` deliberately gains no second required context"* — is about **this** repository and stands, as does the #236 Axis D verdict behind it (#230: `vig-os`'s gate requires only `CI Summary`). Verified byte-unchanged.
- The Mode B sentence is kept, re-scoped to *mutation*: on a private consumer below Enterprise, `workflow_dispatch` is still the human gate on apply.
- Every binding credential rule in the Decision — they bind who may reach the App token, never who may require the check.
- The released **v1.4.0** CHANGELOG entries for #236 and #230 carry the unscoped wording and are **left as history** (released entries are never edited); they were true of this repo when written. The new Unreleased bullet records that, so acceptance item 4 is met for every live file rather than silently.
- `docs/issues/*` and `docs/pull-requests/*` are archival, untouched per the #248 precedent.

## Deliberately NOT done

- **`template/`'s `paths:` filter is annotated, not flipped.** n = 1: ADR-0006 puts a new org on Free, plan-first, where a private repo cannot enforce any context at all, so the org that takes the template on day one cannot be in `exo-pet`'s position yet, and unfiltered there means a credentialed live-API round trip on every README typo — the cost #235 recorded as the filter's whole purpose. Item 5 of this issue asks to *re-check at the next onboarding* before concluding the default is backwards, so flipping now would pre-empt its own acceptance criterion. Recorded instead as an ADR supersession trigger; the flip would want its own issue, since it changes what every future org ships.
- **No fail-soft code change.** Making `Build plan report` / `Upsert plan comment` fail-soft is a behaviour change on a downstream merge gate and belongs in #276, not in a docs PR.
- **Dated third-party governance state stays in the Corrections entry only.** The `template/` block and the `plan.yml` header state the rule unconditionally and name no other org's ruleset or context string — a template skeleton ships into future orgs, and ADR-0007 has now been corrected three times, twice for recording downstream state as durable fact.
