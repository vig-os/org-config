# [PR 274](https://github.com/vig-os/org-config/pull/274) feat(plan): warn when the engine token cannot resolve a declared App slug

## What

`plan` now asks this job's own installation token the two questions otterdog asks and the plan diff
cannot, and folds the answer into the PR comment and the job summary as one `### Declared App slugs`
fragment inside the existing marker — no second comment.

- **`GET /apps/{slug}` per declared slug** — the WRITE-path resolution. `apply` writes every
  App-shaped actor (ruleset `bypass_actors`, ruleset and branch-protection required status checks,
  environment reviewers) by resolving its slug through that call; a `403`/`404` means the patch
  fails, including on a later change to a resource that is already live, because a ruleset patch
  re-sends the whole list. Three of the four sites abort the patch; an environment reviewer is
  instead caught and **skipped**, leaving a protection that was never written, so the report puts
  them in separate tables.
- **Membership of `GET /orgs/{org}/installations`** — the READ-path resolution, for the two ruleset
  sites whose read path needs it (#262's detection half). A declared App the org has no installation
  for is dropped outright as a bypass actor or read back in its numeric `<id>:context` form as a
  status check, so `plan` proposes the same change forever and `apply` never converges.

The two are independent, not an `elif`. The second is deliberately **not** applied to
branch-protection status checks or environment reviewers: an un-prefixed branch-protection check
resolves to the implicit `github-actions`, a first-party App that is never an org installation and
that this org's own `tessera` rules declare and plan clean — a blanket check would fire twice on
today's green config.

Declared actors are extracted token-free, by evaluating the committed jsonnet with otterdog's own
`jsonnet_evaluate_file` (the exact call `GitHubOrganization.load_from_file` makes), so `drift_layer`
stays stdlib-only and only the two reads are credentialed.

## Why

Otterdog's read and write paths resolve a GitHub App differently, which is the whole reason #256
happened: the config was green on review and red on the mutating `apply`. This puts the write path's
own question on the pull request, where this repository's model says failures belong.

## Fail-soft posture (#268)

The draft was designed against ADR-0007's claim that a consumer org wires no plan context into its
ruleset. That claim is wrong about the only consumer: `exo-pet/org-config`'s `Main protection`
requires exactly `plan / Plan committed config against live exo-pet`, and its caller ships **no**
`paths:` filter for that reason (#268 corrects the ADR). So every step here sits on another org's
merge gate, for every PR, including ones that touch no config — and arrives silently on a Renovate
pin bump. Accordingly:

- all three new steps carry `continue-on-error: true`, the engine checkout is `if:`-gated on the
  guard's output, and the engine-pin guard warns and skips rather than `exit 1`ing (the deliberate
  divergence from `drift.yml`, where the drift layer *is* the job);
- the CLI mode catches **every** exception and returns 0 itself rather than relying on the
  workflow's `if !` wrapper — tested;
- `steps.plan.outputs.rc` is neither read nor written, so *Fail on plan error* keeps its contract;
- the comment body now reserves the fragment's bytes inside the 55000-byte budget (fragment capped
  at 8000, truncation noted in place), because an over-long body makes the upsert's `gh api` return
  422 under `set -euo pipefail` — i.e. it would fail that gate.
- `README.md` no longer says flatly that `Plan` is not a required check; the claim is scoped to this
  repository and points at #268.

## Rate limits are not findings

GitHub answers `403` both for *"Resource not accessible by integration"* (the #256 true positive)
and for rate-limit exhaustion, with the same reason phrase — and the step immediately before this
one is a full org read on the same token, the likeliest way to arrive at the limit. `ApiError` now
carries the response headers (lower-cased), and a `403` with `retry-after` or
`x-ratelimit-remaining: 0` is classified **undetermined** and reported under "could not be checked",
never as "`apply` will fail on these". A permission `403` (no such headers) stays a finding. Both
directions are tested, as is the same degradation on the installations read.

## Allow-list

`drift-allowlist.toml` gains a third section in the shape of the other two: `[[app_actor]]` with
`slug` + `reason`. A slug named there is still checked and still printed on every run — under
**known and suppressed**, with its reason — but is not a finding. The case this exists for is a
*private* App owned by a sibling org, on a ruleset that is already live and correct and unrepairable
until upstream eclipse-csi/otterdog#772 lands: without suppression that is a red banner on every PR
comment that nobody can act on, which is exactly the standing noise #262 warns trains reviewers to
wave plans through.

**`vig-os` adds no entry, deliberately** — all three slugs it declares (`commit-action-bot`,
`vig-os-release-app`, the implicit `github-actions`) resolve for this org's installation token, and a
test asserts the committed file suppresses nothing. A downstream org that declares a private App adds
its own entry, in its own config repo; the shape is documented in `template/drift-allowlist.toml`,
and the mode reads the allow-list from the config repo's root (the caller's checkout), not the
engine's.

## Evidence

- `just test`: **224 passed** (was 203 on `main`; TDD — tests committed red first:
  `ModuleNotFoundError: drift_layer.app_actors`, `ImportError: load_app_actor_allowlist`, and
  `2 failed, 24 passed` in `test_github_client.py` on the missing `ApiError.headers`).
- `just precommit`: every hook **Passed**, zizmor `No findings to report` (67 ignored, 140
  suppressed), `otterdog validate --local` succeeded.
- The runtime seam was run by hand, exactly as the step runs it:
  `uvx --from otterdog@1.5.0 python -c '…jsonnet_evaluate_file…' otterdog/vig-os/vig-os.jsonnet`
  → rc=0, 45853 bytes, no credential; then the sub-mode against that output with
  **`DRIFT_REPOS_TOKEN` unset** → the "could not be checked" fragment, `rc=0`.

## Proof limits

This PR's own plan run proves the **green path only**: three declared slugs all `200`, one
installations read, `github-actions` correctly not flagged, the fragment in the comment and the job
summary inside the existing marker, `rc` unchanged. It proves nothing about the unresolvable path
(no private App is declared in `vig-os`, and adding one would prove the check by breaking what it
protects), the suppression path, or the rate-limited path — all three are unit-tested only. The
downstream `.drift-engine` checkout and `job.workflow_sha` resolution are first exercised at the next
consumer pin bump, which is also where the first real unresolvable finding will come from.

## Not done

- No live ruleset read, so an actor that exists **live but is declared nowhere** is still uncovered
  (#262's other half) — said out loud in the fragment, the README and the CHANGELOG.
- The fifth `/apps/` family (branch-protection `push_restrictions`, `review_dismissal_allowances`,
  `bypass_pull_request_allowances`, `bypass_force_push_allowances`) is not covered; `vig-os` declares
  none. Four lines and a site-table row each when it does.
- `app-actors.json` is written for the run and for downstream tooling but uploaded nowhere.
- One unresolvable slug declared at seven sites renders seven rows; correct, and left verbose.
- ADR-0007:148-150 is not edited here — that is #268.
- `template/`'s caller workflow is unchanged (it deletes the `paths:` filter anyway); only its
  allow-list comment gained the `[[app_actor]]` shape.
