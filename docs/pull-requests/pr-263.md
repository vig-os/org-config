# [PR 263](https://github.com/vig-os/org-config/pull/263) fix(docs): App grant needs Organization Members Read & write to apply a team

## What

`docs/runbooks/github-app.md` recorded **Organization → Members: Read**, which is enough to *plan* a
team and not enough to *apply* one. The row now reads **Read & write**, the prose bullet records the
live finding, and a new `#### Read path vs apply path` subsection writes down the general audit the
bug triggered.

## Why

`POST /orgs/{org}/teams` needs Members **write**. The first downstream org to declare a team got a
green plan, a merge, then `403 Resource not accessible by integration` at apply — the least helpful
moment, and one the error text gives no route out of, because the remedy is a UI-only App change
plus a per-installation approval.

The row was the verified outcome of the #16 spike, which enumerated the `import` / `plan --no-web-ui`
**read** path only. Not a regression — a hole that methodology could not see, and the first org to
declare a team fell into it.

## The approval policy (the part that is a decision, not a fact)

The runbook does **not** tell every org to approve the widened level. `Read & write` is what the App
declares; an installation takes it **when that org declares its first team**. An org carrying
`teams: []` — `vig-os` itself — keeps its installation on **Read** as least privilege, because
Members write is not confined to teams: it also grants `PUT /orgs/{org}/memberships/{username}`
(which sets `role`, so it can promote a member to admin), `DELETE /orgs/{org}/members/{username}` and
`POST /orgs/{org}/invitations` — inviting, promoting and removing owners, none of which Organization
→ Administration write includes. The "existing installations must approve" mechanics stay: an App
edit updates the App, not its installations.

## Also in this PR

- **Corrected the Organization → Custom properties `Why` cell**, which still claimed the property
  schema is written at apply. The same audit shows a *schema* write needs **Admin**; the Access level
  stays `Read & write` by decision, and the gap is named in the new subsection. Leaving a table cell
  asserting the wrong level is exactly the defect this PR exists to fix.
- **Environments trip-wire at the pin comment**: a base-template bump that introduces `newEnvSecret`
  / `newEnvVariable` needs a Repository → Environments grant the App does not hold. The literal pin
  lives in `otterdog.json`, which is JSON and cannot carry a comment, so the note sits on
  `justfile.project`'s pin comment (the file that already records the "stays at v0.13.1 by decision"
  rationale) as well as in the runbook and the CHANGELOG.

## Deliberately NOT done

- **No App or installation change.** The App already declares `members: write`; `exo-pet` has already
  approved it. `vig-os`'s installation is left on `read` on purpose (above).
- **No pre-emptive widening** of Custom properties → Admin, Contents → write, or adding Environments.
  Each is documented with its trigger instead; the runbook's own rule is to widen only on proven
  need, and Contents write in particular would mean push access to every file in every repo.
- **`docs/issues/issue-1.md`** still says "Members (read)" — archival record, left alone per the #248
  precedent.
- No engine, workflow, jsonnet or template change; `template/README.md` links to this runbook rather
  than mirroring the table, and a *new* installation takes the App's current set automatically.
