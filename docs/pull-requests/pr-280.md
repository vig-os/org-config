# [PR 280](https://github.com/vig-os/org-config/pull/280) fix(config): declare devkit-smoke-test's commit-app environment

Declares the live-but-undeclared `commit-app` deployment environment on `devkit-smoke-test`, which the drift sweep flagged as a delete (#279, apply run [36226330674](https://github.com/vig-os/org-config/actions/runs/36226330674)):

```text
  - remove environment[name="commit-app", repository=devkit-smoke-test] {
    - branch_policies          = ["dev", "main", "release/*"],
    - deployment_branch_policy = "selected"
    - name                     = "commit-app"
    - prevent_self_review      = false
    - reviewers                = []
    - wait_timer               = 0
  - }
```

The environment is the live-proof harness for devkit's opt-in `DEVKIT_COMMIT_APP_ENVIRONMENT` knob ([vig-os/devkit#1710](https://github.com/vig-os/devkit/issues/1710), shipped to `dev` in [vig-os/devkit#1724](https://github.com/vig-os/devkit/pull/1724)): the knob binds the commit-App token-minting jobs to a deployment environment so the `COMMIT_APP_*` credentials can sit behind a deployment branch policy. That policy — not the job — is then the control that refuses an out-of-policy branch. `main` + `release/*` + `dev` is what devkit's migration guide prescribes for a gitflow repo, and it is exactly what is live.

Two omissions are deliberate and recorded in the inline comment:

- **No secrets.** The knob is not in a devkit release yet (latest is 1.16.0); the harness proves the binding, not a real mint.
- **No reviewers.** A reviewer gate here would add a second approval to devkit's single-approval release train (#167).

`wait_timer` and `prevent_self_review` stay unset — their otterdog defaults (`0`, `false`) already match live.

## Why declare rather than delete or allowlist

The environment *is* the control the devkit knob exists to provide, so deleting it would revert the capability under test and leave the next smoke run without the branch-policy gate it is meant to prove. An allowlist entry was also rejected: `drift-allowlist.toml` is for resources deliberately kept out of the config, and this one is ordinary, modelled, declarable config — an allowlist row would suppress the signal while leaving the resource undefended against a future `--delete-resources` apply. Adopting it into the jsonnet is the option that both silences the diff and puts the resource under config control, which is the ADR-0002 "adopt into config" path.

## What changes live

**Nothing** for the environment itself — the declaration matches the live object field for field, so the proposed delete simply disappears from the plan and apply has nothing to write. Verified against this PR's own `Plan` check ([job log](https://github.com/vig-os/org-config/actions/runs/36233355428/job/108380556732)), all-zeros:

```text
  Plan: 0 to add, 0 to change, 0 to delete.
```

## No drift-layer defect

The detection was correct and timely: the environment was created live at 2026-09-25T19:29:47Z, *after* that day's drift sweep had already run, so the first sweep that could see it was the 2026-09-26 run — which opened #279 on its first observation. Nothing to fix in the drift layer; this is the human-decision half of the issue-only loop working as designed.

Closes #279
