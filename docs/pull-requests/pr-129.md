# [PR 129](https://github.com/vig-os/org-config/pull/129) chore(config): reference status-check apps by slug, not numeric id

Fixes #128.

GitHub's `/apps/{app_slug}` endpoint stopped tolerating numeric ids between the last green apply (2026-08-07 16:35Z) and the #127 apply failure (2026-08-08 07:24Z): `GET /apps/15368` now returns 404 while `GET /apps/github-actions` returns the same app (id 15368, verified by direct probe). otterdog's ruleset **patch** path resolves the app node id from the prefix before `:` in each status check (`models/ruleset.py` → `app_client.get_app_ids` → `GET /apps/{slug}`), so every `'15368:'`-prefixed entry now breaks any apply that patches a ruleset. The **plan** path doesn't resolve node ids, which is why #127's PR checks were green.

Change: all 18 `'15368:<context>'` status-check entries → `'github-actions:<context>'`. Since the slug resolves to the same integration id and live values are id-based, otterdog computes no diff beyond the still-pending #127 change (devkit-smoke-test Main protection review count 0→1), which this apply should finally land.

The un-prefixed `nix flake check` entry under the legacy `branch_protection_rules` (devkit-upgrade era) is a different serialization path and is left as is.

Validation: `just validate` green (jsonnetfmt OK, otterdog 0 errors).
