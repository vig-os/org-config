# [PR 264](https://github.com/vig-os/org-config/pull/264) fix(controls): refuse a truncated list read instead of asserting a shorter set

## What

`get_json()` — the generic read every `unmanaged-controls.toml` row asserts against — issued one GET, sent no `per_page`, and discarded the response headers, `Link: …; rel="next"` included. Since #205 a row may project over a list (`[].name`, `[].context`, `[].permissions.push`) and compare the result as a **set**, so under GitHub's default page size of 30 a row asserted page one as if it were the whole collection.

Two changes, both stdlib-only:

1. `get_json` asks for **`per_page=100`** unless the path already names a page size (joined with `&` when a query string is present, `?` when not; a `per_page` appearing only as a *value* does not count).
2. It **refuses** a response whose `Link` header advertises a further page, raising the new `TruncatedResponseError`.

## Why

The failure mode was the bad one. A truncated list does not raise and does not degrade to `MISSING` — it compares as a **shorter set**, exactly what `select_path`'s own docstring already called unacceptable. Over the page boundary a row either manufactures drift or, where `expect` was itself seeded from a truncated read, **reads permanently clean while the live collection diverges underneath it**. The spike reproduced precisely that: with the guard disabled, a `compare = "set"` row whose `expect` was the 30 values page one carries reported `statuses: ['OK'] / clean: 1 unresolved: 0`.

`TruncatedResponseError` subclasses `ApiError` and carries status **200** — the request succeeded, only its *completeness* failed — so it inherits the per-row degradation path with no new plumbing: the row lands in `unresolved_fingerprints`, its issue is left exactly as it was, and `--controls-report` shows `UNRESOLVED` with `actual = truncated` and a note naming the endpoint. Reusing `UNRESOLVED` rather than adding a verdict is deliberate: "the transport could not resolve the whole collection" is the same contract as "the row could not be read", and a new status would make every consumer learn a value that changes no behaviour.

The refusal is **unconditional**, not reserved for list-shaped rows, because the transport cannot see the row's path — making it conditional would push `compare`/`path` down into the client (killing the dumb-transport property) or lift the `Link` header up into the pure core (a transport concern in L1, against ADR-0007). Over-refusing a scalar read costs one loud, self-limiting degraded row; under-refusing a projection asserts a lie.

`_request` keeps its body-only signature and delegates to a new `_send` that also returns the `Link` header, so the four dedicated paginated helpers (`list_open_drift_issues`, `list_org_repos`, `list_org_secrets`, `list_org_secret_repositories`) and every write method are untouched and never see the guard. Endpoint memoization is unchanged: `_evaluate_control` keys its cache on the row's *resolved endpoint* and `get_json` rewrites the path internally.

## Blast radius — deliberately small

- **No current row changes verdict.** All **7** distinct endpoints this repo's table reads return **no `Link` header at all** at `per_page=100` today, verified read-only with `gh api -i`: `/orgs/{org}`, `/orgs/{org}/actions/permissions`, `/orgs/{org}/actions/permissions/fork-pr-contributor-approval`, `/orgs/{org}/code-security/configurations/237480`, `/repos/{org}/{repo}`, `/repos/{org}/{repo}/actions/permissions` and its `fork-pr-contributor-approval`. `/repos/{org}/{repo}/rules/branches/main?per_page=100` answers all 5 rules in one page. `per_page` on a dict endpoint is inert — GitHub ignores query parameters an endpoint does not define (verified byte-identical body for `/orgs/vig-os`).
- **`UNRESOLVED` opens no drift issue and fails no workflow.** The CLI withholds unresolved fingerprints from the controls reconcile input, they never enter `clean_fingerprints`, the row surfaces as a `::warning::` annotation and the CLI exits 0 — as `drift.yml` already documents.
- **Downstream orgs receive this only at their next engine pin bump.** `exo-pet` pins `022462b # v1.4.0`; its list rows (three over `/orgs/{org}/teams/exopet/repos`, nine collaborator rows, outside collaborators, installations) are all far inside one page — 8 team repos, 12 installations — and the rows that already spell `per_page=100` are left untouched by `_with_max_page_size`. Re-check at that pin bump.

## Deliberately NOT done

- **Option 3, real pagination inside `get_json`** — deferred. Merging pages generically would need to know whether a body is a root list (`/rules/branches/{branch}`, `/orgs/{org}/repos`) or an envelope keyed per endpoint (`secrets`, `repositories`, `check_runs`, …) — exactly the per-endpoint knowledge the dedicated list methods already encode. No row needs more than 100 elements today; the refusal turns that ceiling into a loud limit naming the endpoint, which is the trigger to do option 3 when a row genuinely needs it.
- **The four dedicated list helpers** still stop on `len(batch) < 100` rather than on the absence of `rel="next"`. Out of scope here and tracked separately in #260 — `list_org_repos` is the stronger instance, since a truncation there deletes rows rather than degrading one.
