## Unreleased

### Added

- **Reusable `workflow_call` interfaces + downstream template skeleton** ([#24](https://github.com/vig-os/org-config/issues/24)) — `plan.yml`, `apply.yml`, and `drift.yml` now ALSO expose `workflow_call` (callable cross-org because this repo is public) so a downstream org's private `org-config` repo, created from the new `template/` skeleton, can consume the engine pinned to an exact tag/SHA (ADR-0006). Each takes `org_github_id`/`config_repo` inputs (defaulting to `vig-os`/`org-config`) that parameterize the `otterdog` org arg, the App-token `owner`, the drift `--org`/`--config-jsonnet` path, and the narrowed issue-ops token scope; the App credentials (and `apply`'s optional `SOPS_AGE_KEY`) are declared as `workflow_call` secrets **named identically to this repo's bootstrap Actions secrets**, so every credential reference is byte-identical whether reached on this repo's own events or via a call. Byte-compatibility for vig-os's own triggers is total: on a non-`workflow_call` event the `inputs` context is empty, so each `inputs.X || 'default'` resolves to the vig-os value and each credential falls through to the repo secret unchanged; the `owner`/org selectors resolve to `vig-os`; the `if:` repo-identity guards generalize from the `vig-os/org-config` literal to `format('{0}/{1}', …)` with the same truth value; and the concurrency groups gain an org suffix that is EMPTY on this repo's events (`plan`'s per-PR group and the shared `otterdog-mutate` mutation group stay literally unchanged, so `drift.yml`/`testbed-e2e.yml` keep sharing it) while a downstream caller serializes under `otterdog-mutate-<org>`. Org selectors flow into `run:` blocks via `env:` only (never inline `${{ }}`), keeping the zizmor template-injection surface closed. New `template/` skeleton (inert as live config — see below): a minimal placeholder `otterdog.json`, an `otterdog/README.md` layout note for `otterdog/<org>/<org>.jsonnet`, thin ~5-line caller workflows for plan/apply/drift with a clearly-marked `@vX.Y.Z` pin to replace (and a SHA-pin option noted for medtech), a `.sops.yaml` placeholder, a `drift-allowlist.toml` starter, a CODEOWNERS placeholder, a `renovate.json` that bumps the engine pin, and a `README.md` onboarding runbook (create private repo from template -> install App -> set 3 secrets -> import -> plan-first/read-only posture for Free orgs -> apply after the Team upgrade). `template/` is not picked up by this repo's own CI/hooks as live config: the L0 `validate` recipe's `find otterdog` and the `jsonnetfmt` hook's `^otterdog/` glob are root-anchored (never reach `template/otterdog/`); `actionlint` and `zizmor` scan only root `.github/workflows` (the template callers under `template/.github/workflows/` are never linted as live workflows); and the plan/apply workflows' `paths:` filters (`otterdog.json`, `otterdog/**`, `secrets/**`, `.sops.yaml`) are root-anchored so template copies never trigger a run. Marking the repo as a GitHub template is a one-time `gh` API action performed separately (out of scope for this change).
- **Inventory sweep: undeclared repos + `managed: false` allow-list** ([#21](https://github.com/vig-os/org-config/issues/21)): `src/drift_layer/inventory.py` compares the live org repo inventory (injected client, `GET /orgs/{org}/repos`) against the declared set extracted from the committed otterdog config — a pure, offline, literal read of every `orgs.newRepo('<name>')` (verified equal to a full go-jsonnet evaluation of the same file; keeps the L1 core native-lib-free). A live-but-undeclared repo and a declared-but-absent repo each become a `DriftRecord` (fingerprint namespaces `repository-inventory:<name>` / `repository-inventory-missing:<name>`, distinct titles) feeding the SAME dedup'd `drift`+`critical` reconcile/issue lifecycle (ADR-0002), on an `inventory`-labelled issue population. `drift-allowlist.toml` gains a `[[unmanaged]]` section (the `managed: false` allow-list): repos named there stay visible/reviewed but are exempt from undeclared-repo and settings-reconciliation flagging in both directions. Wired into the `drift-layer` CLI and `drift.yml` as a leg after the plan leg (org-repo read on the full plan token, issue writes on the `issues:write`-narrowed token); a sweep failure degrades explicitly in-tool — plan-drift reconciliation still runs and inventory issues are left untouched (never phantom-closed). Also fixes Python ignores: `__pycache__/`/caches now sit in the git-read root `.gitignore` (devkit only folds `.gitignore.project` in on regeneration).
- **Secrets as code: SOPS/age encrypt/apply pipeline** ([#22](https://github.com/vig-os/org-config/issues/22)) — `.sops.yaml` creation rules encrypt `secrets/*.yaml` (values only; keys stay reviewable) to the `vig-os` age recipient, with header-documented rotation (re-encrypt via PR + re-apply; `sops updatekeys` for key rotation) and the ADR-0003 bootstrap exclusions (the App private key and the age private key are never SOPS-managed). `secrets/vig-os.yaml` commits one canary (`ORG_CONFIG_CANARY`) as age ciphertext. `apply.yml` gains an in-memory decrypt-at-apply bridge (triggered by `secrets/**`/`.sops.yaml` changes): a pinned checksum-verified `sops` decrypts each value and loads it into an ephemeral, passphrase-less GPG-backed `pass` store under `runner.temp`, which otterdog resolves for any secret declared `value: 'pass:org-config/<NAME>'` — its only offline secret-value provider (the `env` provider raises on values). Values are `::add-mask::`-ed and never echoed; the GPG key is transport-only and adds no bootstrap secret. New `docs/runbooks/secrets.md` covers creation, rotation, and what never goes here.
- **Testbed repo + L3 mutation E2E harness** ([#23](https://github.com/vig-os/org-config/issues/23)) — declares the sacrificial public `org-config-testbed` repo in `otterdog/vig-os/vig-os.jsonnet` (description-only override; the vendored `newRepo` seeds no lists, so the evaluated config is drift-free-by-construction) and adds `.github/workflows/testbed-e2e.yml`: a scheduled (weekly Mon 05:23 UTC, away from drift's 03:17) + `workflow_dispatch` harness that joins the `otterdog-mutate` concurrency group (`cancel-in-progress: false`) and dogfoods the real drift path (ADR-0007 L3, never per-PR). It skips gracefully until the first apply creates the testbed, then induces out-of-band description drift via a full App token, runs the in-house `drift-layer`, and asserts exactly one `drift`+`critical` issue → update-not-duplicate on rerun → auto-close on revert, with an always-run idempotent cleanup and a PASS/FAIL summary carrying per-assertion evidence. An opt-in (default-OFF) stray-repo leg create/deletes `org-config-testbed-stray` and asserts the sweep issue, degrading gracefully until the sweep (#21) is deployed; repo deletion is covered by the App's Administration:write.
- **Strict-drift layer + scheduled reconciliation** ([#20](https://github.com/vig-os/org-config/issues/20))
  - `src/drift_layer/`: the in-house strict-drift core (ADR-0002/0007) — a pure-function pipeline with the GitHub client injected at the edge. `parser.py` turns `otterdog plan --local --no-web-ui` output into one `DriftRecord` per resource-level divergence (owning otterdog's `+`/`~`/`!`/`-` block syntax and the `Plan: X to add, Y to change, Z to delete` trailer, tolerating the uv/runner preamble); `allowlist.py` marks config-driven expected drift (`drift-allowlist.toml`) so known artifacts never open issues; `reconcile.py` diffs records against live issues into open/update/close actions; `github_client.py` is the stdlib-only REST edge (a `GitHubClient` Protocol tests fake).
  - Lifecycle (ADR-0002): exactly one deduplicated `drift`+`critical` issue per divergence, keyed by a stable per-resource fingerprint in a hidden `<!-- drift-fingerprint: … -->` marker; recurrence updates the existing issue in place (never duplicates) and adds a timestamped comment; resolution closes it with a comment. Title convention `Drift: <resource>`.
  - `drift-layer` CLI (`uv run drift-layer` / `python -m drift_layer`) with `--dry-run`; issues token read from `$GITHUB_TOKEN`.
  - `.github/workflows/drift.yml`: scheduled (daily 03:17 UTC) + `workflow_dispatch`; joins the static `otterdog-mutate` concurrency group (`cancel-in-progress: false`) so drift and apply never race; full org-wide App token for the read-only plan leg, a second `issues: write`-narrowed token for the issue-ops leg (ADR-0004/0007 least-privilege).
  - TDD: `tests/` with recorded plan fixtures (PR #41 ECA drift / 17 changes, PR #42 vs-dolt-only, synthetic empty and mixed-symbols plans) drives the L1 core. Repo becomes a `uv` project: `pyproject.toml` (`org-config-drift`, `requires-python >=3.12`, ruff + pytest, `src/` layout) + `uv.lock`; the `justfile.project` pytest/lint recipes activate.
- **Apply-on-merge workflow** ([#19](https://github.com/vig-os/org-config/issues/19))
  - `.github/workflows/apply.yml` runs a mutating `otterdog apply --local --no-web-ui --force` of the committed config against live `vig-os` on `push` to `dev` touching `otterdog.json`/`otterdog/**` (engine/workflow edits carry no config delta and are excluded from `paths:`), plus `workflow_dispatch` for reruns (ADR-0007 split cadence: config applies from `dev` on merge).
  - The job runs in the `production` environment (required reviewer `c-vigo`, `dev`-only deployment branch policy): entering it pauses the run until the deployment is approved — the designed human gate before any write token touches live `vig-os`. `push` fires only on this repo (never a fork), so org-admin credentials are never exposed to fork code; an explicit `github.repository` guard asserts this.
  - A static `otterdog-mutate` concurrency group with `cancel-in-progress: false` serializes all mutations without cancelling mid-apply; the future scheduled drift workflow (#20/#21) must reuse the same group so apply-vs-drift never races.
  - Uses the full App installation token (ADR-0004 Corrections) with two scoped, justified `github-app` inline zizmor ignores; least-privilege `permissions: contents: read`; `persist-credentials: false` checkout.
  - `--force` is mandatory for unattended apply (otterdog 1.3.4 prompts and blocks on stdin otherwise); `--local` gates only the vendor re-fetch (same `_init_base_template` skip as `plan`/`validate`), so apply evaluates the exact committed tree; `--delete-resources` is omitted so absent resources are never deleted. Reports otterdog's own apply output to the job summary (truncated safely); a nonzero exit is a failed/partial mutation and reddens the job (unlike plan, mutation errors are not benign report content).
- **Plan-on-PR workflow (L2)** ([#18](https://github.com/vig-os/org-config/issues/18))

  - Uses the full App installation token (ADR-0004 Corrections) with two scoped, justified `github-app` inline zizmor ignores; least-privilege `permissions:` (`contents: read`, `pull-requests: write`); per-PR concurrency with cancel-in-progress.
  - Posts the plan as a marker-keyed PR comment updated in place (truncated safely, with run link) and to the job summary; the job fails only on validation/auth/harness errors — drift (exit 0) is report content, not failure. A fixed footnote flags the expected benign `vs-dolt` `code_scanning_default_languages` drift.

### Fixed

- **Scheduled workflows check out trunk `dev` so they operate on current config post-release** ([#23](https://github.com/vig-os/org-config/issues/23)): `drift.yml` and `testbed-e2e.yml` now pin `actions/checkout` to `ref: dev`. GitHub registers `schedule`/`workflow_dispatch` triggers only from the default branch (`main`, which advances only via a release), so both workflows are inert until the first release (v1.0.0) promotes them onto `main` — at which point the workflow FILE is main's (released) but the config, `src/drift_layer/` code, `drift-allowlist.toml`, and the `justfile.project` otterdog pin it reads all still live on `dev` between releases; without the explicit `ref` the run would take the `main` triggering ref and scan stale released config. Executing dev's Python from a main-pinned workflow is trust-equivalent to the existing dev-push `apply` (both gated by the same PR-to-`dev` review) and opens no new injection surface; each workflow header now documents the registration/activation model (dispatch also only works once the file is on `main`) and the checkout-ref rationale. `apply.yml`/`plan.yml` need no such fix — their `push`/`pull_request`-on-`dev` triggers make the triggering ref already `dev`. Also documents the repository-level **Custom properties: Read & write** App permission in `docs/runbooks/github-app.md`: org-level Custom properties covers only the schema, so setting repo custom-property VALUES (the `type` property) 403s without the repo-level grant — verified 2026-07-17 (apply run `29584038705`).
- **Normalize the base template's ECA status check out of all rulesets** ([#17](https://github.com/vig-os/org-config/issues/17)): the first live plan (PR #41, 17 changes) showed `+ "eclipse-eca-validation:eclipsefdn/eca"` on every ruleset with status checks — `newStatusChecks()`/`newBranchProtectionRule()` seed that Eclipse default and the imported config's `status_checks+:` appends inherited it (same class as the `custom_properties` `null + array` fix). All 15 ruleset `status_checks` lists and tessera's branch-protection `required_status_checks` are now plain overrides expressing live state exactly (cross-checked read-only against `gh api .../rulesets`); no other template-seeded injection remains (all other appended fields have empty template defaults). The only remaining plan line is the known benign `vs-dolt` `code_scanning_default_languages` artifact (otterdog's live read filters out `javascript-typescript` while its schema rejects the split values — upstream inconsistency, already baselined in plan.yml's footnote).
