## Unreleased

### Added

- **`plan` now checks every declared App slug against the two calls otterdog makes and the plan diff does not** ([#259](https://github.com/vig-os/org-config/issues/259)): a new `drift-layer --app-actors-report` mode, wired into `plan.yml` between the otterdog run and the report build, and folded into the marker-upserted PR comment and the job summary. Otterdog's read and write paths resolve a GitHub App differently, which is why this class of config passes review and fails on apply — the write path calls `GET /apps/{slug}` (`models/ruleset.py:649`, `:177-189`, `models/branch_protection_rule.py:348`, `models/environment.py:244`), while the read path never does, mapping `actor_id` back to a slug from `GET /orgs/{org}/installations` instead. The mode runs **two independent** checks with the installation token the job already minted. First, `GET /apps/{slug}` per declared slug: a `403`/`404` means `apply` will fail on any add or change of that resource, including one already live, because a ruleset patch re-sends the whole bypass list — the [#256](https://github.com/vig-os/org-config/issues/256) case. Three of the four sites abort the patch and the fourth, an environment reviewer, is caught and **skipped** (`providers/github/__init__.py:502-506`), leaving a protection that was never written, so the report separates them. Second, membership of the org's App installations, for the two sites whose read path needs it: a declared App the org has no installation for is dropped outright as a bypass actor (`models/ruleset.py:541-548`) or read back in its numeric `<id>:context` form as a status check (`:145-151`), so `plan` proposes the same change on every run and `apply` never converges — the detection half of [#262](https://github.com/vig-os/org-config/issues/262). That second check is deliberately **not** applied to branch-protection status checks or environment reviewers: an unprefixed branch-protection check resolves to the implicit `github-actions`, a first-party App that is never an org installation and that this org's own `tessera` rules declare and plan clean — asking for an installation there would fire on green config, the exact failure mode rejected when #256 was spiked. Both checks read the **declared** config only: an actor that exists live but is declared nowhere needs a live ruleset read (which a Free-plan private repo refuses anyway) and is not covered, and the report says so. Declared actors are extracted token-free — `plan.yml` evaluates the committed jsonnet with otterdog's own `jsonnet_evaluate_file`, the exact call `GitHubOrganization.load_from_file` makes (`models/github_organization.py:536`), verified identical to a `go-jsonnet` evaluation of the same file — so only the two reads are credentialed. The finding is **advisory**: the mode always exits 0 — it catches every exception itself rather than relying on the workflow wrapper — no new step can fail the job, and `steps.plan.outputs.rc` keeps its meaning, so *Fail on plan error* still means config/auth/harness and never drift. That posture is not a convenience: `Plan` is not a required check *in this repository* (ADR-0007 Axis D, [#236](https://github.com/vig-os/org-config/issues/236)), but the only consumer org makes its plan context a required check on `main` and ships no `paths:` filter for that reason ([#268](https://github.com/vig-os/org-config/issues/268)), so every step added to this reusable workflow sits on a downstream merge gate for every pull request — each of the three new steps is therefore guarded, `continue-on-error: true` and `if:`-gated on the guard's output, and the comment body now reserves the fragment's bytes inside the 55000-byte budget so an over-long body can never 422 the upsert and fail that gate. A read that fails for any other reason (401, 0, 5xx, a truncated page) is reported as **not checked**, never as a finding — including a rate-limit `403`, which GitHub renders identically to a permission `403` and which the step immediately after a full org read on the same token is the likeliest to hit: `ApiError` now carries the response headers, and a `403` with `retry-after` or `x-ratelimit-remaining: 0` is classified as undetermined rather than as "`apply` will fail on these". A slug that is unresolvable **by design** — the standard case is a private App owned by a sibling org, on a ruleset that is already live and correct and unrepairable until upstream [#772](https://github.com/eclipse-csi/otterdog/issues/772) lands — takes an `[[app_actor]]` entry (slug + reason) in `drift-allowlist.toml`, the third section of the same governance file as `[[expected]]` and `[[unmanaged]]`: the check still names the slug on every run, under *known and suppressed* with its reason, so the suppression is reviewed rather than silent and the finding list keeps meaning something. `vig-os` adds no entry — all three slugs it declares resolve — and the shape is documented in `template/drift-allowlist.toml` for the org that will need one. `plan.yml`'s own `paths:` filter gains `src/drift_layer/**`, `pyproject.toml` and `drift-allowlist.toml`, because the engine's source now selects part of what the plan report says and a change to it would otherwise ship with no plan run at all (the [#230](https://github.com/vig-os/org-config/issues/230) lesson). Downstream callers inherit the step on their next engine pin bump with no change to their caller workflow — `plan.yml` gains the `.drift-engine` checkout `drift.yml` already uses ([#169](https://github.com/vig-os/org-config/issues/169)), and `template/` changes only in that allow-list comment. **Proof limits, stated:** this PR's own plan run proves the green path only — three declared slugs all `200`, the org's installations read whole, `github-actions` correctly not flagged — while the unresolvable, suppressed and rate-limited paths are unit-tested, and the downstream `.drift-engine` checkout is first exercised at the next consumer pin bump.

### Changed

- **"Otterdog models rulesets" is corrected — it models the ruleset *object*, not every parameter inside a rule, and the merge-method policy is owned by the repo settings** ([#246](https://github.com/vig-os/org-config/issues/246)): two claims in this repo were over-broad in the same direction. `unmanaged-controls.toml`'s "Repository ruleset internals" comment argued that a row for a public repo "would duplicate a modelled control, which is exactly what this table is not for", and `README.md` enumerated the controls Otterdog **cannot model** without naming ruleset rule parameters at all — so a reader concluded that anything inside a ruleset on a public repo is plan-diffed. It is not. Otterdog (every version through 1.6.1, the current pin included) does not model the `allowed_merge_methods` parameter of a `pull_request` rule, and an unmodelled *rule* parameter is worse than merely invisible: `plan` shows no diff because there is no model field, and `apply` re-`PUT`s the rule **without** it, so GitHub's default-on-omit — all three merge methods — is restored every time the ruleset is touched. On **2026-08-08** one routine apply by the org-config App did exactly that to **ten rulesets across four repos** (`commit-action`, `devkit`, `sync-issues-action` Dev/Main/Release plus `org-config` Main), each dropping a hand-set `["merge"]`, and it went unnoticed for six weeks; every row is provable through `GET /repos/{org}/{repo}/rulesets/{id}/history/{version}` — `org-config` Main protection is the cleanest, a human version (43742326, 2026-07-20) carrying `["merge"]` followed directly by a bot version (45947063) carrying all three, with no config change between them. This repo had already recorded the care that was wasted: [`docs/pull-requests/pr-117.md`](docs/pull-requests/pr-117.md) and [`pr-119.md`](docs/pull-requests/pr-119.md) document hand-`PUT`s on 2026-08-07 that rebuilt each payload from a fresh `GET` precisely so `allowed_merge_methods` passed through verbatim — wiped the next morning. Filed upstream as [eclipse-csi/otterdog#768](https://github.com/eclipse-csi/otterdog/issues/768). The **decision** now documented in both files: **repo merge settings own the merge-method policy**. `allow_merge_commit` / `allow_squash_merge` / `allow_rebase_merge` *are* modelled, are declared once in `otterdog/vig-os/house-defaults.libsonnet` (`houseMergePolicy` — merge commits only), and are therefore plan-diffed on every config PR and drift-guarded daily; all four affected repos sit on that policy by construction, so merge-only is still enforced where a contributor meets it, and the widened ruleset parameter cannot offer a button the repo settings do not expose. The ruleset-level parameter stays at the platform default **by decision**, not by neglect. Re-narrowing the ten rulesets by hand is rejected as permanent toil (the next apply re-widens them, with no signal), and an `unmanaged-control` row asserting `["merge"]` is rejected for a subtler reason worth stating: the row would be *correct* and would open an issue every time this engine's own apply re-widened the value — self-inflicted drift noise over a dual source of truth for one policy, with the table asserting a state the tool actively fights. The one capability genuinely deferred is per-branch merge-method granularity, which nothing here uses. The neighbouring unmodelled parameter `require_extra_approval_for_unattributed_changes` needs no action and the comment says so: GitHub's default-on-omit is evidently `true` (it reads `true` in every version above, human- and bot-written alike), which is the value we want. The exit criterion is written into both files — when the [ADR-0005](docs/adr/0005-repo-tooling.md) otterdog pin reaches a version fixing #768, `allowed_merge_methods` gets declared in the jsonnet as ordinary config, matching **each repo's declared merge policy** rather than a blanket `["merge"]` mixin: the house policy is merge commits only, but `h5v`, `nvd-mirror`, `qms`, `qx`, `vigos-mvp` and `vs-dolt` carry `orgs.legacyMergePolicy` and `org-config-testbed` carries `orgs.upstreamMergePolicy` (`otterdog/vig-os/vig-os.jsonnet`), so one blanket declaration would silently narrow any of them that later gains a ruleset — the same class of unnoticed narrowing this entry exists to record, only self-inflicted. Today the distinction is latent, because every ruleset-carrying repo (`commit-action`, `devkit`, `devkit-smoke-test`, `org-config`, `scitadel`, `sync-issues-action`) sits on the house policy; the declaration must still be derived per repo, not assumed. #246 stays open as that tracker. Documentation only: no jsonnet, ruleset, workflow or table-row change, and `--controls-report` is unchanged.

- **The `template/` starter no longer tells a downstream org that Otterdog cannot read its private repositories' rulesets** ([#248](https://github.com/vig-os/org-config/issues/248)): three places still asserted the read gate that [#225](https://github.com/vig-os/org-config/issues/225) retired when it moved the pin to otterdog **1.5.0** for engine `v1.4.0`. `template/unmanaged-controls.toml` — the file every downstream org copies — opened its ruleset section with *"Otterdog cannot read live rulesets on a private repo below Enterprise, so on a private Team-plan org they are precisely the controls with no other detector"* and then recommended "the two rows worth holding"; `README.md` said ruleset internals are assertable *"which matters most on a private repo where Otterdog cannot read rulesets at all"*; and this repo's own `unmanaged-controls.toml` held the capability *"for downstream orgs on Team/Enterprise, whose private repos otterdog cannot read"*. Upstream [eclipse-csi/otterdog#731](https://github.com/eclipse-csi/otterdog/pull/731) removed the plan-and-visibility gate from **both** ruleset read paths — which is precisely what closed [#107](https://github.com/vig-os/org-config/issues/107) / [upstream #729](https://github.com/eclipse-csi/otterdog/issues/729) and released the [#205](https://github.com/vig-os/org-config/issues/205) downstream conversions — so repository rulesets are read on every plan tier and both repo visibilities, the fields Otterdog's schema models are plan-diffed everywhere, and a row asserting one now *duplicates a modelled control*: the template was recommending exactly what the shipped table's own comment rejects. The README already recorded the correction under "Known limitations", so the repo contradicted itself. Each passage is rewritten to say when a row is warranted rather than which repos are unreadable: a rule parameter Otterdog does not model ([#246](https://github.com/vig-os/org-config/issues/246), [upstream #768](https://github.com/eclipse-csi/otterdog/issues/768)), a ruleset deliberately kept out of the config, and — the stronger case now — **organization**-level rulesets, which #731 made readable but which `GitHubOrganization.validate()` still refuses to declare below Enterprise ([upstream #763](https://github.com/eclipse-csi/otterdog/issues/763)), leaving them hand-managed with a row here as their only detector. The two example rows stay exactly as they were, re-labelled as the *shape* a row takes rather than rows to hold by default, so a consumer reading the starter still learns the `/repos/{org}/{repo}/rules/branches/{branch}` form and the `compare = "set"` semantics. Untouched by design: `docs/issues/*.md` and `docs/pull-requests/*.md`, which are archival records of what was true when written; `template/README.md`'s migration note, which already says "previously unreadable"; and the `otterdog-defaults` `v0.13.1` pin, which is held for the `max_cache_size_gb` HTTP 402 reason and has nothing to do with reads. Documentation and template comments only — no row, endpoint, engine, workflow or config change, and `--controls-report` is unchanged.

- **Renovate proposes the otterdog pin bump; a human still adopts it** ([#250](https://github.com/vig-os/org-config/issues/250)): the [ADR-0005](docs/adr/0005-repo-tooling.md) `otterdog_version` pin was moved entirely by hand across **five** literals, because `renovate.json` enabled only `github-actions`, `pep621` and `npm` — none of which matches a bare Just variable or a workflow input `default:` — and defined no `customManagers`. That was recorded as an ADR-0005 correction in [#225](https://github.com/vig-os/org-config/issues/225) after the 1.5.0 bump had to be authored literal by literal, and the failure mode it predicts is not hypothetical: the 1.4.0 bump (`818e1f8`) missed `template/.github/workflows/import.yml` outright ([#164](https://github.com/vig-os/org-config/issues/164) item 7), leaving a template consumer importing on one otterdog and planning on another. `renovate.json` now enables `custom.regex` and defines one manager that keys off a `# renovate: datasource=pypi depName=otterdog` marker placed directly above each literal — `justfile.project` (the SSoT) plus the `workflow_call` defaults of `.github/workflows/{plan,apply,drift}.yml` plus `template/.github/workflows/import.yml` — so all five carry one `depName` and move in a **single** pull request. The **comment-marker** form was chosen over a bare pattern deliberately: those workflow files mention `otterdog_version` in prose as well as as an input key (`plan.yml` even quotes a past bump, "1.4.0 -> 1.5.0", in a comment), so a regex anchored on the key name alone is one edit away from silently matching the wrong line — and silence is precisely this pin's historical failure mode. **What is automated is the editing, not the adopting.** The rule sets `automerge: false`, requests review, and labels the PR `area:ci`; `plan` runs on it because [#230](https://github.com/vig-os/org-config/issues/230) added `justfile.project` to the workflow's `paths:` filter, so the empty-plan evidence that #225 had to dispatch by hand now arrives on the PR for the reviewer to read. **Stated precisely, because it would be easy to over-read as a hard gate:** this is a *requested* review, not an enforced one, and no ruleset can make it enforced here. `Main protection` grants `OrganizationAdmin` an `always` bypass, so the maintainer bypasses every rule in it when merging; `required_approving_review_count` is `0` by decision ([#167](https://github.com/vig-os/org-config/issues/167)) because a sole maintainer cannot self-approve, so raising it would block every human PR in the repo rather than this one bot PR; and `require_extra_approval_for_unattributed_changes: true` does not reach bot PRs at all — the eight most recently merged `app/renovate` PRs (#207, #208, #212, #216–#218, #221, #222) all report an empty `reviewDecision`. The only mechanical guard is therefore `tests/test_otterdog_pin.py`, which grows three checks beyond its existing mirror-equality assertions: every pin site carries its marker (a deleted marker silently drops that site from Renovate and restores the hand-edit failure mode), `custom.regex` stays in `enabledManagers` (an allowlist, where an omission disables the manager entirely), and — the one that makes "the regex is validated" a checked claim rather than a hope — the manager's own `matchStrings` are read out of `renovate.json`, compiled, and run against the real files, asserting exactly one match per site carrying the SSoT value. `renovate-config-validator` passes on `renovate.json`. Two exclusions are deliberate and both preserve an existing decision rather than automating past it. `otterdog.json`'s `otterdog-defaults` `base_template` pin is outside the manager's `managerFilePatterns`: it is held at `v0.13.1` because `v0.14.x` introduces `max_cache_size_gb`, whose endpoint answers `402` on a Free plan and writes a permanent `WARNING` into every `plan.txt` the drift layer parses — the two pins are not in lockstep and must not be moved by reflex. And `template/renovate.json` is **unchanged**, so no downstream org inherits a custom manager it would have to maintain; the marker shipped in `template/.github/workflows/import.yml` is read by this repo's Renovate and is inert in an instantiated consumer, which is stated in the file itself and costs nothing, since that bootstrap is dispatched once at onboarding and its pin stops mattering afterwards. Repository tooling, ADR and template comments only — no engine, plan-execution, workflow-behaviour or org-config change.

- **`tessera` can read the org App secrets its devkit scaffold mints tokens from** ([#252](https://github.com/vig-os/org-config/issues/252)): [tessera#364](https://github.com/vig-os/tessera/issues/364) adopts the devkit scaffold, whose managed `sync-issues.yml` and `devkit-upgrade.yml` mint GitHub App installation tokens from **org** secrets whose `visibility` is `selected`. `tessera` was on none of those lists, and the failure mode is silent by construction — the very trap the `DEVKIT_UPGRADE_APP_ID` comment in this config already warns about, *"its upgrade workflow fails with an empty credential and no error"*. `tessera` is added to exactly four: `COMMIT_APP_CLIENT_ID`, `COMMIT_APP_PRIVATE_KEY`, `DEVKIT_UPGRADE_APP_CLIENT_ID` and `DEVKIT_UPGRADE_APP_PRIVATE_KEY`. **Which four was derived from the scaffolded files rather than assumed**, because the ID form is per-repo and the lists deliberately differ: at devkit **1.16.0** `sync-issues.yml` reads `client-id:` with no numeric fallback, and `devkit-upgrade.yml` takes the legacy numeric `DEVKIT_UPGRADE_APP_ID` only as a fallback (`if { [ -z CLIENT_ID ] && [ -z ID_LEGACY ]; } || [ -z PRIVATE_KEY ]`), so the client-ID form alone satisfies both. `tessera` is therefore **deliberately absent** from `COMMIT_APP_ID` and `DEVKIT_UPGRADE_APP_ID` — adding it there would hand the repo a credential nothing reads and enlarge precisely the surface [#112](https://github.com/vig-os/org-config/issues/112) exists to retire. That makes `tessera` the first repo on the client-ID form **from day one**, with no numeric entry for the migration to unwind later; every other entry on those lists retires with its repo's re-scaffold, this one never needs to. The prose above each list is updated alongside it, not just the arrays: those comments enumerate which repo is on which ID form and why, and they are the only record of that reasoning — a silent list edit would leave them quietly wrong, which is the same class of error [#225](https://github.com/vig-os/org-config/issues/225) found in ADR-0005. Two further secrets appear in the scaffolded workflows and correctly need no action: `GHCR_PULL_TOKEN`, which is not an org secret, not in this config and not a repo secret anywhere — `h5v` runs the same scaffold with zero repo secrets, because it is an optional fallback for pulling the public devcontainer image that `GITHUB_TOKEN` already covers — and `CACHIX_AUTH_TOKEN`, which is declared here as a repo secret for the one repo that uses it and is optional in `ci.yml`. Config only: four `selected_repositories` arrays and the comments above them; no new secret, no value, no visibility change, and no repo, ruleset or workflow change.

- **A GitHub App bypass actor on a ruleset is documented as writable only while the engine's token can read the App** ([#256](https://github.com/vig-os/org-config/issues/256)): a downstream consumer merged a tag ruleset whose single bypass actor is a GitHub App, on a green `plan`, and the dispatched `apply` failed against the live organization with `failed retrieving app node id: … (status=403, "Resource not accessible by integration")`. Otterdog resolves an App bypass actor on the **write** path through `GET /apps/{app_slug}` and this engine authenticates as an App *installation* ([ADR-0004](docs/adr/0004-auth-model-github-app.md) Corrections), so the write succeeds only where that endpoint is readable to such a token. GitHub's own reference for `GET /apps/{app_slug}` documents no authentication requirement at all, so the boundary is stated here as an **observation**, not as a documented mechanism: probed 2026-09-25, a **public** App answers `200` to any caller, while the private App that hit this answers `404` unauthenticated, `200` to an org-owner PAT and `403` to an installation token — the status in the traceback above. The **read** path never calls it: it maps the live `actor_id` back to a slug from `GET /orgs/{org}/installations`, which is why `plan` and `drift` render the actor correctly and why the failure cannot surface on the pull request. That also explains why this organization has never hit it — the ten App bypass actors declared in `otterdog/vig-os/vig-os.jsonnet` name two **public** Apps, and installation-token applies have written both, on two different days. **Six** of the ten rulesets the apply of 2026-08-08 rewrote (the [#246](https://github.com/vig-os/org-config/issues/246) incident set) carry an App bypass actor — *Dev* and *Release* protection on `commit-action`, `devkit` and `sync-issues-action`, every one of them naming `commit-action-bot`, e.g. ruleset `18922479` still at `updated_at 2026-08-08T09:34:28+02:00` with `actor_id 2433383` intact. The three *Tag* protection rulesets that carry the other App are not in that set, so `vig-os-release-app` is evidenced separately and a day earlier: apply run `31190546346` created `devkit` *Tag protection* (`20558615`, `created_at 2026-08-07T17:11:11+02:00`) with that App as its only bypass actor, from a workflow that already minted an installation token. The limitation, the workaround and the residual gap — **detection survives, repair does not**, because a ruleset patch re-sends the whole bypass list — are now recorded in `README.md`'s *Known limitations*, beside the field in `otterdog/vig-os/vig-os.jsonnet`, and in both `unmanaged-controls.toml` comments, which record that the gap deliberately gets no control row: the plan already detects it and no row can restore a write path. The workaround documented is a **one-off `otterdog apply` run with an org-owner PAT** as `OTTERDOG_TOKEN` — an owner can read the slug, so the engine resolves it on its own code path and writes the complete payload — rather than a hand-built REST `PUT` carrying `actor_id` directly: hand-assembling a ruleset payload is exactly the operation that silently lost unmodelled fields in [#246](https://github.com/vig-os/org-config/issues/246), in this repo, in this release. Once the actor is live the installation token's read path maps its `actor_id` back through `GET /orgs/{org}/installations`, matches the declaration and plans clean, so the declaration still detects drift — with one hole of its own, now tracked as [#262](https://github.com/vig-os/org-config/issues/262): an App that is not an installation on the org is dropped on read, leaving a permanent phantom diff. Surfacing the unresolvable slug at plan time, where this repository's model says failures belong, is split out as [#259](https://github.com/vig-os/org-config/issues/259), scoped to all four write-path call sites rather than bypass actors alone. Upstream [eclipse-csi/otterdog#772](https://github.com/eclipse-csi/otterdog/issues/772), the same class of defect as the already-fixed #695; the exit criterion is an ADR-0005 pin that includes the fix.

- **An App bypass actor is documented as *readable* only while its App is an installation on the organization** ([#262](https://github.com/vig-os/org-config/issues/262)): the read-side sibling of [#256](https://github.com/vig-os/org-config/issues/256), and the worse half. Otterdog has no public endpoint for the id→slug direction and says so in its own `FIXME`, so it builds one map per run from `GET /orgs/{org}/installations` (`models/github_organization.py:555-558`) and applies it to every ruleset's `bypass_actors` at `:758-765`. That map can only hold **org installations**. An `Integration` actor whose `actor_id` is missing from it gets no `app_slug`, and `models/ruleset.py:541-548` logs `fail to map integration actor '<id>', skipping` — into otterdog's log, never into `plan.txt` — and **drops the actor from the model entirely**. Both directions are then wrong, and until [#259](https://github.com/vig-os/org-config/issues/259) neither reached the pull request: a declared actor is proposed for addition on *every* plan and `apply` never converges, because a ruleset patch re-sends the whole bypass list (`models/repo_ruleset.py:63-71`) — that half is now reported at review time, by the plan report's App-slug check comparing each declared slug against the org's installations; an undeclared one is a standing, unreported bypass of a protected branch or tag, and still reaches nothing, because catching it needs a live ruleset read. `drift.yml` reconciles the same plan text, so the phantom becomes a recurring drift record rather than a one-off. It is the same root cause as [upstream #732](https://github.com/eclipse-csi/otterdog/issues/732) — the same installation map, for required status checks — with a **strictly worse symptom**, and that contrast is the useful part: a status check *falls back* to the numeric `<integration_id>:<context>` form (`models/ruleset.py:145-151`) and stays both visible and writable, which is exactly why this repo's own prefixes are numeric `15368:` ([#69](https://github.com/vig-os/org-config/issues/69)); a bypass actor has no numeric form, so it does not degrade, it vanishes. Verified unfixed at the **1.5.0** pin and unfixed on upstream **`main`** on 2026-09-25 (`models/ruleset.py:545-552` there, byte-identical logic). **Nothing in the fleet is affected today, and that was checked rather than assumed:** all fifteen `Integration` bypass actors live across the readable `vig-os` and `exo-pet` rulesets — `2433383` `commit-action-bot` (eleven rulesets), `2930017` `vig-os-release-app` (three) and one private App owned by a sibling org, whose slug and id stay in the issue thread because this repository is public — appear in their org's `/installations` listing, with **two** blind spots named rather than glossed, both of them limits of the billing plan rather than surfaces left unread by choice: `vig-os/qms` is private on a Free-plan org, so both of its ruleset endpoints answer `403 Upgrade to GitHub Pro` and its rulesets could not be read; and `GET /orgs/vig-os/rulesets` answers `403 Upgrade to GitHub Team`, because org-level rulesets are a Team/Enterprise feature — a Free-plan org can hold none, so that refusal states the plan rather than hiding a surface, but it was not read either (`exo-pet` is on Team, was read in full, and holds no org-level ruleset). The case that trips it is undetectable from the config alone: a bypass slot granted out of band to an App installed on *some repositories* of the org without being an org installation, or an installation removed while the ruleset keeps the `actor_id`. Recorded in `README.md`'s *Known limitations* as its own entry, beside the `bypass_actors+` note in `otterdog/vig-os/vig-os.jsonnet`, and in both `unmanaged-controls.toml` comments — where, unlike the #256 write-side gap, the verdict is that a row **would** be the only detector, since the actor is invisible to plan and drift alike; this org still holds none, for the factual reason that it has nothing to assert, and the shape is written down for a downstream that does (`/repos/{org}/{repo}/rulesets/<id>` with `path = "bypass_actors[].actor_id"`, the one row form that must carry a ruleset id, because bypass actors do not appear on `/rules/branches/{branch}`). Surfacing it at review time is folded into [#259](https://github.com/vig-os/org-config/issues/259), which already reads the declared App actors and needs one extra `GET /orgs/{org}/installations` to report it. Documentation and config comments only — no row, endpoint, engine, workflow or ruleset change, and `--controls-report` is unchanged.

### Fixed

- **The App grant now says `Read & write` for Organization → Members, and an installation takes that level when its org declares a team** ([#257](https://github.com/vig-os/org-config/issues/257)): `docs/runbooks/github-app.md` recorded **Organization → Members: Read**, which is enough to *plan* a team and not enough to *apply* one. A downstream org that declares its first team therefore got a green plan, a merge, and then `POST /orgs/{org}/teams` → `403 Resource not accessible by integration` — the least helpful moment for the failure to surface, and one the error text gives no route out of, because the remedy is a UI-only App change plus a per-installation approval. Observed on `exo-pet` on **2026-09-25** (`exo-pet/org-config#81`, run `36119473230`): apply exited 1 with nothing mutated, a clean failure rather than a partial one; widening the App and approving the request on that installation made the identical dispatch succeed. **This is not a regression but a hole the [#16](https://github.com/vig-os/org-config/issues/16) methodology could not see.** That spike enumerated the otterdog `import` / `plan --no-web-ui` **read** path and mapped endpoint → permission, so `Members: Read` was correct *for reading*; the apply-side write was never exercised because no downstream org had declared a team until now (`exo-pet` carried `teams: []` from its initial import, precisely to avoid the base template's Eclipse teams). The runbook row and its prose bullet now both read **Read & write**, in the same voice as the Custom-properties row that records the same class of finding, and the bullet names the neighbouring calls that ride on the same level — `PATCH`/`DELETE /orgs/{org}/teams/{team_slug}`, `PUT`/`DELETE /orgs/{org}/teams/{team_slug}/memberships/{user}`, and the easily-missed `PUT /orgs/{org}/organization-roles/teams/{team_slug}/{role_id}`, which assigns a `security_manager` team and which GitHub lists under **Members**, not under Custom organization roles. **Downstream action is required, is per org, and is deliberately not fleet-wide:** editing the App's *Permissions & events* page updates the App, not its installations — each install stays on the permission set it last accepted until an owner of that org approves the new request, so an org that skips the approval keeps 403'ing on the next team it declares. The policy the runbook now records is that an installation takes the widened level **when that org declares its first team**, and an org whose config carries `teams: []` stays on `Read` as least privilege — because Members write is not confined to teams: it also grants `PUT /orgs/{org}/memberships/{username}` (which sets `role`, so it can promote a member to **admin**), `DELETE /orgs/{org}/members/{username}` and `POST /orgs/{org}/invitations`, inviting, promoting and removing owners — none of which Organization → Administration write includes. `GET /orgs/{org}/installations` is named as the cheap confirmation of where an org stands, since the `permissions` object reported there, not the App's settings page, is what a token minted for that org can actually do. A new **Read path vs apply path** subsection records the general audit this triggered: otterdog 1.5.0's `providers/github/rest/*_client.py` write endpoints were re-checked against GitHub's [permissions-required-for-github-apps](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps) reference for every row in the table. The single **Access** column stands — a GitHub App grant is one level per permission, so that column must always carry the *apply*-path level, and after this fix it does for every resource the fleet declares — but three apply-path levels are deliberately left ungranted and are now written down instead of waiting to be rediscovered: **Organization → Custom properties** is `Read & write` while writing a property *schema* needs `Admin` — the table's own *Why* cell, which until now claimed the schema is written at apply, is corrected in the same change (untriggered only because `vig-os`'s one `type` property already matches the config, so the first org declaring a *new* org property fails exactly as this one did); **Repository → Contents** is `Read` while a `default_branch` pointed at a branch that does not yet exist makes otterdog *rename* the current default via `POST /repos/{org}/{repo}/branches/{branch}/rename`, which GitHub lists under Contents **write**; and there is **no Repository → Environments grant**, which environment *secrets and variables* need — invisible today only because the pinned `otterdog-defaults` `v0.13.1` defines no `newEnvSecret` / `newEnvVariable`, a pin held for the unrelated `max_cache_size_gb` `402` reason, so a base-template bump that adds those functions must add the permission in the same change — a trip-wire now carried by `justfile.project`'s pin comment as well as the runbook, since the literal itself lives in `otterdog.json`, which is JSON and cannot hold one. Documentation only — no engine, workflow or config change; the App itself is a human UI step, already done at App level, and each org's installation approval is that org's own call under the policy above.

- **The unmanaged-controls transport refuses a truncated read instead of asserting the first page of a collection** ([#258](https://github.com/vig-os/org-config/issues/258)): `get_json()` — the generic read every `unmanaged-controls.toml` row asserts against — issued one GET, sent no `per_page`, and discarded the response headers, `Link: …; rel="next"` included. Since [#205](https://github.com/vig-os/org-config/issues/205) a row may project over a list (`[].context`, `[].type`) and compare the result as a set, so under GitHub's default page size of **30** the row asserted page one as if it were the whole collection — and that failure is the bad kind: a truncated list does not raise, does not go `MISSING`, and simply compares as a **shorter set**, exactly what `select_path`'s own docstring already called unacceptable. Over the page boundary a row either manufactures drift or, where `expect` was itself seeded from a truncated read, **reads permanently clean while the live collection diverges underneath it** — verified here by disabling the new guard against a 30-element first page whose `expect` matched it exactly: the row reported `OK` and landed in `clean_fingerprints`. Two changes close it, both stdlib-only. `get_json` now asks for **`per_page=100`** unless the path already names a page size (joined with `&` when a query string is there, `?` when it is not; GitHub ignores query parameters an endpoint does not define, verified against `GET /orgs/{org}`), and it **refuses** a response whose `Link` header advertises a further page, raising the new `TruncatedResponseError`. That error is an `ApiError` subclass carrying status **200** — the one API error whose status is a success, because the request worked and only the *completeness* failed — so it travels the degradation path the leg already has: the row lands in `unresolved_fingerprints`, its issue is left exactly as it was, and `--controls-report` shows `UNRESOLVED` with `actual = truncated` and a note naming the endpoint. **Reusing `UNRESOLVED` rather than adding a verdict is deliberate**: "the transport could not resolve the whole collection" is the same contract as "the row could not be read" — leave the issue alone, degrade only this row — and a new status would make every consumer learn a value that changes no behaviour. The refusal is **unconditional**, not reserved for list-shaped rows, because the transport cannot see the row's path: a dict-shaped endpoint never sends a `next` anyway, over-refusing a scalar read costs one degraded row, and under-refusing a projection asserts a lie. The dedicated paginated helpers (`list_open_drift_issues`, `list_org_repos`, `list_org_secrets`, `list_org_secret_repositories`) walk their pages by number and are untouched — `_request` keeps its body-only signature and a new `_send` sibling exposes the `Link` header to `get_json` alone. **No current row changes verdict**: every live collection asserted today is far inside one page (`/repos/{org}/{repo}/rules/branches/main` on this repo answers 5 rules), and endpoint memoization is unchanged because the cache is still keyed by the row's resolved endpoint, not by the requested path. Real pagination inside `get_json` ([#258](https://github.com/vig-os/org-config/issues/258) sketch option 3) is deliberately **not** done: merging pages generically would need to know whether a body is a root list or an envelope keyed by `secrets`/`repositories`/…, which is exactly the per-endpoint knowledge the dedicated methods already encode, and no row needs more than 100 elements today — the refusal makes that a *loud* limit rather than a silent one. `select_path`'s docstring, the table's doctrine comment, `template/unmanaged-controls.toml` and the README degradation sentence all now say so.

- **The org sweep walks pages by `Link: rel="next"`, so a short page can no longer end the list early** ([#260](https://github.com/vig-os/org-config/issues/260)): the four dedicated list methods on `RestGitHubClient` — `list_org_repos()`, `list_open_drift_issues()`, `list_org_secrets()` and `list_org_secret_repositories()` — each composed `page=N` by hand and stopped on `len(batch) < 100`, which is an inference about GitHub's behaviour rather than a reading of what GitHub said, and it is wrong in **both** directions: an endpoint that filters *after* paginating returns a short page that is not the last, and a collection ending exactly on a page boundary returns a full page that is. `list_org_repos()` is the `live` side of the [ADR-0002](docs/adr/0002-drift-semantics.md) inventory sweep, so an undercount there fails twice over at `inventory.py:182-183` (`undeclared = live - declared`, `missing = declared - live`): a live repo past the cut **never produces its `undeclared` record** — the shadow-repo finding the sweep exists for, gone quiet on a green run — and a declared repo past the cut produces a **false `absent`** record, "Declared repository absent from org: `<name>`", with a real issue opened against it. Neither degrades: `cli.py:163-175` drops the inventory leg on a *raised* failure, and a truncation raises nothing. The fix is one shared page walk, `_paginate()`, over the `(body, Link)` transport [#258](https://github.com/vig-os/org-config/issues/258) split out — four copies of the loop become one — following `rel="next"` until GitHub stops sending it, which is exactly what GitHub's pagination guide says to do. **The `next` target is followed verbatim, never rebuilt from a page number**, and that is not pedantry: `/repos/{owner}/{repo}/issues` paginates by **cursor** — captured live, its `next` is `…&per_page=1&page=2&after=Y3Vyc29yOnYyOpLPAAAB…` and it sends **no** `rel="last"` — so a composed `page=N` is not the same request. The walk yields whole documents rather than merged rows, which keeps the two body shapes GitHub uses (a root list for `/orgs/{org}/repos`, an envelope keyed `secrets`/`repositories` for the Actions-secret endpoints) the caller's knowledge and not the transport's; the `search` API's `{"items": […]}` envelope never arises, because no call site reads `/search/*`. A `next` the walk cannot follow raises `TruncatedResponseError` instead of ending quietly — "there is more" must never be read as "that was all". **Nothing was truncated today**: `vig-os` has 14 repositories and `exo-pet` 9, and `GET /orgs/vig-os/repos?per_page=100` answers with no `Link` header at all — this closes the stop condition before a fleet past 100 repositories gets the bad half of it without a signal. The tests move down a layer with the code: the `_RecordingClient` that faked `_request` (and so never exercised a page walk at all) is replaced by a `_PagedClient` faking `_send`, and the new fixtures assert the **exact request sequence** for a multi-page walk, for a short-but-not-last page, and for a full 100-row last page that must cost exactly one request. Following a URL verbatim does cost the walk the ceiling a composed page number gave it for free — a server repeating itself used to end the loop as soon as the composed number ran past the collection — so the walk carries its own: it tracks the URLs it has fetched and raises on a `next` that repeats one, refusing a pagination cycle rather than spinning until the job's `timeout-minutes` burns the rate limit. That bound is on the thing that actually misbehaves, a server handing back a page it already served, rather than on a page count, which would have to guess how long a legitimate collection may be.

### Added

- **Unmanaged-control rows can address JSON list elements, so ruleset internals are assertable** ([#205](https://github.com/vig-os/org-config/issues/205)): `select_path()` walked objects only, which made anything GitHub returns *inside a list* unassertable — and the most consequential control is exactly that shape, since a repository ruleset's `rules` are an array keyed by `type` and the required status checks inside one of them are an array of objects. Two new path forms close it, both stdlib-only and still deliberately not jq ([ADR-0005](docs/adr/0005-repo-tooling.md)): `rules[type=required_status_checks]` selects the **one** element whose field equals the literal, and `required_status_checks[].context` projects a field out of **every** element; an empty key applies either operator to the response itself, for the endpoints that answer with a list at the root. A companion row field `compare = "set"` compares the projected result with a TOML array **order- and duplicate-insensitively**, because GitHub returns a check list in no guaranteed order and an exact comparison would report drift every time the UI reshuffled it. Every ambiguity **degrades instead of guessing**, which is the whole point: zero or several matches, a projection over a non-list or one element that cannot satisfy it, a malformed path, a live value that cannot become a set (a row that forgot its `[].context`, or a field that stopped being a list) all resolve to `UNRESOLVED`, leaving the row's own issue exactly as it was — two rulesets can contribute a rule of the same type to one branch, and picking either would fabricate or hide a security finding, while a partial projection would compare as a shorter set and read as drift or, worse, as clean. Match literals compare against **strings only**, since coercion would make `[id=1]` match a live `true`, the same conflation `_equal` already refuses; declared values are validated at load, so an unknown `compare` mode, an unparsable path, or a set row whose `expect`/`tolerated` is not a list of plain values **drops the row** under the standing rule that a malformed row must never manufacture a finding. Drift bodies gain `missing:`/`unexpected:` lines, since a dropped required check and an unexpected extra one are different incidents. The engine repo itself deliberately gains **no new row**: every vig-os repo but one is public, where Otterdog models rulesets and the plan already diffs them, and the exception (`qms`) is private on a Free-plan org where both ruleset endpoints answer `403 Upgrade to GitHub Pro`. This is capability for **downstream** orgs on Team/Enterprise, whose private repos Otterdog cannot read ([#107](https://github.com/vig-os/org-config/issues/107), [eclipse-csi/otterdog#729](https://github.com/eclipse-csi/otterdog/issues/729)) while REST can — `exo-pet/org-config` can now convert its four `kind = "unassertable"` `main-protection-*` rows into real assertions. Both the shipped table and the `template/` starter document the shape, which reads `/repos/{org}/{repo}/rules/branches/{branch}` rather than `/rulesets/{id}`: no ruleset id to hard-code, readable with repo read access, and it asserts what actually protects the branch whichever ruleset carries it. No behaviour change for any existing row — `--controls-report` on live `vig-os` is unchanged at 13 `OK` / 3 `TOLERATED`.

- **The `Plan` check is advisory by decision, and ADR-0007 now says so** ([#236](https://github.com/vig-os/org-config/issues/236)): `Main protection` requires exactly one context, `15368:CI Summary`, and `Plan` was never one — a fact recorded in passing by [#230](https://github.com/vig-os/org-config/issues/230) but never actually decided. It is now decided, with the trade in [ADR-0007](docs/adr/0007-ci-and-testing-strategy.md)'s alternatives table as a new Axis D. The reasoning corrects the framing the question is usually raised with: `otterdog plan` exits **0** on a non-empty diff, so a *red* plan is invalid config, broken auth or a harness failure — never drift — and the config-validity half of that is already behind the required check, since `otterdog validate --local` runs offline as an L0 pre-commit hook inside the `Lint & Format` job. Requiring `Plan` would therefore gate merges on App-credential health, a property of the runner rather than of the PR, while the diff it is actually reached for is explicitly not a failure under [ADR-0002](docs/adr/0002-drift-semantics.md). The enforcing control stays where mutation happens: the `production` environment reviewer pauses every apply with the exact tree's plan in the same run's summary ([#105](https://github.com/vig-os/org-config/issues/105), [#176](https://github.com/vig-os/org-config/issues/176)), guarded against a stale tree by the tip-of-branch check added after [#99](https://github.com/vig-os/org-config/issues/99). The mechanically-possible alternative is recorded rather than hand-waved: a workflow-level `paths:` filter leaves a required check `Pending` forever, but a job skipped by a **conditional** reports *Success*, so a broad trigger plus a job-level gate and a static summary job would make the check requirable for roughly ten seconds and no live API call on an unrelated PR. It is rejected for now on cost of meaning, not cost of compute — the green would mean *clean*, *skipped* and *fork PR* alike, it needs the templated job name (`Plan committed config against live ${{ ... }}`) made static plus a new ruleset context, and it propagates into `template/` and every consumer org. Its revisit triggers are written down: an unintended diff the `production` approval misses, a second maintainer, or GitHub shipping path-conditional required checks. Empirically the gate has never been needed — `plan.yml` has run 57 times and never once concluded `failure`. Documentation only; no workflow, config or ruleset change — `plan.yml` and `Main protection` are byte-identical.

- **ADR-0007's "L2 runs on every same-repo PR" is corrected — the live plan has been path-filtered since day one** ([#235](https://github.com/vig-os/org-config/issues/235)): the test pyramid described its L2 layer as a read-only `otterdog plan` against `vig-os` "on every same-repo PR", and `plan.yml` has never worked that way — the `pull_request` `paths:` filter was in the workflow's first commit (`f101cc6`), landed the same day the ADR was accepted, so L2 fires only on a same-repo PR into `main` touching `otterdog.json`, `otterdog/**`, `.github/workflows/plan.yml` or, since [#230](https://github.com/vig-os/org-config/issues/230), `justfile.project`. The claim is load-bearing rather than incidental: the pyramid's shape *is* this ADR's decision, and a reader sizing the L2/L3 gap — or waving a new check off to L3 because L2 "already covers every PR" — was reading something untrue of the implementation. The bullet now states the real trigger set and says why it is narrow: a plan is a live-API round trip against the org on a full App installation token ([ADR-0004](docs/adr/0004-auth-model-github-app.md) Corrections), so running one on a README typo diffs the same committed config against the same live org for no new signal — the filter is why L2 is cheap, not an oversight. Recorded as a dated entry in ADR-0007's `## Corrections` block (previously "None yet") rather than silently rewritten, matching [#225](https://github.com/vig-os/org-config/issues/225)'s handling of ADR-0005. Explicitly unaffected: the binding credential rule — plan runs **only** on same-repo PRs — is an upper bound on who may reach the App token, never a promise that every such PR is planned, and L3's "never per-PR" stands; `README.md` already described L2 as "`plan` on every config PR" and is unchanged. A supersession trigger is added for [#236](https://github.com/vig-os/org-config/issues/236), whose skip-job-shim option would drop the filter and retire this correction. - **A pure otterdog pin bump no longer merges without a plan run** ([#230](https://github.com/vig-os/org-config/issues/230)): `plan.yml`'s `pull_request` `paths:` filter listed `otterdog.json`, `otterdog/**` and the workflow itself, but not `justfile.project` — which holds `otterdog_version`, the [ADR-0005](docs/adr/0005-repo-tooling.md) single source of truth that the workflow's own "Resolve otterdog version pin" step greps at run time. That file selects the **binary that produces the diff**, which makes it the highest-leverage input to plan behaviour in the repo, and [ADR-0007](docs/adr/0007-ci-and-testing-strategy.md)'s entire argument for pinning is that a version change can move that behaviour. The gap stayed invisible because the previous bump ([#145](https://github.com/vig-os/org-config/issues/145), 1.3.4 -> 1.4.0) also edited `otterdog/vig-os/vig-os.jsonnet` and was pulled in by `otterdog/**`; [#225](https://github.com/vig-os/org-config/issues/225)'s 1.5.0 bump ([PR #229](https://github.com/vig-os/org-config/pull/229)) was a pure pin-plus-documentation change touching no config path, so **no plan ran at all** — and an empty plan is precisely that issue's acceptance evidence, which had to be produced by hand ([`workflow_dispatch` run 35844030809](https://github.com/vig-os/org-config/actions/runs/35844030809), `0 to add, 0 to change, 0 to delete`). Stated precisely, because the distinction is load-bearing: what a bump was losing is the **automatic plan evidence on the PR**, not a blocking gate. `Plan` is not a required status check — the `Main protection` ruleset requires exactly one context, `CI Summary` — and a path-filtered workflow *cannot* be required, since a required check that never runs leaves the PR pending forever. Scope-wise the filter stays tight and the trade is accepted explicitly: `justfile.project` also carries unrelated recipes, so some plan runs will now diff nothing, but the file has moved **8 times** in this repo's life — no Renovate manager matches a bare Just variable ([#225](https://github.com/vig-os/org-config/issues/225)) and devkit upgrades preserve it, so it only ever moves on a hand edit — which puts a handful of read-only runs against a pin bump silently losing its evidence. `apply-engine.yml` deliberately keeps omitting the same file, and the asymmetry is now recorded inline where a future reader will trip over it: plan must **prove** before merge that the newly pinned engine produces no diff, while apply must not **mutate** the live org off an engine-version edit carrying no config delta — if a pin bump ever does need applying, that is a human `workflow_dispatch` taken after reading the plan. `template/` needs no equivalent line and now says so: downstream the pin is the `otterdog_version:` input literal inside the caller workflow, already matched by `.github/workflows/plan.yml`, and the skeleton ships no `justfile.project` at all ([#56](https://github.com/vig-os/org-config/issues/56)). Workflow trigger and comments only — no engine, config, or plan-execution behaviour change.

- **Otterdog pin bumped 1.4.0 -> 1.5.0, ungating repository-ruleset reads on private repos below Enterprise** ([#107](https://github.com/vig-os/org-config/issues/107), [#225](https://github.com/vig-os/org-config/issues/225)): otterdog read live repo rulesets only when a repository was public or the org was on `enterprise`, so a private downstream org on Team could not declare a repo ruleset at all — the declaration diffed against an empty live set, giving a permanent phantom `add` on every plan and a duplicate `POST` on apply, which is why those rulesets were hand-managed with the declaration held out of the jsonnet. Upstream [#731](https://github.com/eclipse-csi/otterdog/pull/731) removed the gate from both ruleset read paths and, in the same commit and just as load-bearing, gave both clients `if ex.status in (403, 404): return []` at `debug` level — which is what makes the bump safe on a **Free**-plan org, where the newly-attempted `/repos/{org}/{repo}/rulesets` and `/orgs/{org}/rulesets` calls answer `403` and are absorbed silently rather than aborting the plan or adding lines to the `plan.txt` the drift layer parses. Effect here is deliberately nil: every `vig-os` repo but `qms` is public and already ruleset-complete, `qms` declares none, and `otterdog 1.5.0 validate --local` output is identical to 1.4.0 — so this ships the capability for **downstream** Team/Enterprise orgs rather than changing this org's plan. **Migration, and it is not safe to adopt blind:** before v1.5.0 a private repo's live rulesets were never read, so config-declares-none matched live-holds-none and the plan was silent; at v1.5.0 the live model holds them while the config still declares none, so the plan flips from silence to proposing one **deletion per ruleset** — a red plan, and one `drift`+`critical` issue per ruleset on the next scheduled run, none of which self-close. **Declare the rulesets in the jsonnet first, then bump the pin, in one change**, with an empty plan as the acceptance evidence. Deliberately corrected against the issue that requested this: an `apply` dispatch does **not** delete that protection — `apply.yml` omits `--delete-resources` and `operations/apply.py` is byte-identical across the two releases, still skipping every `REMOVE` patch without the flag — so the exposure is plan noise, not lost branch protection. The pin moves across **five** hand-maintained literals — `justfile.project` (the ADR-0005 single source of truth) plus `template/.github/workflows/{plan,apply,drift,import}.yml` — because nothing propagates it ([#56](https://github.com/vig-os/org-config/issues/56)); the 1.4.0 bump missed `import.yml` and left a template consumer importing on one version and planning on another ([#164](https://github.com/vig-os/org-config/issues/164) item 7). The `otterdog.json` `otterdog-defaults` pin **stays at v0.13.1** by decision: v0.14.x adds `max_cache_size_gb`, which would enter otterdog's `included_keys` and call `/orgs/{org}/actions/cache/storage-limit` — `402` on a Free plan — writing a permanent `WARNING` into every plan. ## [v1.3.0](https://github.com/vig-os/org-config/releases/tag/v1.3.0) - 2026-08-24

### Added

- **Apply-dispatch reminder: a merged-but-unapplied config no longer goes unnoticed** ([#202](https://github.com/vig-os/org-config/issues/202)): a new reusable `.github/workflows/apply-reminder.yml` comments the pending apply — merge commit, PR link, dispatch command — onto a long-standing, pinned "Apply dispatch tracker" issue and labels it `pending-apply`; the reusable `apply` workflow gains an optional `tracker_issue` input that, on a successful apply, posts the "applied" confirmation on the same thread and clears the label. The gap it closes is structural and downstream-only: on a **private** config repo below Enterprise, environment required reviewers are unavailable (adding one returns HTTP 422), so the engine's apply-on-merge-with-approval model degrades to `workflow_dispatch`-only and the dispatch *is* the approval gate — after which merged-but-unapplied is a **silent** state, since GitHub suppresses self-activity email for the admin who merged and the first signal would be the next scheduled drift run, up to a day later. The tracker's **assignees are the notification list** (assignment mails them on every later bot comment regardless of watch settings, and the list changes without touching a workflow), one long-lived issue avoids per-merge issue churn, and the thread ends up a durable audit record pairing every config merge with the run that applied it — with the daily drift run still the enforcement backstop for an ignored reminder. Deliberate details: the caller filters on **all four** paths apply consumes (`otterdog.json`, `otterdog/**`, `secrets/**`, `.sops.yaml`), because a two-path filter would let a SOPS secret rotation merge with no reminder; the PR link is parsed from the merge commit title's `(#N)` suffix that house policy guarantees, degrading to a commit-only comment on a direct push rather than failing; the workflow takes its **own** `apply-reminder-<org>` concurrency group, never the shared `otterdog-mutate-<org>` one, where a reminder would queue uselessly behind a 30-minute apply; and it needs no secrets, no checkout and no third-party action — the comment and label are same-repo issue writes on the workflow `GITHUB_TOKEN` (`issues: write` + `contents: read`, the latter per [#173](https://github.com/vig-os/org-config/issues/173)). The `apply` side is **not** on `GITHUB_TOKEN`: the [#176](https://github.com/vig-os/org-config/issues/176) standing rule caps that workflow's whole job graph at `contents: read` at assembly time, before any `if:`, so `issues: write` there would startup-fail every existing consumer — the confirmation rides a narrowed App token minted in-workflow (drift.yml's issue-ops pattern), needing no caller change and no new App grant. Its guard, `inputs.tracker_issue != '' && steps.apply.outcome != 'skipped' && steps.apply.outputs.rc == '0'`, is deliberately triple: the apply step runs under `set +e` so its outcome is `success` even when otterdog failed (`rc` is the only truth), and a superseded run ([#105](https://github.com/vig-os/org-config/issues/105)) self-skips yet stays green — a weaker guard would announce "applied" for a run that applied nothing. **Optional, active by default in the template**, which ships the reminder caller enabled with a `TODO(tracker)` placeholder; an org opts out by deleting the caller, and with `tracker_issue` empty every run is a logged green no-op and `apply.yml` is byte-identical to before, at assembly time and at runtime. The engine repo itself is unaffected — it is public and its apply runs behind a real `production` reviewer gate — so this is downstream-only machinery, held here rather than vendored in a consumer per the [#169](https://github.com/vig-os/org-config/issues/169) principle. Rollout is not automatic: there is no template-sync machinery and Renovate only bumps pins on existing callers, so each org hand-adds the caller and does the one-time tracker/label/assignee setup, documented as a standard step in the onboarding runbook.

Both secrets coexist until every consumer is re-scaffolded; the numeric `DEVKIT_UPGRADE_APP_ID` is retired in a later phase.
- **Unmanaged-controls assertion table** ([#116](https://github.com/vig-os/org-config/issues/116)): a new `src/drift_layer/controls.py` loads `unmanaged-controls.toml`, a declarative table of live org/repo controls otterdog has no schema field for — Actions SHA-pinning, the fork-PR approval policy, the new-repository security defaults, the secret-scanning extras — which are consequently invisible to **both** the plan and the inventory sweep and can be flipped in the UI with nothing noticing. Each `[[control]]` row names a stable `key`, a `scope` (`org`, or `repo` plus a `repository`), a `{org}`/`{repo}`-templated `endpoint`, a dotted `path` into the decoded JSON response, and the `expect`ed literal; optional `tolerated` declares a second accepted value for a known, tracked divergence, so the table records the **desired** value even where reality is currently allowed to differ and the row goes green by itself once the divergence is fixed (any *third* value is real drift). An optional `kind = "unassertable"` documents a control with no readable endpoint. Field selection is a dotted-key walk rather than a jq expression, preserving the drift layer's zero-runtime-dependency, `uvx`-light posture (ADR-0005); `false` and `null` are returned verbatim while an absent field yields a distinct sentinel, so a renamed field degrades instead of fabricating a security finding, and rows that cannot be evaluated as written are dropped rather than half-asserted. Identity is the TOML key, never the live value: the namespaced `unmanaged-control:<scope>:<key>` fingerprint resource is a sibling of the plan's block headers and the sweep's `repository-inventory:`, so all three populations share one dedup keyspace without ever colliding and ADR-0002's update-not-duplicate issue lifecycle applies unchanged.
- **Typed GitHub API errors and a generic read surface on the drift client** ([#116](https://github.com/vig-os/org-config/issues/116)): `RestGitHubClient` gains `get_json(path)` plus the two paginated org-secret reads (`list_org_secrets`, `list_org_secret_repositories`), and every transport failure now surfaces as an `ApiError` carrying the HTTP status — `404` unassertable, `401`/`403` token scope, and `0` for a request that never got an answer at all (DNS, TLS, connection, or decode failure). The typed status is what makes per-row degradation possible for the unmanaged-controls leg: without it the evaluator cannot tell "this control is wrong" from "this control could not be read", and a transient 403 would either be reported as a critical security finding or, worse, silently close a real open one. `get_json` is deliberately a dumb transport with the row's dotted path doing all field selection, so a new control needs a table row rather than a new client method; secret *values* are never returned by the API, so only the metadata the assertion families compare is ever fetched. Existing callers are unaffected in behaviour — the CLI already degrades on any exception from the live-read leg.
- **Unmanaged-control evaluation with per-row degradation** ([#116](https://github.com/vig-os/org-config/issues/116)): `evaluate_controls()` asserts every table row against live state through the injected client and sorts each into exactly one bucket — matched (clean), matched the `tolerated` value (clean plus a summary note, no issue), diverged (a `drift`+`critical` record whose evidence block carries endpoint, path, expected, tolerated, actual, rationale and refs), or unreadable (unresolved). Splitting *clean* from *unresolved* is the load-bearing design point: `reconcile()` closes every open issue whose fingerprint is absent from the records it is handed, so reporting an unreadable row as clean would **phantom-resolve a genuine security finding** on a transient 403. Because a row's fingerprint derives from its TOML key without touching the API, the unresolved rows' issues can be withheld from the reconcile input individually — one unreadable row degrades only itself, strictly better than the inventory sweep's all-or-nothing skip. A `200` whose schema no longer carries the asserted path is likewise unresolved rather than drift, since treating a renamed field as a divergence would fabricate a critical issue out of a GitHub API change. Comparison is strict (`1` is not `true`), responses are memoized per resolved endpoint so the six rows reading `GET /orgs/{org}` cost one request, and `kind = "unassertable"` rows never touch the client at all.
- **Org-secret assertions derived from the committed config** ([#116](https://github.com/vig-os/org-config/issues/116)): `extract_declared_org_secrets()` reads every committed `orgs.newOrgSecret(...)` declaration — name, visibility and `selected_repositories` — with the same strict-literal doctrine already used for `newRepo` (comments stripped, block read to its matching brace, `newRepoSecret(` never matched), and three generated assertion families compare live metadata against it: visibility, reader lists, and undeclared live secrets. This is the one class of drift otterdog structurally *cannot* catch: nine of the ten committed org secrets carry a `'********'` dummy value, so `include_for_live_patch` is false and the plan skips them entirely — a visibility widened in the UI or a reader list hand-edited via `PUT .../repositories` produces no diff at all. otterdog's `public` is translated to the REST API's `all` on read, exactly as its own model does, so an org-wide secret is not reported as permanent drift. Each family yields at most **one** aggregate issue whose body lists every offender (stable identity, volatile body — precisely what the update-in-place lifecycle is for) rather than one issue per secret, and each degrades independently: an unreadable reader list leaves the visibility and inventory families reporting normally. `assert_no_undeclared` is on by default because a live org secret with no committed declaration is an unreviewed credential with no record of who created it or when it should rotate.
- **Unmanaged-control findings reconciled as a third issue population** ([#116](https://github.com/vig-os/org-config/issues/116)): assertion failures now flow into the same ADR-0002 lifecycle as plan drift and the inventory sweep — one deduplicated issue per control, updated on recurrence, auto-closed on resolution — under an `unmanaged-control` label beside `drift`+`critical`. `reconcile_populations()` becomes three-way, and the plan partition now excludes **both** extra labels: without that, the first run would close every inventory and control issue as phantom-resolved. The controls leg degrades one step finer than the sweep's all-or-nothing skip — the issues of rows that could not be *read* are withheld from its reconcile input individually, so a single 403 leaves exactly one issue untouched while every readable row still reports. Issue wording is corrected for the new evidence type: a control issue says the live control diverges from the value asserted in `unmanaged-controls.toml` and labels its evidence block "Live API assertion", rather than claiming a divergence from the committed otterdog config — there is no jsonnet field, and saying otherwise would send the triager hunting for a setting that does not exist; the auto-close comment cites the live assertion for the same reason. `--dry-run` skips the leg (it is a live read by definition) and a new read-only `--controls-report` prints each row's outcome — `OK`/`TOLERATED`/`DRIFT`/`UNRESOLVED`/`SKIPPED`, expected versus actual — with no issue writes at all, which is how a row is verified green *before* the scheduled run would turn it into a critical issue.
- **`unmanaged-controls.toml` seeded with the twelve known unmodellable controls** ([#116](https://github.com/vig-os/org-config/issues/116)): the shipped table now asserts Actions SHA-pinning (org plus `devkit`), the fork-PR approval policy (org plus `devkit`), the two stuck `devkit` secret-scanning extras, the six org-level new-repository security defaults, and the three generated org-secret families; a `template/` stub ships beside it for downstream orgs, and the `unmanaged-control` label joins `.github/label-taxonomy.local.toml`. Every `expect` was verified against live `vig-os` on the seed date and the table lands **green** — `--controls-report` reads 12 `OK` and 3 `TOLERATED`, 0 `DRIFT`, 0 `UNRESOLVED` — so this is a detector, not a posture change; the fork-PR rows lock in today's `first_time_contributors` rather than hardening to `all_external_contributors`, which stays a separate decision. Three rows deliberately record the **desired** value with a `tolerated` escape rather than asserting reality: org SHA-pinning (`expect = true`, tolerated `false` pending [#120](https://github.com/vig-os/org-config/issues/120), so the row goes green with no edit when #120 lands) and the two `devkit` secret-scanning extras, which the enforced org code-security configuration 237480 declares enabled but which need a GHAS Secret Protection entitlement the plan does not carry — a repo-level `PATCH` returns 200 OK and changes nothing. Tolerating those here rather than in `drift-allowlist.toml` is deliberate: an allow-list entry silences the control unconditionally, hides a third value, splits one control's truth across two files, and would be cleared by `apply_allowlist`'s `with_expected()`. `new-repo-advanced-security` is asserted **off** for the same entitlement reason — a default-on would produce new repositories that look protected and are not.
- **The scheduled drift run asserts the unmanaged live controls** ([#116](https://github.com/vig-os/org-config/issues/116)): `drift.yml`'s reconcile step now passes `--unmanaged-controls unmanaged-controls.toml`, so the daily run reconciles three populations in one invocation — plan drift, the inventory sweep, and the live control assertions — each under its own label and its own degradation contract. **No token, permission or App-grant change is needed**, and the header records why: every endpoint the leg touches is a `GET`, and the permissions they need (Org Administration read, Org Secrets read, Repo Administration read) are already inside the full plan token's grant, so the workflow's "read-only by behaviour" argument extends unchanged. The step stays green on a degraded leg without a blanket `continue-on-error` that would also mask a genuine reconcile failure: rows that could not be read surface as `::warning::` annotations while their issues are left untouched. The reconciler's output is teed to a file and fenced into the run summary alongside the plan — the actions taken plus the per-row control annotations — which keeps the CLI free of any GitHub Actions-specific behaviour.
- **`devkit` tag-protection ruleset** ([#115](https://github.com/vig-os/org-config/issues/115)): `devkit` publishes the release tags every consumer pins yet declared no `target: 'tag'` ruleset, so anyone with write access could create, move, or delete one out of band — `commit-action` has had this ruleset since #43. The new `Tag protection` block mirrors it verbatim (`include_refs: ['~ALL']`, creations/updates/deletions blocked, `allows_force_pushes: true`, single bypass actor `vig-os-release-app`). One always-bypass actor is sufficient because `release.yml`'s publish job is the repo's **only** tag writer (`git tag -a` + `git push origin <version>`, on a token minted from `RELEASE_APP_CLIENT_ID`/`RELEASE_APP_PRIVATE_KEY` — App `vig-os-release-app`, `app_id` 2930017) and `promote-release.yml` prunes leftover RC tags with the same App; `devkit` also uses bare `X.Y.Z` tags (no `DEVKIT_TAG_PREFIX`) and declares no floating tags, so nothing ever force-moves a published tag. This ruleset carries no status checks, so `otterdog apply` can **create** it normally — unlike the two ruleset modifications below, it is not affected by [#69](https://github.com/vig-os/org-config/issues/69).

### Changed

- **ADR-0002's "the plan is the sole drift signal" premise recorded as superseded** ([#116](https://github.com/vig-os/org-config/issues/116)): the README's "Drift is issue-only" section now documents the third population and `unmanaged-controls.toml`, and ADR-0002 gains a dated Corrections entry. They were never a mistake — they were collateral of the Debian -> Nix migration in `devkit`. `devkit` `36a40550` ("ci: authenticate Docker Hub pulls to avoid rate limits", [vig-os/devkit#473](https://github.com/vig-os/devkit/issues/473), 2026-04-02) added `dockerhub-username`/`dockerhub-token` inputs to the `build-image` composite action and logged in to `docker.io` before `setup-buildx-action` so CI pulls were authenticated rather than anonymous; the org secrets were created the **same day** (11:30 and 11:31 UTC) to feed it. `devkit` `1d4e9db1` ("build(nix): decommission the Debian build path", 2026-06-24, on `main` and `dev`) removed the login along with the path that needed it, and nothing has referenced either name since. Unlike the #111 precedent, the live org secrets were deleted by the org owner **before** this change merged, so `plan` shows no pending deletions (`otterdog apply` never deletes secrets, so the order matters only for plan noise). Deleting a GitHub secret does not revoke the credential it held, so the underlying Docker Hub access token — which would otherwise have stayed valid indefinitely with no consumer and no audit trail — was revoked in Docker Hub's own account settings as part of the same retirement. Phase 2 of the orphaned-org-secret retirements begun in [#111](https://github.com/vig-os/org-config/issues/111); found by the consumer-matrix sweep in [#123](https://github.com/vig-os/org-config/issues/123).
- **Orphaned `APP_SYNC_ISSUES_ID` / `APP_SYNC_ISSUES_PRIVATE_KEY` org secrets** ([#111](https://github.com/vig-os/org-config/issues/111)): the two `vig-os` **organization** secrets are dropped from `otterdog/vig-os/vig-os.jsonnet`. A 2026-08-07 sweep of every `sync-issues.yml` in the org found zero consumers at org scope: the only workflows naming them are `tessera`'s, and `tessera` carries its **own repo-level secrets of the same names** belonging to a different App (the repo-scoped `tessera-sync-issues-bot`, `app_id` 4483218) — a repo-level secret always shadows an org-level one, so nothing ever resolved to the org pair. Every other repo's `sync-issues.yml` authenticates with `COMMIT_APP_*`. `tessera`'s `orgs.newRepoSecret('APP_SYNC_ISSUES_*')` declarations are deliberately **untouched** (the comment beside them already warns against "deduplicating" them into org secrets). Because `otterdog apply` never deletes secrets, the live org secrets are deleted out-of-band after merge; until then they surface as two pending deletions in the plan. Phase 1 of the App-secret consolidation program tracked in [#112](https://github.com/vig-os/org-config/issues/112).

### Fixed

- **`apply` can no longer execute a stale approved tree** ([#105](https://github.com/vig-os/org-config/issues/105)): the production-environment approval gates the *run*, not the *tree* — applies queue behind the approval wait (serialized `otterdog-mutate` group), so a later merge to trunk could supersede a still-waiting run, and approving that older run mutated live state toward a config no longer on `main` (the [#99](https://github.com/vig-os/org-config/issues/99) incident: an approved stale tree recreated three intentionally deleted repos as empty stubs plus their rulesets, then exited rc=2 on the post-create patches). Two defenses, combining the first and third guards proposed in #105: **(1) supersession self-guard** — the gated job's first step (i.e. the first thing to run *after* approval, the only moment the check is meaningful) compares the run's `github.sha` against the live tip of the applied branch via the API; on mismatch every subsequent step skips, the job stays green, and a notice + job summary explain that the newer queued apply carries the delta. Consequence, documented in the workflow header: re-running an old run can never apply an old tree — re-applying the *current* state takes a fresh `workflow_dispatch`. **(2) pre-approval plan preview** — a new ungated, read-only `preview` job runs the *exact* tree's plan into the same run's job summary, one click from the approve button, so the reviewer sees what approving will execute instead of trusting the queue. It reuses `plan.yml` via a local `workflow_call` (single source of the plan harness; `plan.yml`'s fork-PR guard now also admits `push`, which is fork-safe by construction), is deliberately not a `needs:` of `apply` (a preview harness failure must never block a legitimate apply), and runs on this repo's own events only — the empty-`inputs` test distinguishes an own push/dispatch from a downstream `workflow_call`, so template callers ([#56](https://github.com/vig-os/org-config/issues/56)) are unaffected and can wire their own preview beside their apply caller. The cancel-superseded-runs variant from #105 was deliberately not taken: it needs `actions: write` on a separate trigger, and the self-guard already makes the superseded run die harmlessly at its own first step.
- **Otterdog bumped 1.3.4 -> 1.4.0 and the eighteen status-check tokens restored to the numeric `15368:` form** ([#69](https://github.com/vig-os/org-config/issues/69)): resolves both horns of the dilemma #69 documented. Upstream [eclipse-csi/otterdog#695](https://github.com/eclipse-csi/otterdog/issues/695) shipped in otterdog **1.4.0** ([PR #700](https://github.com/eclipse-csi/otterdog/pull/700)) as a **write-path-only** fix: a numeric `<integration_id>:<context>` token is now sent as `integration_id` instead of being resolved as an app slug (`GET /apps/15368` -> 404, the failure that broke every ruleset write since #65). The read/render path is untouched — and structurally so: otterdog's id->slug injection only consults `GET /orgs/{org}/installations`, and `github-actions` (app_id 15368) is a first-party app that is never an org installation, so live rulesets *always* read back numeric. The slug migration in [#129](https://github.com/vig-os/org-config/issues/129) (a workaround for the write 404) therefore produced a permanent phantom `15368:X -> github-actions:X` plan diff on all twelve app-bound rulesets, filed by the drift layer as [#130](https://github.com/vig-os/org-config/issues/130)–[#141](https://github.com/vig-os/org-config/issues/141) — this restores the numeric form (undoing `3487ed9`), which zeroes the plan and lets the reconciler auto-close all twelve on the next scheduled run. The canonical prefix form is thus **per-app** (numeric for first-party apps, slug for org-installed ones), recorded in an inline comment in `otterdog/vig-os/vig-os.jsonnet`. The pin is bumped in `justfile.project` (SSoT, ADR-0005) **and** in the four hand-maintained `template/.github/workflows/{plan,apply,drift,import}.yml` literals, which are not wired to the SSoT ([#56](https://github.com/vig-os/org-config/issues/56)); L1 plan fixtures re-checked against 1.4.0 per ADR-0007. The `gh api` manual-PUT interim from #69 stays the fallback until a real ruleset write under 1.4.0 confirms the fix end-to-end.

### Security

- **The one-time `all -> selected` flip executed for the nine dummy-valued org secrets; declared consumer lists refreshed to post-devkit-1.7.0 reality and pre-seeded for the client-ID migration** ([#112](https://github.com/vig-os/org-config/issues/112)): the org owner performed the UI flip on 2026-08-10 (by #123's design the dummy-valued declarations are documentation, so the flip is out-of-band by construction), and this change re-aligns the declared `selected_repositories` lists with what was actually implemented. The lists were re-derived from a same-day sweep of every live default-branch `.github` workflow tree (all org repos, `.yml` and `.yaml`) because the #123 sweep of 2026-08-07 had **gone stale within 72 hours**: the devkit 1.7.0 adoptions re-scaffolded `sync-issues.yml` from `app-id` to `client-id` in `devkit`, `devkit-smoke-test`, and `org-config`, so `COMMIT_APP_ID` narrows by those three repos — its remaining consumers are `commit-action` and `sync-issues-action` (numeric form in their pre-1.7 `sync-issues.yml`) plus the fully-legacy `h5v` and `scitadel`. The same wave made `DEVKIT_UPGRADE_APP_CLIENT_ID` (declared consumer-less in #114) a real consumer secret: `devkit-smoke-test` and `org-config` reference it today, transitionally alongside the numeric form. Deliberately wider than strict references: `h5v` and `scitadel` are **pre-seeded** into all three `*_CLIENT_ID` lists and the corresponding `*_PRIVATE_KEY` unions so their eventual re-scaffold ([#112](https://github.com/vig-os/org-config/issues/112)) starts with working credentials — avoiding the empty-credential-no-error trap the `DEVKIT_UPGRADE` maintenance-coupling comment documents. One transcription error in the UI flip was caught by reading the live lists back through the value-free `GET /orgs/vig-os/actions/secrets/<name>/repositories` endpoint — `RELEASE_APP_CLIENT_ID` briefly granted `nvd-mirror` (adjacent in the repo picker) instead of `scitadel` — and corrected through the same value-free repositories API. That near-miss is the concrete case for asserting these lists mechanically: nothing in this repo would have noticed, which is exactly the [#116](https://github.com/vig-os/org-config/issues/116) drift-assertion gap.
- **The remaining eleven org secrets declared `visibility: selected` with per-secret consumer lists** ([#123](https://github.com/vig-os/org-config/issues/123)): all twelve `vig-os` organization secrets were `visibility: all`, so three GitHub App **private keys** and a Docker Hub token were readable by every workflow in all 14 repos — including unmaintained `vs-dolt` and the automation-churned `org-config-testbed`, neither of which consumes a single org secret. Lists were derived from a full sweep of every `secrets.*` reference in all 14 repos (whole `.github` tree, `.yml` **and** `.yaml` — `vs-dolt` uses the latter and a `*.yml` glob would have missed it; cross-repo `workflow_call` checked and absent, so every `secrets: inherit` resolves in the repo declaring the caller). The lists deliberately differ per secret rather than sharing one: the client-ID migration ([#112](https://github.com/vig-os/org-config/issues/112)) means `*_APP_CLIENT_ID` covers the five repos on `DEVKIT_VERSION=1.6.0` while `*_APP_ID` still covers `h5v` (`0.3.1`) and `scitadel` (`0.3.3`), and the private keys are the union. `DEVKIT_UPGRADE_APP_*` reaches only the four repos actually carrying a scaffolded `devkit-upgrade.yml`; a **maintenance-coupling comment** in the jsonnet records that any repo re-scaffolded to devkit >= 1.6 must be added or its upgrade workflow fails with an empty credential and no error. `DOCKERHUB_TOKEN`/`DOCKERHUB_USERNAME` get an empty list — they are orphaned (zero consumers org-wide; `vs-dolt` uses its own repo-level `DOCKER_HUB_*`), with retirement tracked in [#125](https://github.com/vig-os/org-config/issues/125). **Config-only change, and inert until the values become resolvable:** these eleven are declared `value: '********'`, and `otterdog/models/secret.py:88` excludes dummy-valued secrets from live-patch generation (`models/__init__.py:788`), while the REST API rejects a visibility change without `encrypted_value`+`key_id` (HTTP 422). So the one-time `all -> selected` flip is a UI action by the org owner — and because `plan` renders live patches, these eleven produce **no plan diff at all**, verified empirically. The declared visibility is therefore documentation of the intended state, **not** an assertion: nothing in this repo will notice if a list is widened again. Machine-checking it belongs with the other unmanaged controls in [#116](https://github.com/vig-os/org-config/issues/116); making it genuinely declarative would require moving the eleven values into SOPS as the canary already is, which collides with ADR-0003's deliberate bootstrap exclusions and is out of scope here.
- **`ORG_CONFIG_CANARY` narrowed from org-wide to `org-config` only** ([#123](https://github.com/vig-os/org-config/issues/123)): first secret migrated off `visibility: all`, and the pilot for the remaining eleven. A grep of every `secrets.*` reference in all 14 `vig-os` repos (both `.yml` and `.yaml`, whole `.github` tree, cross-repo `workflow_call` checked and absent) found **no workflow anywhere reads this secret** — it is written by `otterdog apply` from the committed SOPS ciphertext and exists only to prove that pipeline, so `org-config` is the entire audience. It is also the only org secret this repo can migrate declaratively: its jsonnet value is a real credential-provider reference (`pass:org-config/ORG_CONFIG_CANARY`) rather than a `'********'` dummy, so `include_for_live_patch` is true (`otterdog/models/secret.py:88`) and `apply` writes visibility itself. The other eleven are dummy-valued and therefore **skipped** by apply, and the REST API refuses a visibility change without `encrypted_value`+`key_id` (HTTP 422), so their one-time `all -> selected` flip is a UI action — tracked in [#123](https://github.com/vig-os/org-config/issues/123).
- **Workflows can no longer approve pull requests anywhere in `vig-os`** ([#121](https://github.com/vig-os/org-config/issues/121)): the org-level `settings.workflows.actions_can_approve_pull_request_reviews` was `true`, so a GitHub Actions workflow could submit an **approving review** — the one permission that satisfies `Main protection`'s `required_approving_review_count: 1` without a human, reachable by any workflow with `pull-requests: write`, including one introduced by the very PR it would approve. With `allowed_actions: all` and no action allow-list, that reached every repo in the org. `devkit` was the only repo closing it at repo level; it is now `false` org-wide. `devkit`'s repo-level declaration is deliberately left in place — redundant with the new default, but it keeps the intent explicit on the repo that publishes the fleet's tooling. Note the nesting: org-level workflow settings live under `settings.workflows` in the vendored schema's `newOrg`, a different location from the repo-level `workflows+:` block that hangs directly off `newRepo`.
- **Organization members can no longer create repositories** ([#121](https://github.com/vig-os/org-config/issues/121)): `members_can_create_public_repositories` and `members_can_create_private_repositories` flip from an explicit `true` to an explicit `false`. Repository creation in this org is config-first — a repo is declared in `otterdog/vig-os/vig-os.jsonnet` and `otterdog apply` creates it — and a repo created through the UI instead bypasses every default this repo exists to enforce (merge policy, rulesets, signed commits, secret scanning) while starting with no ruleset at all. The recovery path is deliberately asymmetric: apply **creates** what the config declares but never **deletes** what it omits (`--delete-resources` is deliberately omitted, `.github/workflows/apply.yml:87`), so an undeclared repo is never cleaned up automatically — it surfaces only as a `drift` + `critical` inventory issue in the `repository-inventory:<name>` namespace ([#21](https://github.com/vig-os/org-config/issues/21)) and is then removed by hand. This binds today rather than being theoretical: the org has three members, of whom one is a plain member. Organization **owners** can always create repositories — GitHub grants that unconditionally and no org setting revokes it — so for them the config-first rule remains discipline backed by the drift sweep. That residual is accepted, not overlooked.
- **`devkit`'s `main` now dismisses stale approvals on push** ([#118](https://github.com/vig-os/org-config/issues/118)): `Main protection` required 1 approving review but left `dismiss_stale_reviews_on_push` off, so an approval survived every subsequent push to the PR branch — a reviewer could sign off on a two-line docs change and the author could then push arbitrary commits onto the same branch and merge to `main` on the strength of a review that never saw them. The required status checks are `strict` and re-run on every push, so CI could never be stale; the human review could, and after [#115](https://github.com/vig-os/org-config/issues/115) retired the unsatisfiable code-owner gate it is the only human control on `main`. `dismisses_stale_reviews: true` closes that window. `main` only: `Dev protection` and `Release protection` both require 0 approvals, so they have no review to dismiss.
- **CodeQL is now a required status check on `devkit`'s `main`** ([#115](https://github.com/vig-os/org-config/issues/115)): `devkit`'s `codeql.yml` already ran on every PR to `main`, but `Main protection` gated only on `15368:Test Summary`, so a PR with a red CodeQL leg merged. The ruleset now also requires `15368:CodeQL Analysis (actions)` and `15368:CodeQL Analysis (python)` — **two** contexts rather than one, because the workflow's `analyze` job is a `language: ['python', 'actions']` matrix and each leg reports under its own matrix-suffixed name (the single `CodeQL` check on the same commit comes from the `github-advanced-security` App, not from `github-actions`/`15368`, and is the code-scanning result check rather than a workflow job). `devkit` is public, so `codeql.yml`'s `if: ${{ !github.event.repository.private }}` guard never skips the job and neither context can hang pending. `Dev protection` and `Release protection` are deliberately unchanged — `main` is the branch releases are cut from.
- **`devkit` secret-scanning extras: found unsettable, not changed** ([#115](https://github.com/vig-os/org-config/issues/115)): `security_and_analysis.secret_scanning_non_provider_patterns` and `secret_scanning_validity_checks` read `disabled` on `devkit` despite the repo being public with secret scanning and push protection on, and they **cannot be turned on from here**. otterdog 1.3.4 models only `secret_scanning` and `secret_scanning_push_protection` (`otterdog/models/repository.py`; the vendored `otterdog-defaults.libsonnet` exposes the same two), so neither can be declared — and the out-of-band route is a dead end too: `gh api -X PATCH repos/vig-os/devkit` returns `200 OK` and silently changes nothing, because `devkit` is attached to the **enforced** `vig-os` code-security configuration `237480` ("Github + Advanced QL allowed"), which already declares both `enabled` at org level. An enforced configuration overrides repo-level writes, so the org says enabled, the repo reads disabled, and no write from either side moves it — the features need a GHAS Secret Protection entitlement the org's plan does not carry. Nothing was changed; the org configuration is deliberately left alone (it governs every repo in the org, and its `code_scanning_default_setup: enabled` interacts with `devkit`'s advanced CodeQL workflow). Recorded in [#116](https://github.com/vig-os/org-config/issues/116) as an **asserted** row carrying a `tolerated` value — `expect = "enabled"` (the desired state, on record) with `tolerated = "disabled"` (today's unsettable reality), so the row is clean-but-noted now and goes green by itself if the entitlement ever lands, rather than being silenced in `drift-allowlist.toml`. The same shape covers `sha_pinning_required` (true on `devkit`, false org-wide, unmodelled by otterdog: `expect = true`, `tolerated = false`); the fork-PR approval policy is asserted outright against `/orgs/{org}/actions/permissions/fork-pr-contributor-approval`, which does resolve. No row in the shipped `unmanaged-controls.toml` uses `kind = "unassertable"` — the escape hatch exists in the schema but nothing needed it.
